Block 1: AI-assisted R programming

Prerequisites

  • A GitHub account, an IDE (RStudio or Positron), and the Git, renv and testthat skills from earlier sessions.
  • Claude Code, the workshop’s main tool, installed and checked before the day: follow Setting up Claude Code, which also lists the accounts it works with.
  • An Anthropic API key for Block 6, where you build your own agent in R. It is separate from a Claude subscription; Setting up Claude Code shows how to get one and test it.
  • Posit Assistant works as an alternative for most blocks; each block has a collapsed Using another tool callout saying where it differs.
  • Your institution’s permission to use these tools, and, near research data, your ethics approval and data agreements. Block 3 covers this.

GitHub Copilot is needed only for the self-study page on inline completions.

Learning outcomes

By the end of the day you will be able to:

  1. Explain what a large language model is and why the model choice matters.
  2. Debug your own code with AI, and know when AI helps most.
  3. Choose how much an agent may do, and know every route by which your data leave your machine.
  4. Write an AGENTS.md instruction file and a skill, and test that they load.
  5. Protect files with a permission rule, and detect any change with git.
  6. Build a small agent in R, and say where approvals and permission rules act inside it.
  7. Have an agent clean data against a codebook you own, and check it with tests.
  8. Have an agent refactor code under a characterisation testA test that checks new code reproduces the saved output of the original code exactly. It shows the output is unchanged, not that it is correct., with the reference in your hands.

Materials

You work in your own copy of a workshop template repository, forked before the day and used in every block from Block 2 (its layout, and what each block uses).

TipReference: how the day is made forgiving

The repository holds a synthetic voles dataset, scripts, and three things that make the day forgiving:

  • Tests that wait. The tests that check the protections pass from the start; every other test skips until its block is done. In the wrap-up they run together as one suite.
  • Checkpoint branches. checkpoint-skills, checkpoint-cleaning and checkpoint-refactor: if you fall behind, switch to the next one from the Git pane’s branch menu and carry on. Nobody needs to finish every exercise.
  • Built-in protections. The raw data, the checks and the references are protected before you start.

Verification is the workshop’s only non-negotiable, and it is what lets you automate with confidence: once you can check an agent’s work quickly and independently, you can hand it more of the work. Every exercise ends with that check.

The thread through the day: Check · Reproduce · Record

Every block applies three habits, and ends with a box saying what it added:

  • Check. Treat what an AI produces as a claim, and verify it independently: the data, a test, a reference you hold, the Git pane’s diff, or your own knowledge of the biology.
  • Reproduce. The code runs in a fresh R sessionAn R session with nothing loaded from earlier work: Session > Restart R in RStudio or Positron (with “never save .RData” set, as on Day 1), callr::rscript() from the console, or Rscript in the terminal. Code that only works in your current session depends on something you did not record. with the package versions in the lockfileThe renv.lock file that records the R version and the exact package versions a project uses, so renv::restore() can rebuild the same environment., and nothing changed that you did not see.
  • Record. Leave the evidence a reader needs: a codebook, logs of every data change, numbers computed in code, and a log of your AI use.

Your workshop repository starts Claude Code in Manual mode (default): it asks before every edit and before most commands (read-only ones, such as head, run without asking). Claude Code’s own default is auto, where a second model approves actions for you; Block 3 explains the difference. Stay in Manual and read each request before you answer. One rule for every approval: approve a run only if you can say what it does and why you want it now; refusing is always safe.

Block 1: framing

This block gives you the two words you will use all day, what a large language model is, and why its context window matters. It ends with a short discussion and a quiz.

⏱ ~20 minutes: presentation, a short discussion and a quiz, while any set-up problems are sorted out.

Framing and mental models

Two words recur all day. An assistantAny AI tool that helps you write or understand code, from inline completion to a chat window. In this course “assistant” is the general word; “agent” is used when the tool acts on your files. is any AI tool that helps you write or understand code. An agentAn assistant that can read across a project’s files and, depending on its permission mode, edit them and run commands, such as Claude Code. An agent acts; a chat window only advises. is an assistant that acts: it reads your project and, if you let it, edits files and runs commands. Claude Code and Posit Assistant are agents; a chat window that only answers is not. To see how one works inside, you build a small one yourself in Block 6.

What is a large language model?

A large language model predicts the next fragment of text from what came before, having learnt from a large share of the public internet, code included. Every tool today is built on one. Models differ in code quality and in how often they invent functions that do not exist, so if a model gives you consistently poor suggestions and your plan lets you switch, switching is a cheap experiment.

Why the context window matters

An LLM has no memory between calls: each one starts with only what you supply, up to the limit of its context windowThe maximum amount of text a language model can consider in one call. The model has no memory between calls, so it sees only what is in the context window.. That one fact explains the day. Instruction files and skills give the model context it would not otherwise have; because they are only requests, Block 5 adds controls that hold either way, and tests check the result.

Remember: the AI sees only what you give it, and everything it sees has left your machine.

Going further (not covered live)

This material is not covered in the live session. Work through it afterwards if it is useful to you.

TipWhich tool does what
  • Claude Code runs in the Terminal tab of RStudio or Positron, which starts in your project’s root folder: the folder it acts on. Every block’s main text uses it, and checks its work from the R console and Git pane.
  • Posit Assistant is the in-IDE chat and agent in RStudio and Positron. It can also see your live R session. See What’s new in Posit AI.
  • GitHub Copilot gives inline completions in RStudio and Positron. Its cloud agent, used only in some Going further sections, needs a paid plan; see the Copilot plans page.
TipModels

Claude Code uses Anthropic’s Claude models; Posit Assistant runs on Posit AI or a provider key you configure; GitHub Copilot offers Claude, GPT and Gemini models. You do not need strong opinions about which model is best, only to know that the choice exists and changes the output.

TipTwo modes of execution

The tools you use today are synchronous and local: they work on your machine, respond in seconds, and can be interrupted. Their reach differs: the current file for inline completion, the project folder and the output of its own commands for Claude Code, and your live R session too for Posit Assistant. An asynchronous, remote agent, such as the Copilot cloud agent, works on its own branch on someone else’s servers and returns a pull request minutes later; you meet it in the Going further sections of Blocks 3, 5 and 8. The first invites you to watch and interrupt; the second, to write a precise specification and review what comes back. Block 3 turns this into a ladder of autonomy.

TipThe thread, in more detail

Day 1 introduced renv; Day 4 checks that an agent has kept to it. On Day 2 you saw what a reviewable project needs (TADA! and the README, and the SORTEE checklist); Day 4 shows how AI can help produce that record without inventing any of it. Many journals, funders and institutions now ask authors to declare AI use, and a log written at the time is easier and more accurate than one reconstructed later.
