Block 1: AI-assisted R programming

Prerequisites

  • A GitHub account, an IDE (RStudio or Positron), and experience with Git, renv and testthat from earlier days.
  • Claude Code, the workshop’s main tool, installed and checked before the day: follow Setting up Claude Code, which also lists the accounts it works with.
  • An Anthropic API key for Block 6, where you build your own agent in R. It is separate from a Claude subscription; Setting up Claude Code shows how to get one and test it.
  • Posit Assistant works as an alternative for most blocks; each block has a collapsed Using another tool callout saying where it differs.
  • Your institution’s permission to use these tools, and, near research data, your ethics approval and data agreements. Block 3 covers this.

GitHub Copilot is needed only for the two self-study pages: inline completions (Copilot Free is enough) and the Copilot cloud agent (a plan that includes it).

Learning outcomes

By the end of the day you will be able to:

  1. Explain what a large language model is, how a tool differs from the model behind it, and why what is in its context window matters (this block).
  2. Debug your own code with AI, and know when AI helps most (Block 2: Debugging with AI).
  3. Choose how much an agent may do, and know every route by which your data leave your machine (Block 3: Context, disclosure and autonomy).
  4. Write an AGENTS.md instruction fileA file the assistant loads into every conversation, such as AGENTS.md or CLAUDE.md, stating the project’s standing conventions. Its contents are requests, not guarantees., install a skillA reusable procedure for one kind of task: a folder containing a SKILL.md file (and optionally scripts and templates) that an assistant loads only when it is invoked by name or judged relevant from its description., and test that they load (Block 4: Instructions and skills).
  5. Protect files with a permission rule, and detect any change with git (Block 5: Enforced controls).
  6. Build a small agent in R, and say where approvals and permission rules act inside it (Block 6: Build your own agent in R).
  7. Have an agent clean data against a codebook you own, and check it with tests (Block 7: Data cleaning and validation).
  8. Have an agent refactor code under a characterisation testA test that checks new code reproduces the saved output of the original code exactly. It shows the output is unchanged, not that it is correct., with the reference in your hands (Block 8: Functionalise a script step).
  9. Use AI as a code reviewer, and grade it against the Day 2 answer key (Block 9: AI-assisted code review).

Materials

You work in your own copy of a workshop template repository. You fork it before the day and use it in every block from Block 2 to Block 8, and on the self-study page on the Copilot cloud agent (its layout, and what each block uses). Block 9 works in a separate folder, ~/ai-review, so that the AI reviewer sees only the script under review.

Every block ends with a Going further section that is not covered live. The two self-study pages listed under Prerequisites are for after the day.

Verification is the workshop’s only non-negotiable. It lets you automate with confidence. Once you can check an agent’s work quickly and independently, you can hand it more of the work. Every exercise ends with that check.

The thread through the day: Check · Reproduce · Record

Every block applies three habits, and ends with a box saying what it added:

  • Check. Treat what an AI produces as a claim. Verify it independently against the data, a test, a reference you hold, the Git pane’s diff (Positron: the Source Control view), or your own knowledge of the biology.
  • Reproduce. The code runs in a fresh R sessionAn R session with nothing loaded from earlier work: Session > Restart R in RStudio or Positron (with “never save .RData” set, as on Day 1), callr::rscript() from the console, or Rscript in the terminal. Code that only works in your current session depends on something you did not record. with the package versions in the lockfileThe renv.lock file that records the R version and the exact package versions a project uses, so renv::restore() can rebuild the same environment., and nothing changed that you did not see.
  • Record. Leave the evidence a reader needs: a codebookA table describing each variable: its type, valid range, missing-value codes, unit and label mappings. It is the data dictionary from Day 2 with machine-readable rules, and you own it, not the AI., logs of every data change, numbers computed in code, and an AI-use logA record written at the time of each piece of AI-assisted work, in the form: date; tool and model; task; what you kept or changed. It becomes the AI declaration in a README..

Claude Code keeps running on your computer, with the same files, permission rules and approvals, so the computer and the claude process must stay on. An approval you tap on your phone follows the same rule as one at your desk.

Your workshop repository starts Claude Code in Manual mode (default): it asks before every edit and before most commands (read-only ones, such as head, run without asking). Claude Code’s own default is auto, where a second model approves actions for you; Block 3: Context, disclosure and autonomy explains the difference. Stay in Manual and read each request before you answer. One rule for every approval: approve a run only if you can say what it does and why you want it now; refusing is always safe.

Framing: tools, models and context

This block introduces the two words you will use all day, the three tools and how they differ, what a large language model is, and why its context window matters.

⏱ ~20 minutes: presentation, a short discussion and a quiz, while any set-up problems are sorted out.

Assistants and agents

Two words recur all day. An assistantAny AI tool that helps you write or understand code, from inline completion to a chat window. In this course “assistant” is the general word; “agent” is used when the tool acts on your files. is any AI tool that helps you write or understand code. An agentAn assistant that can read across a project’s files and, depending on its permission mode, edit them and run commands, such as Claude Code. An agent acts; a chat window only advises. is an assistant that acts: it reads your project and, if you let it, edits files and runs commands. Claude Code and Posit Assistant are agents; a chat window that only answers is not. To see how one works inside, you build a small one yourself in Block 6: Build your own agent in R.

A tool is not a model. The tool decides where you type, what it can read and what it may do. What is a large language model?

A large language model (LLM) predicts the next fragment of text from what came before. It has learnt from a large share of the public internet, code included. Every tool today is built on one. Models differ in code quality and in how often they invent functions that do not exist. If a model gives you consistently poor suggestions and your plan lets you switch, try another: switching is a cheap experiment.

Model and effort level. Two settings change what you get. The model is which LLM answers: larger models, such as Opus, are more capable and cost more per token; smaller ones, such as Sonnet and Haiku, are faster and cheaper. The effort levelHow much a model reasons before it answers. In Claude Code it runs from low to max; a higher level can help with hard problems, but it is slower and uses more tokens. sets how much the model thinks before it answers: higher effort can help with hard problems, but it is slower and uses more tokens. The quick reference shows how to change both. Whatever you use, record the model in your AI-use log.

Why the context window matters

An LLM has no memory between calls: each one starts with only what you supply, up to the limit of its context windowThe maximum amount of text a language model can consider in one call. The model has no memory between calls, so it sees only what is in the context window.. That one fact explains the day. Instruction files and skills give the model context it would not otherwise have. They are only requests, so Block 5 adds controls that hold whether or not the model follows them, and tests check the result.

Remember: the model sees only what reaches its context window, and everything that reaches it has left your machine.

TipChanging the model in other tools

In Posit Assistant, use its model picker. In Copilot Chat, use the model menu (inline completions have a separate setting). In R, ellmer::chat_anthropic() takes the model as model =, and the effort level as params = params(reasoning_effort = "low"); Block 6 sets the model this way.

TipTwo modes of execution

The tools you use today are synchronous and local: they act on files on your machine, respond in seconds, and can be interrupted. An asynchronous, remote agent, such as the Copilot cloud agent, works on its own branch on someone else’s servers. It returns a pull request minutes later; the self-study page on the Copilot cloud agent walks through it. The first kind invites you to watch and interrupt. The second invites you to write a precise specification and review what comes back. Block 3 turns this into a ladder of autonomy.

TipThe thread, in more detail

Day 1 introduced renv; Day 4 checks that an agent has kept to it. On Day 2 you saw what a reviewable project needs (TADA! and the README, and the SORTEE checklist). Day 4 shows how AI can help produce that record without inventing any of it. Many journals, funders and institutions now ask authors to declare AI use, and a log written at the time is easier and more accurate than one reconstructed later.
