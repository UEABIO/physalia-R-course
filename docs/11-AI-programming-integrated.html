Block 1: AI-assisted R programming

Prerequisites

You need a GitHub account, a working IDE (RStudio, Positron, or VS Code), and basic Git and GitHub fluency at the level of cloning a repository, making a branch, opening a pull request, and merging. Block 9 also assumes a working knowledge of renv and testthat, both covered in earlier sessions.

The workshop’s main tool is Claude Code, Anthropic’s agent that runs in a terminal. You need a Claude Pro or Max subscription, a Claude for Teams or Enterprise seat, or a Claude Console account billed per request. Installing it and running the checks in Setting up Claude Code is pre-work: do it before the day.

If you prefer to work inside RStudio or Positron, Posit Assistant is supported as an alternative. It runs on a Posit AI subscription or on a provider key you supply, and each page notes where it differs from Claude Code.

GitHub Copilot is needed only for inline completion in Block 2, for which Copilot Free is enough, and for the optional cloud-agent material in some Going further sections, which needs a paid plan. Check the Copilot plans page for what is currently available.

Whichever tools you use, check that your institution permits them, and if you will use them near research data, that your ethics approval and data agreements allow it. Block 4 covers this in detail.

Learning outcomes

By the end of the workshop, you will be able to:

  1. Articulate what a large language model is, and explain what choosing between underlying models materially affects.

  2. Use inline completion in your chosen IDE, and identify what context the tool can and cannot see.

  3. Use AI assistance to debug code you have written, and recognise the cases in which AI is most and least useful for debugging.

  4. Explain what an assistant can see and do, identify every route by which your data leave your machine, and choose an appropriate level of autonomy for a task.

  5. Write and test an AGENTS.md instruction file and a skill, and explain why both are requests to the model rather than guarantees.

  6. Test a permission rule that protects raw data, find a route around it, and detect any change with git.

  7. Clean data with an agent against a codebook you own, and check the result with validation rules and an audit of every change.

  8. Use AI as a code reviewer and grade its findings against a known answer key.

  9. Have an agent functionalise a script step under a characterisation testA test that checks new code reproduces the saved output of the original code exactly. It shows the output is unchanged, not that it is correct., keeping the reference in your own hands, and explain why an unchanged result is not necessarily a correct one.

  10. Check an AI translation of analysis code for equivalence, report results without typed numbers, and leave with a documented repository: a README drafted only from verifiable inputs, and a log of your AI use.

Materials

Participants will work with a synthetic biological dataset (voles_metabolism.csv) and a workshop template repository that they fork before the day (its layout is in Your workshop repository). The template uses renv for project-local packages, so after forking and opening the project, run renv::restore() once as part of the pre-work. Block 7 uses a copy of the voles data with errors planted in it (data/raw/voles_raw.csv), which ships with the template, and Block 8 uses the project folder from https://osf.io/jgeq9/ that you reviewed by hand on Day 2.

The template also ships a tests/ folder. Each test waits (skips) until the block that creates its files is done, so the folder grows into one test suite that you run at 16:00 to confirm the whole day’s work still holds. And it has three checkpoint branches, block5-done, block7-done and block9-done: if you fall behind, switch to the next one from the Git pane’s branch menu and carry on. Nobody needs to finish every exercise to finish the day.

A note on platform variation

  • Claude Code runs in the Terminal tab of RStudio or Positron, which starts in your project’s root folder: the folder Claude Code acts on. The main text of every block uses it, and checks its work from the R console and the Git pane (see checking work).
  • Posit Assistant is the alternative: the in-IDE chat and agent in RStudio and Positron, which can see your live R session as well as your project files. See What’s new in Posit AI. Where it differs from Claude Code, a collapsed Using Posit Assistant box says how.
  • GitHub Copilot provides the inline completions in Block 2, in all three IDEs.

Verification is the workshop’s only non-negotiable. AI tools generate plausible code quickly. They do not guarantee correctness, and they do not relieve you of responsibility for what your code does. Every exercise in this workshop ends with a verification step. Treat that step as the most important part of the exercise. Verification is also what lets you automate with confidence: once you can check an agent’s work quickly and independently, you can hand it more of the work.

The thread through the day: Check · Reproduce · Record

Every block applies the same three habits to a different task, and each block ends with a short box saying what it added to each:

  • Check. Treat everything an AI produces as a claim, and verify it with something independent of the AI: the data, a test, a reference you hold, git diff, or your own knowledge of the biology.
  • Reproduce. Make sure the result does not depend on the session it came from. What is a large language model?

A large language model (LLM) is a statistical model trained to predict the next token (roughly, the next fragment of text) given the tokens before it. Modern LLMs are trained on a substantial portion of the public internet, including code repositories, technical documentation, and prose. Every tool in this workshop is built on LLMs. Claude Code uses Anthropic’s Claude models. Posit Assistant runs on Posit AI or on the provider key you configure. GitHub Copilot offers several providers: Anthropic’s Claude family, OpenAI’s GPT family, and Google’s Gemini family. Where a tool exposes a model picker, the choice matters, because models differ measurably in code quality, instruction-following, and propensity to hallucinate library calls or function signatures that do not exist.

For the present workshop, you do not need to develop strong opinions about which model is best. You do need to know that the choice exists, that it changes the output, and that if a model produces consistently poor suggestions for your work and your plan lets you choose, switching is a cheap experiment.

Two modes of execution

An assistant can act on your behalf in two quite different modes. The first is synchronous and local: inline completion, Claude Code in your terminal and Posit Assistant in your IDE all work on your machine, respond in seconds, and can be interrupted at any point. This is the mode you use all day. Their scope is whatever the tool can reach: the current file for inline completion, the project folder and the output of the commands it runs for Claude Code, your live R session for Posit Assistant.

The second is asynchronous and remote. An agent such as the Copilot cloud agent takes a task, works on its own branch on someone else’s servers, and returns a pull request for you to review some minutes later. You meet it only in the Going further sections of Blocks 4, 6 and 9.

The two modes invite different verification. The synchronous mode invites you to watch and interrupt; the asynchronous mode invites you to write a precise specification, walk away, and review what comes back. Block 4 refines this into a ladder of autonomy, from suggesting the next line to acting with no prompts (acting remotely is the extra rung in its Going further section), and Block 5 shows how much of the specification can be written once, in instructions and skills.

Why the context window matters

LLMs do not have memory between calls. Each interaction starts fresh, with whatever you supply as context. The context windowThe maximum amount of text a language model can consider in one call. The model has no memory between calls, so it sees only what is in the context window. is the upper limit on how much text the model can consider in a single call. This is the technical fact that motivates everything else in the workshop: instructions exist to inject persistent context into a system that has none; skills exist to make procedural context available on demand. And because instructions and skills are only context, which the model may or may not follow, Block 6 adds controls that hold whether or not the model reads them.

If you remember nothing else from this block, remember that the AI sees only what you give it, and that everything it sees has left your machine. The rest of the workshop is mostly about giving it the right things, and checking what it does with them.

Discussion

Take three minutes. Think about the two questions below on your own, then post a short answer to each in the Zoom chat. The facilitator picks out the most interesting answers to discuss as a group.

  1. What is one task you would like to hand to an agent by 16:00, and how would you check it? And is there anything you would not delegate at all?

  2. How do you use AI tools at the moment? Chat in the browser, IDE chats, terminal agents such as Claude Code?

The discussion does not need to reach consensus. Its purpose is to surface the criteria participants already apply intuitively, which will inform how they use these tools after the workshop.
