Block 3: Debugging with AI

AI is most useful for debugging code you wrote yourself. You know what you intended, so you can judge its diagnosis against your intention rather than against an unknown ground truth. It can spot syntax mistakes you missed, suggest fixes for errors, and explain unfamiliar messages.

This block uses three error types, ordered by what the debugger needs to know. The first is a typo that needs no data. The second needs the actual values in the data. The third runs cleanly, returns a plausible answer and is wrong; only knowledge of the expected result reveals it. The differences show where AI can stand in for looking up documentation, where it cannot stand in for inspecting the data, and where it cannot stand in for knowing the biology.

⏱ ~20 minutes

Setup

Load the voles data.

In the R console:

library(tidyverse)
voles <- read_csv(here::here("data", "raw", "voles_metabolism.csv"))

Use Claude Code, started from your workshop repository’s root folder. Claude Code cannot see the objects in your R console, such as voles or high_dose. It can read the files in your repository and run code itself, so it sees your data only by reading the file or running a command. Block 4 looks at what each tool can see.

Exercise 1: A syntax error

You wrote this in your script to count voles per treatment:

ggplot(voles, aes(x = treatment_arm)) +
  geom_barchart()

R returns:

Error in geom_barchart(): could not find function "geom_barchart"

1. Ask for a fix. In Claude Code or a chat window, paste the code and the error and ask. With inline completion, paste both into your script as a block comment, add # Fix this code:, and let the assistantAny AI tool that helps you write or understand code, from inline completion to a chat window. In this course “assistant” is the general word; “agent” is used when the tool acts on your files. suggest a continuation.

In the R script (for inline completion):

# This code gives an error:
# ggplot(voles, aes(x = treatment_arm)) +
#   geom_barchart()
#
# Error: could not find function "geom_barchart"
#
# Fix this code:

Before accepting any suggestion, write one sentence explaining why the original failed. That sentence is your verification step: if you can write it, you understood the fix; if you cannot, the AI has solved the problem and you have learned nothing.

ggplot(voles, aes(x = treatment_arm)) +
  geom_bar()

The function is geom_bar(), not geom_barchart(). ggplot2’s geoms use short names with no _chart suffix. “Could not find function” is R’s standard message when a function does not exist in any loaded package, and it is the easiest class of error to recognise.

Exercise 2: A logic error

You wrote this in your script to compute mean post-treatment mass for high-dose voles:

high_dose <- voles |>
  filter(treatment_arm == "high_dose")

high_dose |>
  summarise(mean_mass = mean(mass_post_g))

The code runs without error. R returns:

# A tibble: 1 × 1
  mean_mass
      <dbl>
1       NaN

There is no error message to paste. The code does exactly what you asked; the bug is in what you asked for. No assistant can diagnose this reliably without knowing what your data contain.

1. Inspect the data before asking for help. Three calls take seconds.

In the R console:

voles |> distinct(treatment_arm)
voles |> count(treatment_arm)
nrow(high_dose)

The first two show that the values are Control, Low_dose and High_dose (capital first letter, underscore between words). The third returns zero. You have diagnosed the bug without an AI.

2. Ask with the evidence in hand. Paste the code and the diagnostic output together and ask for confirmation.

Prompt (Claude Code or a chat window):

I am trying to compute mean post-treatment mass for high-dose voles.
My code:

  high_dose <- voles |>
    filter(treatment_arm == "high_dose")

  high_dose |>
    summarise(mean_mass = mean(mass_post_g))

returns NaN. But voles |> distinct(treatment_arm) returns
"Control", "Low_dose", "High_dose". I think the filter fails because of
the capitalisation. Is that the only problem?

The exercise is to ask with the diagnostic context already in place, not to ask the AI to diagnose blind. AI is quick at typo-spotting and syntax recall; distinct() is quicker at telling you what is in your data.

With Claude Code, you can ask it to run the diagnostics itself. Because it cannot see high_dose in your console, it will read the data file and rerun the code. Ask it to show the commands and their output, and read the output yourself before accepting its diagnosis.

TipUsing Posit Assistant

Posit Assistant can run the same diagnostics in your live R session. The rule is the same: ask it to show the commands and their output, and read the output yourself.

high_dose <- voles |>
  filter(treatment_arm == "High_dose")

high_dose |>
  summarise(mean_mass = mean(mass_post_g, na.rm = TRUE))

The value now matches the data exactly. na.rm = TRUE is a precaution: this dataset has no missing values in mass_post_g, but real biological data usually do.

Exercise 3: A correct-looking but wrong result

You wrote this to get the mean change in body mass by treatment arm:

voles |>
  mutate(mass_change_g = mass_pre_g - mass_post_g) |>
  summarise(mean_change = mean(mass_change_g), .by = treatment_arm)

It runs. There is no error and no NaN. R returns something like:

# A tibble: 3 × 2
  treatment_arm mean_change
  <chr>               <dbl>
1 Control             -0.21
2 Low_dose            -1.49
3 High_dose           -3.19

Every value is a small number of grams, plausible for a vole, so nothing looks wrong. But the result is the reverse of the truth. The treatment was designed to increase body mass, and the dataset was built so that mass rises with dose. The table says that mass falls, and falls most at the highest dose.

The data contain nothing that explains it: apart from one deliberate missing value in metabolic_rate_post, which this calculation does not use, glimpse(), distinct() and count() report nothing unusual. The fault is in the arithmetic: mass_pre_g - mass_post_g measures loss, when you wanted gain.

Note

Can an AI catch this? Only if it knows what the answer should be. Given the code and output alone, an assistant can describe what the code does, but nothing in the code or the output says that mass should rise. If you state the expected direction, it is far more likely to name the error. The knowledge that makes the error visible is yours.

1. Before you trust any result that runs cleanly, write down what a correct result should look like. Here: positive values, increasing from Control to High_dose. Then compare. The mismatch between “positive and increasing” and “negative and decreasing” is the diagnosis.

2. You may ask an AI for a second opinion, with the expected direction included. “This should show mass gain increasing with dose, but the values are negative and decreasing; what is wrong?” will usually get the sign error named. A prompt with only the code and output usually will not.

voles |>
  mutate(mass_change_g = mass_post_g - mass_pre_g) |>
  summarise(mean_change = mean(mass_change_g), .by = treatment_arm)

mass_change_g is post minus pre. With the subtraction the right way round, the means are positive and increase with dose, matching the study design. The original ran without complaint because subtraction works in either direction; the only signal that it was wrong was knowing what the answer should be.

The debugging checklist

When code fails, order matters: inspect the data first, ask the AI second.

  1. Read the error message in full. The function name and the phrase (“could not find function”, “object not found”, “non-numeric argument”) usually locate the bug.
  2. Inspect the relevant data. glimpse(), distinct() on categorical columns, summary() on numeric columns, and nrow() after a filter catch most logic errors in seconds.
  3. Check names exactly, including capitalisation and underscores. Most “object not found” errors are typos.
  4. If steps 1 to 3 do not locate the bug, give the assistant the code, the error message and the diagnostic output together. The combination is much more useful than the error alone.
  5. After the AI suggests a fix, write one sentence explaining why the original failed. If you cannot, you have not understood the fix.
  6. Before trusting a result that runs without error, state what it should look like (sign, rough magnitude, expected ordering) and compare. This check depends on your knowledge of the study, which no assistant has unless you supply it.

An aesthetic-mapping error

This error needs ggplot2’s grammar rather than the data. You wanted a scatter plot of post-treatment metabolic rate against post-treatment mass, coloured by treatment arm:

ggplot(voles, aes(x = mass_post_g, y = metabolic_rate_post)) +
  geom_point(color = treatment_arm) +
  labs(title = "Metabolic rate by mass")

R returns an error saying that object treatment_arm was not found. The exact wording varies between ggplot2 versions.

1. Ask for a fix. Before accepting it, write one sentence on why ggplot2 could not find treatment_arm.

ggplot(voles, aes(x = mass_post_g, y = metabolic_rate_post)) +
  geom_point(aes(colour = treatment_arm)) +
  labs(title = "Metabolic rate by mass")

treatment_arm is a column in the data, so the mapping must go inside aes(). An argument outside aes(), such as color =, expects a fixed value like "red" or "#0072B2". ggplot2 looked for an object called treatment_arm in your environment, found none, and stopped. colour and color are interchangeable in ggplot2.
