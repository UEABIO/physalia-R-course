Block 3: Context, disclosure and autonomy

Two questions decide how far you can trust an AI assistantAny AI tool that helps you write or understand code, from inline completion to a chat window. In this course “assistant” is the general word; “agent” is used when the tool acts on your files.: what can it see, and what can it do? You trace what reached the model provider in Block 2, then hand an agentAn assistant that can read across a project’s files and, depending on its permission mode, edit them and run commands, such as Claude Code. ⏱ ~30 minutes · Start on main, Git pane clean, Claude Code running in Manual mode.

Exercise 1: What can it see?

Name the routes (3 minutes)

Goal: see exactly what reached the model provider when the agent investigated in Block 2, so that you can name every route your data take.

Start state: Claude Code running in the Terminal tab, as you left it in Block 2.

ImportantWorking with confidential data: five habits
  1. Work on a copy. Put a synthetic or anonymised copy in the project, and run the final analysis on the real data yourself, outside the agent’s folder.
  2. Know your account. Commercial accounts (Team, Enterprise, API) are not used for model training; on Pro or Max, set /privacy-settings. Check your institution’s approval, ethics approval and data agreements first.
  3. Deny reads of sensitive folders in /permissions, for example Read(/data/confidential/**). It stops Claude Code’s own file reads and simple commands such as cat, but not R code that opens the file itself.
  4. Stay in Manual mode, but it does not ask before read-only commands such as head and cat, so keep confidential files out of the project (habit 1).
  5. Describe, don’t show. names() gives column names and summary() the shape of the data; print(), glimpse() and str() show actual values.
TipHow it works: tool notes

There is no .claudeignore file, and /sandbox is not available on native Windows. Posit Assistant blocks .Renviron and .env by default, and shares the names and types of objects in your session, not their values; code it runs can still print values.

TipContext you hold in your head (instructor demonstration)

An assistant’s answer about your data is only as good as its context: it is reliable only when it has real information, such as something you pasted, a file it read, or output from a command it ran. In Block 2 you mostly pasted that information yourself; once, you let the agent fetch it. Either way, everything it uses leaves your machine.

A data file supplies column names, but not your question or your design. Your instructor asks a new chat:

Prompt (browser chat):

I have a dataset with pre and post measurements. How should I analyse it?

and then, in another new chat:

Prompt (browser chat):

I have 72 voles, balanced across three treatment arms (Control, Low_dose,
High_dose) and two sexes (M, F). Each animal has body mass measured before
and after treatment, and a single post-treatment metabolic-rate reading.

My question is whether the high-dose treatment changes mass relative to
control, and whether the effect differs between sexes.

The dataset is small (n = 12 per cell). I will report effect sizes alongside
any inferential test. Given this design, what is a defensible primary
analysis, and what are the main threats to its validity?

The first gets a tour of options; the second can get a recommendation, because the design now exists outside your head. Treat it as a proposal to check: the primary analysis is your decision. To try it yourself, see Going further.

Exercise 2: What can it do?

The model is the same at every rungOne level of the autonomy ladder in Block 4, from suggesting a line (rung 0) to acting with no prompts (rung 5). Each step up removes a moment when you would have seen an action before it happened. of the autonomy ladder; what changes is its permission modeThe setting that decides how much Claude Code may do without asking: plan (read only), default (asks before edits and commands), acceptEdits (edits without asking) and bypassPermissions (never asks).: what it may do without asking. Rung 3, act with approval, is where routine work is safe: you start from a commit, so any change can be reverted; you see every edit and command first; and a test checks the result, whatever the agent reports.

NoteHow it works: the autonomy ladder

An assistant that advises leaves you to filter every change. An agent that acts removes that filter, unless you put it back: the rungs differ in how much of that filtering is left to you.

Rung What happens Claude Code Posit Assistant
0. Suggest Completes the line you are typing — Next Edit Suggestions
1. Ask Answers; changes nothing — (no ask mode; Block 2’s answer-only line is a request) Ask mode (/ask)
2. Plan Proposes steps; changes nothing until you approve /plan /plan
3. Act, with approval Edits files and runs commands, asking first Manual (default): the workshop’s starting mode Normal mode
4. Act, partly unsupervised Some actions without asking acceptEdits; auto (a classifier approves actions) Auto mode (/auto)
5. Act, unsupervised No prompts bypassPermissions YOLO mode (/yolo)

From rung 3 up, what changes is which tool calls run without your approval; Block 6, after lunch, builds that approval step in code. Your workshop repository starts Claude Code in Manual, although recent versions of Claude Code start in auto; keep Manual for confidential data. /plan can still run commands, so read any it proposes. Use rungs 0 to 3 only; the quick reference has the rest.

Each rung up removes a moment when you would have seen the action: in acceptEdits, for example, file commands such as cp and mv run without asking, so a cp over a raw data file needs no approval. And the higher the rung, the more an agent acts on its guesses about your conventions, which is why Block 4 writes them down.

Ask, plan, act (15 minutes)

Goal: have the agent add a column and a plot script at rung 3, then check its work with the diff and the tests, so that you trust the change because you checked it, not because the agent reported it.

Start state: your workshop repository on main, Git pane clean, Claude Code in Manual mode. Check its work from the R console and the Git pane (checking work).

1. Plan (rung 2). In Claude Code, type /clear, then:

Prompt (Claude Code):

/plan In scripts/explore_voles.R, add a mass_change_g column (mass_post_g
minus mass_pre_g) to the voles data frame itself. Create a new script
scripts/explore_mass_change_plot.R that plots mass_change_g by
treatment_arm and saves the figure to outputs/ with ggsave(). Don't run
anything; I'll check the scripts myself.

Before approving, check the plan names both files, adds the column to voles itself, leaves data/raw/ alone and saves the figure to outputs/. If anything is missing, choose No, keep planning and say what to change.

2. Act, with approval (rung 3). Choose Yes, manually approve edits. It is not the first option: the first, Yes, and use auto mode, switches the approvals off. Then read each edit before you approve it. Answer each request with plain Yes or No. Never choose an option that says don’t ask again: it saves a rule that skips the question from then on.

AGENTS.md makes it ask to run git status before it edits: that only reads, so Yes is fine. It may also ask to run the new scripts with Rscript. Approve a run only if you can say what it does and why you want it now; refusing is always safe. For the scripts, choose No: you check the result yourself next.

3. Read the diff. Click Diff in the Git pane for each changed file and read it as you would a colleague’s work: the diff shows every change, including any you did not ask for.

4. Record. Create docs/ai-log.md (usethis::edit_file("docs/ai-log.md")) and write the first line of your AI-use logA record written at the time of each piece of AI-assisted work, in the form: date; tool and model; task; what you kept or changed. It becomes the AI declaration in a README. yourself, on one line, in the form from Block 1. Don’t copy the example: put today’s date, as YYYY-MM-DD, and the model name shown above the Claude Code prompt.

2026-10-19; Claude Code (model as shown above the Claude Code prompt); added mass_change_g and a plot script; kept both after reading the diff

Writing it before you test means the tests check it too.

5. Test, then commit. Restart R (Session → Restart R), so nothing left in your session can make a test pass, and run:

In the R console:

testthat::test_dir(here::here("tests"))

The tests check that mass_change_g in voles really is post minus pre, that the plot script saves a figure in outputs/ from a fresh R session, and that your log line has four parts and a real date; tests for later blocks skip. Commit the log and both scripts together (git ignores outputs/).

You are done when you have read every line of the diff, the tests show no failures, the explore and ai_log lines of the test output show their tests under OK, not S (skipped), and your first log line is committed with both scripts.

If it goes wrong: select the unwanted change in the Git pane and click Revert, then ask again more clearly. If test_explore.R says voles has no mass_change_g, the agent made the column somewhere else: ask it to add the column to voles itself. An S on explore or ai_log means its file is missing or misnamed. Out of time? Carry on: at the end of Block 4, checkpoint-skills holds this block’s files (commit or discard your changes in the Git pane first, so the switch is not blocked).

TipStretch: reflect on the rungs

At which rung did you decide the most? Where would you have missed an unwanted change without the diff?

Payoff. What did the agent do, how long did checking it take, and would you automate this again?

NoteAt the command line

The same checks from a terminal (after /exit, or in a second Terminal tab): git status, git diff, and Rscript -e "testthat::test_dir('tests')".

NoteThe safe vibe-coding recipe
  1. Commit, so you start from a clean Git pane.
  2. Protect the inputs: /permissions shows the deny rules, or you add one.
  3. Have the checks ready: tests in tests/ before the agent starts.
  4. Ask in one prompt or skill, in Manual mode, reading each approval.
  5. Run the checks: the test suite in a fresh R session.
  6. Read the diff in the Git pane, then commit or revert.

You will use these six steps in Blocks 7 and 8; the template ships the protections and the tests, so most of it is checking they are there.

NoteCheck · Reproduce · Record
  • You can now: hand an agent a routine multi-file change at rung 3, trusted because you read every diff and a test you did not write checks the result.
  • Check: the Git pane’s diff after every agent action; the agent’s report that something “still runs” is a claim until a test confirms it.
  • Reproduce: work only in a committed, clean repository, so every change is a diff you can inspect or revert.
  • Record: your AI-use log starts here, in docs/ai-log.md.

TipAccess and cost

Plans and prices change; check before the session.

  • Claude Code needs an Anthropic account, used through a subscription or an API key; see Anthropic’s documentation for current options.
  • Posit Assistant uses Posit AI Pass or your own provider key, including an Anthropic API key. In RStudio, providers are configured in the assistant’s settings.
  • GitHub Copilot bills in AI credits; check GitHub’s plans page for what your plan includes.
  • Your institution may have approved some of these tools and not others.
TipTrusting a repository’s configuration

Project settings and hooks are code that runs on your machine. A cloned repository can carry its own, so trust only repositories whose configuration you have read.

TipGitHub Copilot and the remote rung

GitHub Copilot offers the same ladder in its own surfaces. Copilot Chat on github.com can also see files in the repository you open it from.

Rung 6, the Copilot cloud agent, works on the repository on GitHub, in an environment GitHub runs. It takes a task such as an issue, works on its own branch and returns a pull request. Copilot Free includes only limited agent features; check GitHub’s plans page to see whether your plan includes the cloud agent. The cloud agent appears in the Going further section of Block 8, where its pull request meets a review gate.

TipStretch: the same error at three levels of context

The code voles |> mutate(mass_change_g = mass_post - mass_pre_g) fails with “object ‘mass_post’ not found”. In three new browser chats, ask about it with more context each time: first the error message alone; then the error plus the code; then the error, the code and the output of glimpse(voles). Only with the column names in front of it can a chat name mass_post_g. Column names you never supplied, or a famous dataset you never mentioned (penguins, mtcars), are signs it is guessing.

TipExercise: context you hold in your head

To try the demonstration above yourself, ask a new browser chat the first prompt, then another new chat the second, and compare the answers. A data file can supply column names and types, but not your scientific question or your design intent.

Glossary

term definition
agent An assistant that can read across a project's files and, depending on its permission mode, edit them and run commands, such as Claude Code. An agent acts; a chat window only advises.
AI-use log A record written at the time of each piece of AI-assisted work, in the form: date; tool and model; task; what you kept or changed. It becomes the AI declaration in a README.
assistant Any AI tool that helps you write or understand code, from inline completion to a chat window. In this course "assistant" is the general word; "agent" is used when the tool acts on your files.
permission mode The setting that decides how much Claude Code may do without asking: plan (read only), default (asks before edits and commands), acceptEdits (edits without asking) and bypassPermissions (never asks).
rung One level of the autonomy ladder in Block 4, from suggesting a line (rung 0) to acting with no prompts (rung 5). Each step up removes a moment when you would have seen an action before it happened.
