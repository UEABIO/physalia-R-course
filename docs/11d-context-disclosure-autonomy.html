Block 4: Context, disclosure and autonomy

Two questions decide how far you can trust anything an AI assistantAny AI tool that helps you write or understand code, from inline completion to a chat window. In this course “assistant” is the general word; “agent” is used when the tool acts on your files. does with your code:

  1. What can it see? Its answers are only as good as its context, and everything it sees has left your machine.
  2. What can it do? An assistant that advises leaves you as the filter on every change. An agentAn assistant that can read across a project’s files and, depending on its permission mode, edit them and run commands, such as Claude Code. An agent acts; a chat window only advises. that acts removes that filter.

This block covers both, using Claude Code in the terminal. If you use Posit Assistant instead, the collapsed boxes give the differences.

⏱ ~33 minutes

Part A: What can the assistant see?

Surface Example What it can see Can it act?
Browser chat Any chat website What you paste No
Terminal agent Claude Code Project files, and the output of any command it runs Yes, in your files and shell
Session-aware IDE assistant Posit Assistant in RStudio or Positron Your live R session (loaded packages, data frames, console history) and project files Yes, in your session and files
Note

Knowing versus guessing. An assistant can describe your data confidently for two quite different reasons: it has been given real information, or it is recalling patterns from training data. Only the first is reliable.

It has real information when you pasted the output, when it read a file, when the IDE injected your session, or when it ran code and read the result. It is guessing when none of those apply. The tells are a well-known dataset you never mentioned (mtcars, iris, penguins) or column names and values you never supplied.

Even with context, a model’s account of what it can see is unreliable. Check any data-specific claim against the real object.

Exercise 1: Context decides the answer

The same error, three levels of context (10 minutes)

1. Error only. Open a new browser chat and ask “What does this error mean?”, pasting only this:

Prompt (browser chat):

Error in `mutate()`:
ℹ In argument: `mass_change_g = mass_post - mass_pre_g`.
Caused by error:
! object 'mass_post' not found

The answer can only reason from the error text.

2. Error plus code plus structure. Open another new chat and paste:

Prompt (browser chat):

I am running this code:

  voles |>
    mutate(mass_change_g = mass_post - mass_pre_g)

and getting:

  Error in `mutate()`:
  ℹ In argument: `mass_change_g = mass_post - mass_pre_g`.
  Caused by error:
  ! object 'mass_post' not found

The data structure is:

  Rows: 72
  Columns: 6
  $ subject_id          <chr> "V001", "V002", "V003", ...
  $ sex                 <chr> "M", "F", "M", ...
  $ treatment_arm       <chr> "Control", "Control", ...
  $ mass_pre_g          <dbl> 28.3, 27.9, 30.1, ...
  $ mass_post_g         <dbl> 28.5, 28.0, 30.5, ...
  $ metabolic_rate_post <dbl> 13.21, 12.84, 13.55, ...

What is wrong?

It should name the missing _g suffix.

3. No paste at all. Save the failing code as scripts/scratch_error.R in your workshop repository (usethis::edit_file("scripts/scratch_error.R") in the R console creates and opens it). In the project’s Terminal tab, start Claude Code in default mode with claude, and ask only:

Prompt (Claude Code):

Why does the mutate() call in scripts/scratch_error.R fail?

Claude Code can open the script and run code to inspect the data. Then ask: “How do you know the column names?” Compare its answer with what you know it was given. If it claims to have seen something it could not have seen, you have found the unreliability described in the callout above.

You are done when you can say which of the three answers named the real cause, and why. Then delete the scratch file, so Exercise 2 starts clean: in the R console, file.remove(here::here("scripts", "scratch_error.R")), or delete it from the Files pane.

TipUsing Posit Assistant

Load the data in your R session and run the failing code, then ask Posit Assistant only: “Why did my last command fail?” A session-aware assistant can read your console history and the data frame without your pasting anything.

The lesson is not that one route is correct. The answer is only as good as the context, and context reaches the model by more than one route.

Disclosure: every route out of your machine

Everything an assistant sees is sent to a model provider. Data leave your machine by four routes:

Everything on the left of an arrow reaches the model provider. Know which routes your tool can use before you decide what to show it.

  1. What you paste. Errors, outputs, printed results.
  2. Files it reads. A data file in the repository or project folder.
  3. Session context the IDE injects. Posit Assistant reads loaded packages, data frames and console history, so a data frame in memory can reach the model without any paste.
  4. Output of commands it runs. If an agent runs print(voles) or head data.csv, those values enter its context.

Before you decide what to show, know what the surface can already reach. A data file committed to the repository, or a tibble loaded in your session, may already be disclosed.

When you describe a data frame deliberately, three commands reveal increasing amounts:

  • names(voles) lists column names only, in their original order.
  • summary(voles) adds ranges, quartiles and missing-value counts for numeric columns: the shape of the data, not individual records.
  • glimpse(voles) or str(voles) adds the first few actual values of every column.
Important

Before using an assistant on research data, check three things: whether your institution permits sending this kind of data to this provider; whether your ethics approval and data-sharing agreements allow it; and whether a synthetic or anonymised copy would serve instead. Tool settings that restrict reading (see Block 6) reduce accidental exposure, but they do not make an agent safe for confidential data: any command it runs that prints data sends that data to the provider.

For personal or confidential data, let the agent work on a synthetic copy and run the final code on the real data yourself, outside the agent’s workspace. Hooks and project settings are also code that runs on your machine, and a cloned repository can carry its own; trust only repositories whose configuration you have read.

Context you hold in your head

NoteInstructor demonstration (3 minutes)

A data file can supply column names and types, but not your scientific question or your design intent. Your instructor will ask a new browser chat this:

Prompt (browser chat):

I have a dataset with pre and post measurements. How should I analyse it?

and then, in another new chat, this:

Prompt (browser chat):

I have 72 voles, balanced across three treatment arms (Control, Low_dose,
High_dose) and two sexes (M, F). Each animal has body mass measured before
and after treatment, and a single post-treatment metabolic-rate reading.

My question is whether the high-dose treatment changes mass relative to
control, and whether the effect differs between sexes.

The dataset is small (n = 12 per cell). I will report effect sizes alongside
any inferential test. Given this design, what is a defensible primary
analysis, and what are the main threats to its validity?

The first returns a tour of options (paired tests, change scores, ANCOVA, mixed models); the second can return a recommendation, because the design and the question now exist outside your head. Treat even the better answer as a proposal to check against a statistics text or a colleague. Choosing the primary analysis is your decision, not the assistant’s.

Part B: What can the assistant do?

The model is the same at every level below. What changes is its permission modeThe setting that decides how much Claude Code may do without asking: plan (read only), default (asks before edits and commands), acceptEdits (edits without asking) and bypassPermissions (never asks).: what it is allowed to do without asking, and therefore where you sit in the loop. Each level is a rungOne level of the autonomy ladder in Block 4, from suggesting a line (rung 0) to acting with no prompts (rung 5). Each step up removes a moment when you would have seen an action before it happened. on an autonomy ladder.

Rung What happens Claude Code Posit Assistant
0. Suggest Completes the line you are typing — Next Edit Suggestions
1. Ask Answers; changes nothing Ask a question in plan mode Ask mode
2. Plan Proposes steps; changes nothing until you approve plan mode /plan
3. Act, with approval Edits files and runs commands, asking first default mode Normal mode
4. Act, partly unsupervised Some actions without asking acceptEdits mode Auto mode
5. Act, unsupervised No prompts bypassPermissions YOLO mode

In Claude Code, rungs 1 and 2 both use plan mode; they differ only in what you ask for, an answer or a plan. Rung 6, acting remotely on a branch and returning a pull request, is covered in Going further below.

In Claude Code, Shift+Tab cycles default, acceptEdits and plan; the Claude Code quick reference in Block 1 lists the other commands you need. In Posit Assistant, /plan, /auto, /yolo and /restricted switch modes. Use rungs 0 to 3 throughout this course. Do not use rung 5.

Where a routine task is safe. Rung 3 is the everyday working level, and it is safe for routine work such as adding a derived column and a plot script to an exploratory analysis. Three things make it safe: you start from a committed repository, so any change can be reverted; every edit and command is shown to you before it happens; and a test then checks the result, independently of the agent’s report. Exercise 2 below is exactly this.

Warning

Read the rung’s small print. acceptEdits in Claude Code approves more than edits: it also auto-approves common file commands such as mkdir, touch, mv and cp. A cp that overwrites a raw data file needs no approval in that mode. Posit Assistant’s auto mode replaces your judgement with a classifier model’s. Each step up the ladder removes a moment when you would have seen the action before it happened.

Approval fatigue is real. At rung 3, an approval prompt you click through without reading is rung 5 with extra steps. Block 6 covers the rules that hold however tired you are.

Higher rungs make instruction files matter more. At rung 1, a convention the assistant does not know costs you a re-read. From rung 3 upwards, the agent acts on its guess, and the guess lands in your files. That is why Block 5, on instructions and skills, comes next, and why Block 6, on enforced controls, follows it.

Exercise 2: The same task, rising autonomy

Ask, plan, act (15 minutes)

Start: your workshop repository on main, committed and clean (the Git pane shows no changed files), so every change is a diff you can inspect or revert. Never run an agent with uncommitted work you are not prepared to lose. While Claude Code runs in the Terminal tab, do your checking from the R console and the Git pane, as in checking work.

1. Ask. In the project’s Terminal tab, start Claude Code in plan mode.

In the terminal:

claude --permission-mode plan

Prompt (Claude Code):

In scripts/explore_voles.R, how would I add a column mass_change_g equal to
mass_post_g minus mass_pre_g?

Read the answer. The Git pane should still show no changed files.

2. Plan. Still in plan mode, give a goal that spans several files:

Prompt (Claude Code):

In scripts/explore_voles.R, add a derived mass_change_g column (mass_post_g
minus mass_pre_g). Create a new script scripts/explore_mass_change_plot.R
that plots mass_change_g by treatment_arm and saves the figure to outputs/
with ggsave(). Then check that both scripts run in a fresh R session.

Before approving, check that the plan names every file it will touch, does not touch raw data, saves the figure to outputs/, and says how it will check the scripts run. Amend the plan in conversation if any of that is missing.

3. Act, with approval. When Claude Code asks whether to proceed, choose Yes, manually approve edits, so it stays in default mode and asks before each edit or command. Read each approval prompt before answering it. Refuse at least one action you consider out of scope, and note how the agent responds. If nothing is out of scope, refuse its first Rscript call: you will run the check yourself in step 4.

4. Review and check. When it finishes, open each changed file in the Git pane and click Diff. Read the diff as you would a colleague’s contribution. The agent’s statement that the scripts “still run” is a claim; check it yourself. Restart R (Session → Restart R), then in the R console:

In the R console:

testthat::test_file(here::here("tests", "test_explore.R"))

The first test checks that mass_change_g really is post minus pre; the second runs the plot script in a fresh R session and checks that a figure arrived in outputs/, with no stray Rplots.pdf.

You are done when both tests pass and you have read every line of the diff.

If it goes wrong: select the unwanted change in the Git pane and click Revert, then ask again with a clearer prompt. If you run out of time, switch to the block5-done branch from the Git pane’s branch menu at the end of Block 5.

5. Compare. At which rung did you decide the most? At which rung would you have missed an unwanted change if you had not read the diff?

Payoff. What did the agent do, how long did checking it take, and would you automate this again?

6. Start your AI-use log. Create docs/ai-log.md (usethis::edit_file("docs/ai-log.md") in the R console) and write the first line of your AI-use logA record written at the time of each piece of AI-assisted work, in the form: date; tool and model; task; what you kept or changed. It becomes the AI declaration in a README. yourself, rather than asking the agent, in the form set out in Block 1. Keep each entry on one line. For example:

2026-10-19; Claude Code (model as shown above the Claude Code prompt); added mass_change_g and a plot script; kept both after reading the diff; rejected one out-of-scope edit

Commit it with the agent’s changes from the Git pane. You will add a line after each block in which an agent does work; tests/test_ai_log.R checks every line has this form.

TipUsing Posit Assistant

Use Ask mode for step 1, /plan for step 2, and Normal mode for step 3. The review and the test in step 4 are the same: the Git pane and the R console.

NoteAt the command line

The same checks from a terminal (after /exit, or in a second Terminal tab): git status, git diff, and Rscript -e "testthat::test_file('tests/test_explore.R')".

Note

Access and cost. Plans and prices change; check before the session.

  • Claude Code needs an Anthropic account, used through a subscription or an API key; see Anthropic’s documentation for current options.
  • Posit Assistant uses Posit AI Pass or your own provider key, including an Anthropic API key. In RStudio, providers are configured in the assistant’s settings.
  • GitHub Copilot bills in AI credits; check GitHub’s plans page for what your plan includes.
  • Your institution may have approved some of these tools and not others.
NoteCheck · Reproduce · Record
  • You can now: hand an agent a routine multi-file change at rung 3, trusted because you read every diff and a test you did not write checks the result.
  • Check: the Git pane’s diff after every agent action; the agent’s report that something “still runs” is a claim until a test confirms it.
  • Reproduce: work only in a committed, clean repository, so every change is a diff you can inspect or revert.
  • Record: your AI-use log starts here, in docs/ai-log.md.

GitHub Copilot and the remote rung

GitHub Copilot offers the same ladder in its own surfaces. Copilot Chat on github.com can also see files in the repository you open it from.

Rung GitHub Copilot
0. Suggest Inline suggestions
1. Ask Ask in Chat
2. Plan Plan mode in the IDE
3. Act, with approval Agent mode, approving each tool call
4. Act, partly unsupervised Agent mode with auto-approval
5. Act, unsupervised —
6. Act remotely Cloud agent

Rung 6, the Copilot cloud agent, works on the repository on GitHub, in an environment GitHub runs. It takes a task such as an issue, works on its own branch and returns a pull request. Copilot Free includes only limited agent features; check GitHub’s plans page to see whether your plan includes the cloud agent. The cloud agent appears in the Going further section of Block 9, where its pull request meets a review gate.

Glossary

term definition
agent An assistant that can read across a project's files and, depending on its permission mode, edit them and run commands, such as Claude Code. An agent acts; a chat window only advises.
AI-use log A record written at the time of each piece of AI-assisted work, in the form: date; tool and model; task; what you kept or changed. It becomes the AI declaration in a README.
assistant Any AI tool that helps you write or understand code, from inline completion to a chat window. In this course "assistant" is the general word; "agent" is used when the tool acts on your files.
permission mode The setting that decides how much Claude Code may do without asking: plan (read only), default (asks before edits and commands), acceptEdits (edits without asking) and bypassPermissions (never asks).
rung One level of the autonomy ladder in Block 4, from suggesting a line (rung 0) to acting with no prompts (rung 5). Each step up removes a moment when you would have seen an action before it happened.
