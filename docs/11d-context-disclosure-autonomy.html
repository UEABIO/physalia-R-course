Block 3: Context, disclosure and autonomy

Two questions decide how far you can trust an AI assistantAny AI tool that helps you write or understand code, from inline completion to a chat window. In this course “assistant” is the general word; “agent” is used when the tool acts on your files.: what can it see, and what can it do? First you trace what reached the model provider in Block 2. Then you hand an agentAn assistant that can read across a project’s files and, depending on its permission mode, edit them and run commands, such as Claude Code. Goal: see exactly what reached the model provider when the agent investigated in Block 2, so that you can name every route your data take.

TipContext you hold in your head (instructor demonstration)

An assistant’s answer about your data is only as good as its context. It is reliable only when it has real information: something you pasted, a file it read, or output from a command it ran. A data file supplies column names, but not your question or your design.

Where to run it: a new browser chat (claude.ai or similar) with no project, files or memory attached, such as a temporary chat. Not Claude Code: inside the workshop repository it would read AGENTS.md and the data file (route 2), so even the first prompt would get a specific answer.

Your instructor asks a new chat:

Prompt (browser chat):

I have a dataset with pre and post measurements. How should I analyse it?

and then, in another new chat:

Prompt (browser chat):

I have 72 voles, balanced across three treatment arms (Control, Low_dose,
High_dose) and two sexes (M, F). Each animal has body mass measured before
and after treatment, and a single post-treatment metabolic-rate reading.

My question is whether the high-dose treatment changes mass relative to
control, and whether the effect differs between sexes.

The dataset is small (n = 12 per cell). I will report effect sizes alongside
any inferential test. Given this design, what is a defensible primary
analysis, and what are the main threats to its validity?

The first gets a tour of options. The second can get a recommendation, because the design now exists outside your head. Treat it as a proposal to check: the primary analysis is your decision.

Try it yourself after the session: give each prompt to its own new browser chat and compare the answers. For a third run, give the first prompt to Claude Code in your workshop repository. It reads the data without being asked and names the columns, but it still cannot know your question.

ImportantWorking with confidential data: five habits, strongest first

An agent reads what it judges useful. If one route is closed, it often tries another: refused a file, it may offer R code that opens the same file. So the habits are listed from the one that always holds to the ones that only slow it down.

  1. Keep it out of the project. Put a synthetic or anonymised copy in the project, and run the final analysis on the real data yourself, outside the agent’s folder. A file that is not there cannot be read by any route.
  2. Know your account. Commercial accounts (Team, Enterprise, API) are not used for model training. On Pro or Max, set /privacy-settings. Check your institution’s approval, ethics approval and data agreements first.
  3. Read every R command before you approve it. In Manual mode, Claude Code asks before it runs Rscript. Look for file paths in the code, and say No to any that would open a file you want kept out. You will see an agent offer this route in Block 7.
  4. Add a deny rule as well, in /permissions, for example Read(/data/confidential/**). It stops Claude Code’s own file reads and simple commands such as cat and head. It does not stop R code that opens the file, or a search of the whole project such as grep -r, which runs without asking. Treat it as a speed bump, not a wall (Block 5).
  5. Describe, don’t show. names() and dim() describe the data without showing values. summary() prints real minima and maxima. print(), glimpse() and str() print actual rows.
TipHow it works: tool notes
  • Claude Code:
    • There is no .claudeignore file.
    • Read-only commands such as cat, head, grep and ls never ask, even in Manual mode.
    • On macOS, Linux and WSL2, the /sandbox command adds an operating-system block on reading paths you list (sandbox.filesystem.denyRead). That block applies to R code too. The sandbox is not available on native Windows.
  • Posit Assistant:
    • It blocks .Renviron and .env by default.
    • Its session context, the names and types of your objects, can be switched off.
    • Code it runs in your live session can still print values.
    • Its documentation does not say whether a deny rule can name a folder, so test one before you rely on it.

Exercise 2: What can it do?

The model is the same at every rungOne level of the autonomy ladder in Block 3, from suggesting a line (rung 0) to acting with no prompts (rung 5). Each step up removes a moment when you would have seen an action before it happened. of the autonomy ladder. What changes is what it may do without asking you, which in Claude Code is set by its permission modeThe setting that decides how much Claude Code may do without asking: plan (read only), default (asks before edits and commands), acceptEdits (edits without asking) and bypassPermissions (never asks).. Rung 3, act with approval, is where routine work stays checkable:

  • you start from a commit, so you can revert any change;
  • you see every edit and command first;
  • a test checks the result, whatever the agent reports.
NoteThe autonomy ladder

An assistant that advises leaves you to filter every change. An agent that acts removes that filter, unless you put it back. The rungs differ in how much of that filtering is left to you.

Each rung answers two questions: can the assistant change your files or run code, and what do you approve?

Rung Changes files or runs code? What you approve Claude Code Posit Assistant
0. Suggest No: it completes the line you are typing Each suggestion, by accepting it — Next Edit Suggestions
1. Ask No: it answers in the chat Nothing; it may still read files — (no ask mode; Block 2’s answer-only line is a request) Ask mode (/ask)
2. Plan No edits: it proposes steps The plan, before anything changes /plan /plan
3. Act, with approval Yes Every edit and every command, except read-only ones Manual (default): the workshop’s starting mode Normal mode
4. Act, partly unsupervised Yes Only actions outside a set it may take alone acceptEdits (edits and file commands); auto (a classifier approves actions) Auto mode (/auto)
5. Act, unsupervised Yes Nothing bypassPermissions YOLO mode (/yolo)

In Claude Code, reading a project file never needs approval, at any rung. From rung 3 up, what changes is which tool callsA single action an agent takes, such as reading a file, editing a file or running a shell command. Permission rules and hooks act on tool calls. run without your approval. Block 6, after lunch, builds that approval step in code. Your workshop repository starts Claude Code in Manual, although recent versions of Claude Code start in auto. Keep Manual for confidential data. /plan may run commands to explore, and on recent versions some run without asking you. Use only rungs 0 to 3 today. The quick reference lists the commands for the other modes.

Each rung up removes a moment when you would have seen the action. In acceptEdits, for example, file commands such as cp and mv run without asking, so a cp over a raw data file needs no approval. The higher the rung, the more an agent acts on its guesses about your conventions. That is why Block 4 writes them down.

Ask, plan, act (15 minutes)

Goal: have the agent add a column and a plot script at rung 3, then check its work with the diff and the tests, so that you trust the change because you checked it, not because the agent reported it.

Start state: your workshop repository on main, Git pane clean, Claude Code in Manual mode. Check its work from the R console and the Git pane (checking work).

1. Plan (rung 2). In Claude Code, type /clear, then:

Prompt (Claude Code):

/plan In scripts/explore_voles.R, add a mass_change_g column (mass_post_g
minus mass_pre_g) to the voles data frame itself. Create a new script
scripts/explore_mass_change_plot.R that plots mass_change_g by
treatment_arm and saves the figure to outputs/ with ggsave(). Don't run
anything; I'll check the scripts myself.

Before you approve, check that the plan names both files, adds the column to voles itself, leaves data/raw/ alone and saves the figure to outputs/. If anything is missing, choose No, keep planning and say what to change.

2. Act, with approval (rung 3). Choose Yes, manually approve edits. It is not the first option: the first, Yes, and use auto mode (or Yes, auto-accept edits), switches the approvals off. Then read each edit before you approve it. Answer each request with plain Yes or No. Never choose an option that says don’t ask again: it saves a rule that skips the question from then on.

If it asks to run git status before it edits (AGENTS.md asks it to check), answer Yes: that command only reads. It may also ask to run the new scripts and the test suite with Rscript. Approve a run only if you can say what it does and why you want it now; refusing is always safe. For these, choose No: you check the result yourself next.

3. Read the diff. Click Diff in the Git pane for each changed file. Read it as you would a colleague’s work: the diff shows every change, including any you did not ask for.

4. Record. Start your AI-use logA record written at the time of each piece of AI-assisted work, in the form: date; tool and model; task; what you kept or changed. It becomes the AI declaration in a README.. The agent knows the date, its model and what it did, so let it draft the line. Only you know what you kept or changed, so that part stays yours.

Prompt (Claude Code):

Create docs/ai-log.md and add one line for the work you just did, in the
form: date (YYYY-MM-DD); Claude Code (your model name); task; TODO.
Leave the last field as TODO.

Approve the new file after reading it. Then open it (usethis::edit_file("docs/ai-log.md")) and replace TODO with what you kept or changed. Check that the date and the model match what is shown above the Claude Code prompt. The finished line looks like this:

2026-10-19; Claude Code (Claude Opus 5.5); added mass_change_g and a plot script; kept both after reading the diff

Writing it before you test means the tests check it too.

5. Test, then commit. Restart R (Session → Restart R) so that nothing left in your session can make a test pass. Then run:

In the R console:

testthat::test_dir(here::here("tests"))

test_dir() runs every test*.R file in tests/. The template ships them; in this block, these are the ones that matter:

File Checks Before this block
test_explore.R mass_change_g in voles really is post minus pre; the plot script runs in a fresh R session and saves a figure in outputs/ Skipped: no plot script yet
test_ai_log.R Every log line has four parts and a real date Skipped: no log yet
test_controls.R Manual mode, the deny rules and AGENTS.md are still in place (Block 4) Already passing

The other test files are for later blocks, and skip. Commit the log and both scripts together (git ignores outputs/).

Where tests like these come from in your own work. None of these checks needed the answer in advance. Each comes from what you asked for: the definition of the column, a script that runs from a fresh session and saves a file, a log line in the agreed form. So you can write them, or have the agent draft them for you to read, before the agent does the work. They cannot tell you whether the plot is a good one: you check that by looking. Block 8 writes a test from scratch.

NoteThe test you just ran: tests/test_explore.R 
# tests/test_explore.R ----
# Block 3: the derived column and the plot script the agent wrote.
library(testthat)
testthat::local_edition(3)

test_that("mass_change_g is post-treatment mass minus pre-treatment mass", {
  script <- here::here("scripts", "explore_voles.R")
  # the plot script is Block 3's other output: once it exists, the column must too
  skip_if_not(
    file.exists(here::here("scripts", "explore_mass_change_plot.R")),
    "Block 3 not done yet: no plot script"
  )

  # run the script in a fresh R session, so its library() calls cannot change
  # this one, and bring back only the voles data it made
  voles <- callr::r(
    function(script) {
      env <- new.env()
      utils::capture.output(sys.source(script, envir = env))
      if (exists("voles", envir = env)) env$voles else NULL
    },
    args = list(script),
    wd = here::here()
  )
  expect_true(
    !is.null(voles) && "mass_change_g" %in% names(voles),
    label = "explore_voles.R adds mass_change_g to voles"
  )
  expect_equal(voles$mass_change_g, voles$mass_post_g - voles$mass_pre_g)
})

test_that("the plot script runs in a fresh R session and saves to outputs/", {
  script <- here::here("scripts", "explore_mass_change_plot.R")
  skip_if_not(file.exists(script), "Block 3 not done yet: no plot script")

  # an Rplots.pdf made earlier by something else is not this script's fault
  rplots <- here::here("Rplots.pdf")
  rplots_before <- file.exists(rplots)
  expect_no_error(
    callr::rscript(script, wd = here::here(), show = FALSE)
  )
  after <- list.files(here::here("outputs"), recursive = TRUE)

  expect_true(
    length(after) > 0 && any(grepl("\\.(png|pdf)$", after)),
    label = "a .png or .pdf in outputs/"
  )
  expect_false(
    !rplots_before && file.exists(rplots),
    label = "no stray Rplots.pdf (save the figure with ggsave())"
  )
})

You are done when you have read every line of the diff, the tests show no failures, the explore and ai_log lines of the test output show their tests under OK, not S (skipped), and your first log line is committed with both scripts.

If it goes wrong: select the unwanted change in the Git pane and click Revert, then ask again more clearly. If test_explore.R says voles has no mass_change_g, the agent made the column somewhere else: ask it to add the column to voles itself. An S on explore or ai_log means its file is missing or misnamed. Out of time? Carry on: at the end of Block 4, checkpoint-skills holds this block’s files (commit or discard your changes in the Git pane first, so the switch is not blocked).

NoteAt the command line

The same checks from a terminal (after /exit, or in a second Terminal tab): git status, git diff, and Rscript -e "testthat::test_dir('tests')".

NoteThe safe vibe-coding recipe
  1. Commit, so you start from a clean Git pane.
  2. Protect the inputs: /permissions shows the deny rules, or you add one.
  3. Have the checks ready: tests in tests/ before the agent starts.
  4. Ask in one prompt or skill, in Manual mode, reading each approval.
  5. Run the checks: the test suite in a fresh R session.
  6. Read the diff in the Git pane, then commit or revert.

You will use these six steps in Blocks 7 and 8. The template ships the protections and the tests, so most of the work is checking that they are there.

NoteCheck · Reproduce · Record
  • You can now: hand an agent a routine multi-file change at rung 3, trusted because you read every diff and a test you did not write checks the result.
  • Check: the Git pane’s diff after every agent action; the agent’s report that something “still runs” is a claim until a test confirms it.
  • Reproduce: work only in a committed, clean repository, so every change is a diff you can inspect or revert.
  • Record: your AI-use log starts here, in docs/ai-log.md.

TipAccess and cost

Plans and prices change; check before the session.

  • Claude Code needs an Anthropic account, used through a subscription or an API key; see Anthropic’s documentation for current options.
  • Posit Assistant uses Posit AI Pass or your own provider key, including an Anthropic API key. In RStudio, providers are configured in the assistant’s settings.
  • GitHub Copilot bills in AI credits; check GitHub’s plans page for what your plan includes.
  • Your institution may have approved some of these tools and not others.
TipTrusting a repository’s configuration

Project settings and hooks are code that runs on your machine. A cloned repository can carry its own, so trust only repositories whose configuration you have read.

TipGitHub Copilot and the remote rung

Copilot offers the same ladder, plus a rung 6: its cloud agent works on your repository on GitHub, on its own branch, and returns a pull request. The self-study page Self-study: Hand a task to GitHub Copilot’s cloud agent walks through it.

TipStretch: the same error at three levels of context

The code voles |> mutate(mass_change_g = mass_post - mass_pre_g) fails with “object ‘mass_post’ not found”. In three new browser chats, ask about it with more context each time. First give the error message alone. Then give the error plus the code. Last, give the error, the code and the output of glimpse(voles). With the code, a chat may guess mass_post_g by analogy with mass_pre_g, but only the glimpse() output lets it confirm the name. Column names you never supplied, or a famous dataset you never mentioned (penguins, mtcars), are signs it is guessing.

Glossary

term definition
agent An assistant that can read across a project's files and, depending on its permission mode, edit them and run commands, such as Claude Code. An agent acts; a chat window only advises.
AI-use log A record written at the time of each piece of AI-assisted work, in the form: date; tool and model; task; what you kept or changed. It becomes the AI declaration in a README.
assistant Any AI tool that helps you write or understand code, from inline completion to a chat window. In this course "assistant" is the general word; "agent" is used when the tool acts on your files.
permission mode The setting that decides how much Claude Code may do without asking: plan (read only), default (asks before edits and commands), acceptEdits (edits without asking) and bypassPermissions (never asks).
rung One level of the autonomy ladder in Block 3, from suggesting a line (rung 0) to acting with no prompts (rung 5). Each step up removes a moment when you would have seen an action before it happened.
tool call A single action an agent takes, such as reading a file, editing a file or running a shell command. Permission rules and hooks act on tool calls.
