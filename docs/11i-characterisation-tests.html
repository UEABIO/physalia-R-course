Block 9: Functionalise a script step and prove the result is unchanged

You have a computation that already works and you want to turn it into a reusable function. An agent can do that in seconds. The hard part is not the refactor but the verification: a change that “improves” code can quietly alter its output, so how do you confirm the function still does what the script did?

You already know the method from the tidy-evaluation chapter: a characterisation testA test that checks new code reproduces the saved output of the original code exactly. It shows the output is unchanged, not that it is correct.. Freeze the original output once, then require the new code to reproduce it exactly. Here the twist is who does the work. Claude Code writes the function and the test; you hold the reference and check what it did. The test establishes that the output is unchanged, not that it is correct, and Step 2 shows why that distinction matters, using a missing value that has been in the data all along.

⏱ ~38 minutes

The single most important property of this layout: the referenceIn a characterisation test, the saved output of the original, trusted code (stored in tests/fixtures/). You capture it yourself, once, before any refactoring; the agent never creates or regenerates it., tests/fixtures/metabolic_summary.rds, is created by you, once, and by nobody else. Tests read it as a fixtureA file a test reads as fixed input or expected output. In this course, the reference .rds file in tests/fixtures/.. Every protection in this block exists to keep that true.

The original scripts

The data are read by one function that states every column type. The analysis, the reference and the test all call it, so they read the data identically. A column whose type read_csv() guesses differently in one place produces a test failure that has nothing to do with the refactor.

# scripts/functions/load_voles.R ----
load_voles <- function() {
  readr::read_csv(
    here::here("data", "raw", "voles_metabolism.csv"),
    col_types = readr::cols(
      subject_id          = readr::col_character(),
      sex                 = readr::col_character(),
      treatment_arm       = readr::col_character(),
      mass_pre_g          = readr::col_double(),
      mass_post_g         = readr::col_double(),
      metabolic_rate_post = readr::col_double()
    )
  )
}
# scripts/04_load_data.R ----
library(tidyverse)
library(here)
source(here("scripts", "functions", "load_voles.R"))

voles <- load_voles()

Inspect the data with glimpse(voles) at the console, not inside the script, so that sourcing the script from a test prints nothing.

# scripts/05_analysis.R: the original, trusted version ----
library(tidyverse)
library(here)
source(here("scripts", "04_load_data.R"))

metabolic_summary <- voles |>
  group_by(treatment_arm, sex) |>
  summarise(
    mean_rate = mean(metabolic_rate_post),
    sd_rate   = sd(metabolic_rate_post),
    n         = n(),
    .groups   = "drop"
  )

Two things to notice now and leave alone:

  1. The data contain one missing value in metabolic_rate_post, and this code has no na.rm, so one cell of the result is NA. Do not “fix” it yet. Step 2 is about exactly this.
  2. group_by() returns groups sorted by their keys. The .by argument returns them in order of first appearance in the data. If the two orders differ, a refactor that switches to .by changes the row order of the output.

The agent never creates or regenerates the reference. A reference produced by the code under test can only confirm that the code agrees with itself.

Before anything else, run scripts/05_analysis.R yourself and confirm that metabolic_summary looks as you expect, including the one NA cell. Then run the provided capture script once, yourself. It is shown below; run it in the R console with source(here::here("tests", "make_reference.R")).

# tests/make_reference.R ----
# Run ONCE, by you, BEFORE any refactoring.
source(here::here("scripts", "05_analysis.R"))
dir.create(here::here("tests", "fixtures"), showWarnings = FALSE, recursive = TRUE)
saveRDS(
  metabolic_summary,
  here::here("tests", "fixtures", "metabolic_summary.rds")
)

Commit the reference immediately, so that any later change to it is visible.

In the terminal:

git add tests/fixtures/metabolic_summary.rds
git commit -m "Capture reference output before refactoring"

Capture it now, before the refactor. Afterwards, 05_analysis.R computes the summary through the very function under test, so re-capturing would compare the function with itself.

Protect it. Each control covers a different route:

  • Claude Code. The .claude/settings.json that ships with the template already contains the deny rulesA permission rule in the deny list of .claude/settings.json that stops Claude Code’s built-in tools from editing or reading the matching files. It checks shell output redirects such as > file, but not R code or most other commands that change the same files. this block relies on, among others:

    Edit(/tests/fixtures/**)
Edit(/tests/make_reference.R)
Edit(/data/raw/**)

    They protect specific files, not the whole of tests/ or scripts/, so the agent can still write the new function and its test. Start Claude Code and run /permissions to confirm the rules are listed. Then test them:

    1. The edit tool is refused.

    Prompt (Claude Code):

    Overwrite tests/fixtures/metabolic_summary.rds with an empty file.

    The agent’s edit tool is refused by the deny rule.

    2. The shell route reaches you, not the rule.

    Prompt (Claude Code):

    Remove tests/fixtures/metabolic_summary.rds with a shell command.

    Expect an approval prompt, not a refusal: the deny rule does not stop a command such as rm. Refuse it. Only you stopped that route, and only git would have shown that it happened.

  • Every route. Git. git status --short tests/fixtures should print nothing for the rest of this block.

Warning

What a deny rule does not cover. Claude Code’s deny rules apply to its built-in file tools, and to shell output redirects such as > file, but not to R code or most other commands it runs. An agent that ran Rscript tests/make_reference.R would overwrite your reference without touching an edit tool. That is why git, not the deny rule, is the final check, and why the checklist below asks you to read the agent’s command log: the commands it ran, shown in the Claude Code conversation.

Step 1: refactor and test with Claude Code, in two prompts

Split the job into two prompts, not one. A single prompt that writes both the refactor and the test lets one misunderstanding (about row order, say) shape both files at once, producing a passing test that proves nothing. Separating them stops the test inheriting the refactor’s assumptions.

Start Claude Code in default mode from the root of your workshop repository, with the repository committed and clean. In default mode it asks before each edit; read each request before you approve it.

In the terminal:

claude

Prompt 1 (Claude Code): the refactor only.

Move the computation in scripts/05_analysis.R into a documented function
summarise_metabolic_rate() in scripts/functions/summary_functions.R, with a
roxygen2 block and an argument check. Make 05_analysis.R call the new function
instead of the inline pipeline. Do not write any tests, and do not touch
anything under tests/.

Read the diff (git diff, in the terminal). If it uses .by without a trailing arrange(), leave that for now; the test will expose it.

Prompt 2 (Claude Code): the test only.

Add tests/test_summary_functions.R. It must call local_edition(3), source
scripts/functions/load_voles.R and scripts/functions/summary_functions.R,
read tests/fixtures/metabolic_summary.rds, and compare it with
summarise_metabolic_rate(load_voles()) using expect_equal().

Do not create, regenerate or modify anything under tests/fixtures/, and do not
run tests/make_reference.R. I captured that reference myself; a reference you
generate proves nothing.

Before you trust a passing test, check what the agent wrote and did:

  1. The test reads tests/fixtures/metabolic_summary.rds. It does not hard-code expected numbers. If it does, the check is circular whatever the result.
  2. The test calls summarise_metabolic_rate(), the function under test, not a reimplementation of the pipeline inside the test.
  3. git status --short tests/fixtures prints nothing.
  4. The agent’s command log (the commands it ran, shown in the conversation) has no run of tests/make_reference.R.

Now run the test yourself.

In the R console:

testthat::test_file(here::here("tests", "test_summary_functions.R"))

If the function used .by without arrange(), it fails on row order, not values. Have the agent add dplyr::arrange(treatment_arm, sex) and run again. If it passed first time, remove the arrange() yourself to see the failure, then restore it.

Reproduce it without the agent. A test that passes in your IDE session can depend on objects or packages already loaded there. Commit, then check in a fresh R sessionAn R session with nothing loaded from earlier work, such as the one Rscript starts. Code that only works in your current session depends on something you did not record..

In the terminal:

Rscript -e "renv::status()"
Rscript -e "testthat::test_file('tests/test_summary_functions.R')"
git status --short

renv::status() should report a consistent state. If the agent used a package that is not in the lockfileThe renv.lock file that records the R version and the exact package versions a project uses, so renv::restore() can rebuild the same environment., decide whether you want it and record it with renv::snapshot(), as on Day 1. The test must pass in the fresh R session that Rscript starts, and git status should show nothing new: in particular, nothing under tests/fixtures/.

NoteWithout an agent: write the function and the test yourself

A tidy refactor naturally reaches for the modern .by argument. Write this first attempt in scripts/functions/summary_functions.R:

# scripts/functions/summary_functions.R: first attempt ----
summarise_metabolic_rate <- function(data) {
  data |>
    dplyr::summarise(
      mean_rate = mean(metabolic_rate_post),
      sd_rate   = stats::sd(metabolic_rate_post),
      n         = dplyr::n(),
      .by       = c(treatment_arm, sex)
    )
}

Now write the test and run it:

# tests/test_summary_functions.R ----
library(testthat)
local_edition(3)
source(here::here("scripts", "functions", "load_voles.R"))
source(here::here("scripts", "functions", "summary_functions.R"))

test_that("summarise_metabolic_rate() reproduces the original summary", {
  reference <- readRDS(here::here("tests", "fixtures", "metabolic_summary.rds"))
  expect_equal(summarise_metabolic_rate(load_voles()), reference, tolerance = 1e-8)
})

Run it with testthat::test_file(here::here("tests", "test_summary_functions.R")).

It fails, and not on the numbers. .by returns the groups in order of first appearance; the reference, made with group_by(), has them sorted. The values are right but the rows are in a different order, and expect_equal() reports a mismatch. Add dplyr::arrange(treatment_arm, sex) to the end of the pipeline and the test passes. That failure is the lesson in miniature: a change that improved the code altered the output, and the characterisation test caught it.

If your test passed first time, the data happen to be stored in sorted order. Check with load_voles() |> dplyr::distinct(treatment_arm, sex).

While writing the test, resist one temptation: do not type the expected numbers into the test as literals. A test that compares the function with numbers you transcribed proves nothing about whether the refactor preserved the original computation. The test must read the .rds.

The function you should converge on, with documentation and an argument check:

# scripts/functions/summary_functions.R: refactored ----
#' Summarise post-treatment metabolic rate by treatment arm and sex
#'
#' @param data A data frame with columns treatment_arm, sex and
#'   metabolic_rate_post.
#' @return A tibble with one row per treatment_arm and sex, sorted by both,
#'   giving the mean, standard deviation and number of rows.
summarise_metabolic_rate <- function(data) {
  stopifnot(is.data.frame(data))
  required <- c("treatment_arm", "sex", "metabolic_rate_post")
  missing_cols <- setdiff(required, names(data))
  if (length(missing_cols) > 0) {
    stop(
      "`data` is missing required column(s): ",
      paste(missing_cols, collapse = ", "),
      call. = FALSE
    )
  }

  data |>
    dplyr::summarise(
      mean_rate = mean(metabolic_rate_post),
      sd_rate   = stats::sd(metabolic_rate_post),
      n         = dplyr::n(),
      .by       = c(treatment_arm, sex)
    ) |>
    dplyr::arrange(treatment_arm, sex)
}

Finally, make scripts/05_analysis.R call the function, so it genuinely replaces the code it came from:

# scripts/05_analysis.R: after refactoring ----
library(tidyverse)
library(here)
source(here("scripts", "04_load_data.R"))
source(here("scripts", "functions", "summary_functions.R"))

metabolic_summary <- summarise_metabolic_rate(voles)

Run the test again; it should still pass.

NoteInstructor demonstration (3 minutes)

The review gate. Local controls do not exist for an agent that works remotely. Your instructor will show a pull request that changes a file under tests/ being held until the code owner reviews it. How to set up CODEOWNERS and branch protection for your own repository is in the Going further section of Block 6.

Step 2: unchanged is not correct

Your test passes. The function reproduces the reference exactly, including the NA cell. The characterisation test has certified that the refactor preserved the original behaviour, and the original behaviour reports a missing mean for one group of animals.

Is that the right answer? It depends on what you meant. If you want the mean of the animals that were measured, the original code was wrong all along, and the refactor faithfully preserved the error. A characterisation test cannot tell the difference, because it compares against the past, not against the truth.

Decide, change, and test the change independently (10 minutes)

1. Decide. Suppose you conclude that the mean and standard deviation should use the measured animals only. There is a second, quieter problem: n() counts rows, including the animal with no measurement, so n would no longer match the number of values behind the mean. A summary that reports a mean of 11 animals beside n = 12 misstates the sample size.

2. Change the function (by hand or with your agent):

# scripts/functions/summary_functions.R: missing values handled ----
summarise_metabolic_rate <- function(data) {
  stopifnot(is.data.frame(data))
  required <- c("treatment_arm", "sex", "metabolic_rate_post")
  missing_cols <- setdiff(required, names(data))
  if (length(missing_cols) > 0) {
    stop(
      "`data` is missing required column(s): ",
      paste(missing_cols, collapse = ", "),
      call. = FALSE
    )
  }

  data |>
    dplyr::summarise(
      mean_rate = mean(metabolic_rate_post, na.rm = TRUE),
      sd_rate   = stats::sd(metabolic_rate_post, na.rm = TRUE),
      n_used    = sum(!is.na(metabolic_rate_post)),
      n_missing = sum(is.na(metabolic_rate_post)),
      .by       = c(treatment_arm, sex)
    ) |>
    dplyr::arrange(treatment_arm, sex)
}

3. Run the characterisation test. It fails, correctly. The output has changed, and the test exists to tell you so.

4. Add a known-answer test before re-capturing anything. A known-answer testA test that checks code against a result worked out independently, for example by hand. It can show code is correct, where a characterisation test only shows it is unchanged. checks the new behaviour against a result you can compute by hand, independent of any reference file:

# add to tests/test_summary_functions.R ----
test_that("means ignore missing values and n_used counts measured animals", {
  toy_df <- tibble::tibble(
    treatment_arm       = c("Control", "Control", "Control"),
    sex                 = c("F", "F", "F"),
    metabolic_rate_post = c(10, 14, NA)
  )
  result <- summarise_metabolic_rate(toy_df)

  expect_equal(result$mean_rate, 12)
  expect_equal(result$n_used, 2)
  expect_equal(result$n_missing, 1)
})

5. Only now, re-capture the reference, as a recorded decision. Re-run tests/make_reference.R yourself and commit with a message that states why.

In the terminal:

git add tests/fixtures/metabolic_summary.rds scripts/functions/summary_functions.R tests/test_summary_functions.R
git commit -m "Exclude missing metabolic rates from mean and SD; report n_used and n_missing"

Re-capturing compares the function with itself, so it is acceptable only under three conditions: you decided it, an independent known-answer test checks the new behaviour, and the commit records why. Without those, re-capturing a reference to make a failing test pass is the circular verification this whole block warns against.

The general rule: characterisation tests protect behaviour you have already judged correct. Judging it correct is a separate step, and it is yours.

From convention to skill

The protective sentence in Prompt 2 (“do not create, regenerate or modify anything under tests/fixtures/”) is the same for every refactor, so it is a candidate for a skill. The hazard is that once the rule lives in a skill, you no longer see it, and a colleague using your skill may not know that the whole trust argument rests on it. A skill is also only an instruction; the deny rules and git checks hold whether or not the agent reads it. If you build one, keep the “reference stays with the human” clause as a visible line. An example to compare with your own, stored in .agents/skills/characterisation-refactor/SKILL.md as in Block 5:

NoteExample: characterisation-refactor/SKILL.md 
---
name: characterisation-refactor
description: >-
  Refactors working R analysis code into documented functions under a
  characterisation test, so the output is proved unchanged. Use when asked to
  functionalise, refactor or tidy a script whose output must not change.
  Not for fixing bugs or changing results.
disable-model-invocation: true
---

# Refactor under a characterisation test

## The reference stays with the human
The frozen reference in tests/fixtures/ is captured by the user, once, before
any refactoring. A reference produced by the code under test proves nothing.
- Never create, regenerate or modify anything under tests/fixtures/.
- Never run tests/make_reference.R or any script that writes a fixture.
- If no reference exists, stop and ask the user to capture one.

## Procedure
1. Present a plan: the code to move, the function name and file, and the
   test file. Wait for the user to confirm.
2. Refactor only. Write the function in scripts/functions/ with a roxygen2
   block and an argument check, and make the original script call it. Do not
   write or edit tests in this step. Stop and let the user review the diff.
3. Test only. Write a testthat file that reads the reference from
   tests/fixtures/ and compares it with the function's output using
   expect_equal(). Never hard-code expected values, and never reimplement
   the computation inside the test.
4. Run the tests in a fresh R session and report the output verbatim.

## Rules
- If the test fails, report the difference. Never change the test, the
  tolerance or the reference to make it pass.
- Sort rows explicitly (dplyr::arrange()) where grouping could change their
  order.
- Do not change behaviour, including how missing values are handled. A
  passing test shows the output is unchanged, not that it is correct; list
  anything that looks wrong for the user to decide.
NoteCheck · Reproduce · Record
  • Check: the reference you captured, read by a test the agent wrote in a separate prompt; the four-point checklist; and a known-answer test, because unchanged is not correct.
  • Reproduce: renv::status() and the test passing in a fresh Rscript session, with nothing changed under tests/fixtures/.
  • Record: any re-captured reference is a decision with a commit message that says why. Add a line to docs/ai-log.md: the two prompts, whether the test passed first time, and what you changed.

An asynchronous agent: the Copilot cloud agent

The same work can be handed to an agent that runs remotely while you do something else. It works on a branch in GitHub’s infrastructure and returns a pull request. Before you start, check that your Copilot plan includes the cloud agent, that copilot-setup-steps.yml is on your default branch (see the next section), and that the repository is protected.

Protect the reference on GitHub. Local deny rules do not exist for a remote agent. Add a .github/CODEOWNERS file naming yourself for the protected paths, and turn on branch protection for main so that merging requires your review and a passing r-checks run:

/tests/fixtures/      @your-github-username
/tests/make_reference.R @your-github-username
/.github/             @your-github-username

Keep the two-step discipline by writing two issues, and assign the second only after you have reviewed and merged the first.

Issue 1

Title: Move the metabolic-rate summary into a function

Move the summary computation in scripts/05_analysis.R into a documented
function summarise_metabolic_rate() in scripts/functions/summary_functions.R,
with a roxygen2 block and an argument check. Make 05_analysis.R call it.

Acceptance criteria:
- Do not add or change anything under tests/, data/ or .github/.
- The output must be identical to the current output, including row order
  and the existing NA value.

Issue 2 (after Issue 1 is merged)

Title: Add a characterisation test for summarise_metabolic_rate()

Add tests/test_summary_functions.R. It must call local_edition(3), source
scripts/functions/load_voles.R and scripts/functions/summary_functions.R, and
compare summarise_metabolic_rate(load_voles()) with
tests/fixtures/metabolic_summary.rds using expect_equal().

Acceptance criteria:
- Do not create, modify or regenerate anything under tests/fixtures/, and do
  not run tests/make_reference.R.
- Run the tests and report the result in the pull request description.

Assign each issue to Copilot. When a pull request arrives:

  1. Open Files changed. Confirm that only the expected files changed. A change under tests/fixtures/ or .github/ should not merge, and CODEOWNERS will in any case require your review for it.
  2. Read the test against the four-point checklist in Step 1.
  3. Check that the r-checks run on the pull request passed.
  4. Pull the branch and run the test on your own machine. The agent’s report that “tests pass” is its claim; your run is the check.

If something is wrong, comment on the pull request to ask for a revision, or close it. Nothing reaches main until you merge.

The environment the test runs in

A characterisation test is only as stable as the environment it runs in. The column types in load_voles() handle the finest-grained part. The R version and the package set are handled by two GitHub Actions workflows.

r-checks.yml is the independent check. It runs the tests from a clean checkout on every push to main and on every pull request:

name: r-checks
on:
  push:
    branches: [main]
  pull_request:

jobs:
  tests:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: r-lib/actions/setup-r@v2
        with:
          r-version: "4.5.2"   # match the R version in renv.lock
          use-public-rspm: true
      - uses: r-lib/actions/setup-renv@v2
      - name: Run tests
        run: Rscript -e 'testthat::test_dir("tests", stop_on_failure = TRUE)'

It is independent of your machine and of the agent’s environment, but it is not tamper-proof. A pull request can change the workflow file or the reference it checks against. CODEOWNERS and branch protection (above) are what make a passing run meaningful: you review every change to those paths before it merges.

copilot-setup-steps.yml builds the environment the Copilot cloud agent works in. Following GitHub’s documented pattern:

name: "Copilot Setup Steps"

# Runs when this file changes, so you can see whether setup succeeds,
# and can be run by hand from the Actions tab.
on:
  workflow_dispatch:
  push:
    paths:
      - .github/workflows/copilot-setup-steps.yml
  pull_request:
    paths:
      - .github/workflows/copilot-setup-steps.yml

jobs:
  # The job must be called copilot-setup-steps or Copilot will not use it.
  copilot-setup-steps:
    runs-on: ubuntu-latest
    permissions:
      contents: read
    steps:
      - name: Check out repository
        uses: actions/checkout@v4
      - name: Set up R
        uses: r-lib/actions/setup-r@v2
        with:
          r-version: "4.5.2"   # match the R version in renv.lock
          use-public-rspm: true
      - name: Restore packages from renv.lock
        uses: r-lib/actions/setup-renv@v2

Four requirements, each with a different failure mode:

  • The job name must be exactly copilot-setup-steps. If it is not, Copilot ignores the file and works without your packages. That failure is usually loud: the tests error on the first missing function.
  • The file must be on the default branch, or it is not used.
  • The runner must be Ubuntu x64 Linux, the only runner type the cloud agent supports.
  • The lockfile must be restored. If it restores the wrong versions, the failure is quiet: tests run and pass against different package behaviour. The frozen reference then certifies sameness against the wrong baseline.

When the agent’s test run and the independent r-checks run disagree, suspect the environment before you suspect the code.

Glossary

term definition
characterisation test A test that checks new code reproduces the saved output of the original code exactly. It shows the output is unchanged, not that it is correct.
deny rule A permission rule in the deny list of .claude/settings.json that stops Claude Code's built-in tools from editing or reading the matching files. It checks shell output redirects such as > file, but not R code or most other commands that change the same files.
fixture A file a test reads as fixed input or expected output. In this course, the reference .rds file in tests/fixtures/.
fresh R session An R session with nothing loaded from earlier work, such as the one Rscript starts. Code that only works in your current session depends on something you did not record.
known-answer test A test that checks code against a result worked out independently, for example by hand. It can show code is correct, where a characterisation test only shows it is unchanged.
lockfile The renv.lock file that records the R version and the exact package versions a project uses, so renv::restore() can rebuild the same environment.
reference In a characterisation test, the saved output of the original, trusted code (stored in tests/fixtures/). You capture it yourself, once, before any refactoring; the agent never creates or regenerates it.
