Block 8: Functionalise a script step and prove the result is unchanged

You let an agent turn working code into a function and prove that nothing changed. The proof is a characterisation testA test that checks new code reproduces the saved output of the original code exactly. It shows the output is unchanged, not that it is correct., as in the tidy-evaluation chapter: the new code must reproduce the original output exactly. That output is frozen as a referenceIn a characterisation test, the saved output of the original, trusted code (stored in tests/fixtures/). A trusted script captures it once, from the unchanged code, before any refactoring, and you commit it. After that, nothing regenerates it except your own recorded decision.. Then you decide whether the unchanged output is right. Changing it on purpose, and recording why, is an exercise for after the day.

⏱ ~25 minutes · Start on main (or checkpoint-cleaning), Git pane clean, Claude Code running in Manual mode.

One request, one commit, one diff, one test run (20 minutes)

Goal: one request to the skill, ending with a committed reference, a refactored function and a protected test that proves the output unchanged, so that you can restructure working code without fearing that its results moved.

Start state: Step 0 done, Git pane clean. In Claude Code, type /clear to clear any earlier conversation.

1. Ask.

Prompt (Claude Code):

/characterisation-refactor Move the summary in scripts/05_analysis.R into
summarise_metabolic_rate() in scripts/functions/summary_functions.R.

The skill shows its plan as a message and waits. Read it: the plan should capture the reference first. Then reply in Claude Code: Yes, go ahead, or say what to change.

2. Approve the capture, then commit the reference. The skill asks to run tests/make_reference.R. Answer each request with plain Yes or No. Never choose an option that says don’t ask again: it saves a rule that skips the question from then on. Approve a run only if you can say what it does and why you want it now. Refusing is always safe. Here you can say both: it saves the original code’s output before anything changes. When the skill stops, the Git pane should show only tests/fixtures/metabolic_summary.rds as new. Commit it (“Capture reference output before refactoring”), then tell the agent to carry on.

3. Read the diff when it stops again. In the Git pane, click Diff on each changed file. Look for anything beyond moving the code into the function. Then tell the agent to carry on and write the test. If it asks whether to commit the refactor first, reply No, go ahead: you commit everything at the end.

4. Protect the new test. The skill runs only its new test file, reports the output and stops. Now protect that test, so the agent cannot later change it to make a failing run pass. In /permissions, add the deny rule Edit(/tests/test_summary_functions.R). Save it to the project’s shared settings file, .claude/settings.json.

5. Run the whole suite. Restart R (Session → Restart R), so that nothing left in your session can make a test pass. Then run this in the R console:

testthat::test_dir(here::here("tests"))

test_summary_functions.R (the agent’s) the function reproduces your reference exactly
test_reference_guard.R (shipped) the agent’s test reads your reference file and calls the function, and the reference is unchanged since your commit
test_controls.R (shipped) every deny rule is in place, including your new one

6. Record it. Add a line to docs/ai-log.md (date; tool and model; task; what you kept or changed): ask the agent to draft it, as in Block 3, then write the last part yourself. Note whether the test passed first time.

You are done when the suite has no failures and the Git pane shows only the function, 05_analysis.R, the new test, .claude/settings.json and your log as changed. Commit them.

If it goes wrong: see Fixes for Step 1 below the task, or switch to checkpoint-refactor.

Payoff. What did the agent do, how long did checking it take, and would you automate this again?

NoteFixes for Step 1
  • The capture. If the agent declines to run make_reference.R, or a guard hook from Block 5 blocks it, capture the reference yourself. Restart R, run source(here::here("tests", "make_reference.R")), commit the .rds, and tell the agent the reference is committed.
  • Changed files. If anything other than the .rds changed before your commit, Revert it in the Git pane and ask again. The Git pane undoes a change whatever made it; /rewind undoes only changes made with the agent’s edit tools, not by R code it ran (Block 5).
  • Row order. If the test fails on row order, not values, the function used .by without sorting. Ask the agent to add dplyr::arrange(treatment_arm, sex).
  • The new rule. If test_controls.R says the test is unprotected, check the rule’s spelling in /permissions. If settings.json is not in the Git pane, the rule went to the local file: remove it there and add it again, choosing .claude/settings.json. If the agent offers to add the rule itself, refuse: it is yours to add.

Otherwise, Revert the agent’s files and ask again, or switch to checkpoint-refactor.

NoteHow it works: the capture, the settings file and the test rules

The capture. The skill runs make_reference.R only if no reference exists yet and scripts/ has no uncommitted changes. It never runs it again after that. Who runs the capture script matters less than when: before any code changes, from a script you trust, and committed by you. After that, git and test_reference_guard.R notice any change to the reference.

The shared settings file. /permissions can save a rule to .claude/settings.json, which you commit. It can also save it to the local .claude/settings.local.json, which git ignores, so a rule saved there never reaches a commit. The rule takes effect at once.

No known-answer case yet. Your AGENTS.md asks for a known-answer test with every new function. The skill’s test rules take priority here. A characterisation test compares with the original output; known-answer tests come in Step 2, once you decide the behaviour should change. The skill also leaves the whole suite and the settings to you.

# Refactor under a characterisation test

## The reference comes from the original code, and the user commits it
The frozen reference in tests/fixtures/ is written by the user's own capture
script (tests/make_reference.R) from the original, unchanged code, and the
user commits it before anything else changes. A reference made after the code
has changed proves nothing.
- Run tests/make_reference.R at most once, in step 2 below, and only if no
  reference exists yet and git status shows no uncommitted changes under
  scripts/. Never run it at any other time, and never edit the capture script.
- Never edit, regenerate or delete anything under tests/fixtures/.
- If a reference already exists, use it as it is.

## Procedure
1. Present a plan: whether a reference must be captured, the code to move,
   the function name and file, and the test file. Wait for the user to
   confirm.
2. Capture only, if no reference exists. Run git status; if anything under
   scripts/ has uncommitted changes, stop and ask. Otherwise run
   Rscript tests/make_reference.R, report the file it wrote, and stop: ask
   the user to commit it before you change any code. Do not commit it
   yourself.
3. Refactor only. Write the function in scripts/functions/ with a roxygen2
   block and an argument check, and make the original script call it. Do not
   write or edit tests in this step. Stop and let the user review the diff.
4. Test only. Write tests/test_<functions file>.R (for
   scripts/functions/summary_functions.R, that is
   tests/test_summary_functions.R). Start it with library(testthat) and
   testthat::local_edition(3), source the function files with
   here::here(), read the reference from tests/fixtures/ with readRDS(), and
   compare it with the function's output using expect_equal(). Never
   hard-code expected values, and never reimplement the computation inside
   the test. Include an expect_error() test showing that the argument check
   rejects data with a required column missing. This step's rules take
   precedence over any project instruction to add known-answer tests: those
   come later, if the user decides the behaviour should change.
5. Run only the new test file in a fresh R session, for example
   Rscript -e "testthat::test_file('tests/test_summary_functions.R')", and
   report the output verbatim. Then stop: the user protects the new test and
   runs the whole suite. Do not change any settings file.

## Rules
- If the test fails, report the difference. Never change the test, the
  tolerance or the reference to make it pass.
- Sort the output rows explicitly with dplyr::arrange() on the grouping
  columns, so the order never depends on how the data happen to be stored.
- Do not change behaviour, including how missing values are handled. A
  passing test shows the output is unchanged, not that it is correct; list
  anything that looks wrong for the user to decide.

Step 2: unchanged is not correct

Your test passes, including the NA mean and SD for one group. If you wanted the mean of the animals that were measured, the original code was wrong all along. A characterisation test cannot tell: it compares against the past, not against the truth. Deciding whether the behaviour is correct is a separate step, and it is yours.

Discuss: is the original right? (3 minutes)

Goal: decide whether the output you just protected is correct, so that you never mistake “unchanged” for “right”.

1. Look at the reference. In the R console, run readRDS(here::here("tests", "fixtures", "metabolic_summary.rds")). One group’s mean and SD are NA, and its n counts an animal that was never measured.

2. Answer in the chat: is that what the analysis should report? If not, what would you change? And how would you prove the new behaviour is right, when the characterisation test will now fail by design?

Use measured animals only: na.rm = TRUE for the mean and SD, and a count of measured and missing animals instead of n. Prove it with a known-answer testA test that checks code against a result worked out independently, for example by hand. It can show code is correct, where a characterisation test only shows it is unchanged.: a small table whose answer you work out by hand. Then re-capture the reference yourself, and commit it with a message saying why. The re-captured reference is a decision you recorded, not drift.

You are done when you can say why the passing test does not show the output is correct, and what would.

TipDo it yourself (after the day): change the behaviour and re-capture

Decide, change, and test the change independently (12 minutes)

Goal: change the behaviour on purpose, prove it with a known-answer test, and record why the reference changed, so that anyone reading the history sees a decision, not drift.

1. Decide. The mean and standard deviation should use measured animals only, and the count should not include the unmeasured animal (n() counts rows).

2. Ask for the change and a known-answer test.

Prompt (Claude Code):

In summarise_metabolic_rate(), compute the mean and SD with na.rm = TRUE, and
report n_used and n_missing instead of n. Add a known-answer test on a small
tibble in a new file, tests/test_known_answers.R, and show me how you worked
out the expected values. Do not change tests/test_summary_functions.R.

A known-answer testA test that checks code against a result worked out independently, for example by hand. It can show code is correct, where a characterisation test only shows it is unchanged. checks the new behaviour against a result you can work out by hand. Check the arithmetic yourself: the mean of 10, 14 and a missing value is 12, from two measured animals.

# scripts/functions/summary_functions.R: missing values handled ----
summarise_metabolic_rate <- function(data) {
  stopifnot(is.data.frame(data))
  required <- c("treatment_arm", "sex", "metabolic_rate_post")
  missing_cols <- setdiff(required, names(data))
  if (length(missing_cols) > 0) {
    stop(
      "`data` is missing required column(s): ",
      paste(missing_cols, collapse = ", "),
      call. = FALSE
    )
  }

  data |>
    dplyr::summarise(
      mean_rate = mean(metabolic_rate_post, na.rm = TRUE),
      sd_rate   = stats::sd(metabolic_rate_post, na.rm = TRUE),
      n_used    = sum(!is.na(metabolic_rate_post)),
      n_missing = sum(is.na(metabolic_rate_post)),
      .by       = c(treatment_arm, sex)
    ) |>
    dplyr::arrange(treatment_arm, sex)
}
# tests/test_known_answers.R ----
library(testthat)
testthat::local_edition(3)
source(here::here("scripts", "functions", "summary_functions.R"))

test_that("means ignore missing values and n_used counts measured animals", {
  toy_df <- tibble::tibble(
    treatment_arm       = c("Control", "Control", "Control"),
    sex                 = c("F", "F", "F"),
    metabolic_rate_post = c(10, 14, NA)
  )
  result <- summarise_metabolic_rate(toy_df)

  expect_equal(result$mean_rate, 12)
  expect_equal(result$n_used, 2)
  expect_equal(result$n_missing, 1)
})

3. Watch the characterisation test fail, correctly. Run the suite as in Step 1. The output has changed, so the characterisation test fails; the known-answer test passes. If the agent asks to run make_reference.R, refuse: re-capturing is your decision.

4. Re-capture the reference, as a recorded decision. Restart R, then run this in the R console:

source(here::here("tests", "make_reference.R"))

5. Commit, then run the suite. Commit the reference, the function and the new test file. Use a message that says why, for example “Exclude missing metabolic rates from mean and SD; report n_used and n_missing”. Only then run the suite as in Step 1: test_reference_guard.R fails while the new reference is uncommitted.

Re-capturing is safe here for three reasons: you decided it, a known-answer test checks the new behaviour, and the commit records why.

6. Record it. Add a line to docs/ai-log.md (date; tool and model; task; what you kept or changed) and commit it.

You are done when the whole suite passes again, the re-captured reference is committed with its reason, and your AI-log line is committed.

If it goes wrong: if the known-answer test fails, the arithmetic or the function is wrong. Read both before changing either.

TipWhat the skill does, step by step

The skill turns a capture and two prompts into one request. By hand, you do the capture yourself: restart R, run source(here::here("tests", "make_reference.R")), and commit the .rds. The two prompts are below. Splitting the work matters. A single prompt that writes both the refactor and the test lets one misunderstanding (about row order, say) shape both files at once. The result is a passing test that proves nothing.

Prompt 1: the refactor only.

Move the computation in scripts/05_analysis.R into a documented function
summarise_metabolic_rate() in scripts/functions/summary_functions.R, with a
roxygen2 block and an argument check. Make 05_analysis.R call the new function
instead of the inline pipeline. Do not write any tests, and do not touch
anything under tests/.

Prompt 2: the test only.

Add tests/test_summary_functions.R. It must call local_edition(3), source
scripts/functions/load_voles.R and scripts/functions/summary_functions.R,
read tests/fixtures/metabolic_summary.rds, and compare it with
summarise_metabolic_rate(load_voles()) using expect_equal().

Do not create, regenerate or modify anything under tests/fixtures/, and do not
run tests/make_reference.R. I captured that reference myself; a reference you
generate proves nothing.

Before you trust a passing test, check four things:

  1. the test reads the .rds rather than hard-coding numbers;
  2. it calls the function rather than reimplementing the pipeline;
  3. nothing changed under tests/fixtures/;
  4. the agent’s commands (shown in the conversation) include no run of tests/make_reference.R after the capture you committed.

The shipped test_reference_guard.R checks part of this automatically: that the test reads the .rds and calls the function, and that nothing under tests/fixtures/ has changed since your commit. It cannot tell whether numbers were also typed into the test, or the pipeline copied into it. So read the test once yourself. The fourth check is why you read approval requests in Manual mode.

Warning

What a deny rule does not cover. Claude Code’s deny rules apply to its built-in file tools, to simple file commands it recognises (such as cat, sed and tee) and to shell redirects such as > file. They do not apply to R code or most other commands it runs (Block 5). The skill relies on that to take the first snapshot. But an agent that ran Rscript tests/make_reference.R again later would overwrite your reference without touching an edit tool. That is why git and test_reference_guard.R are the final checks.

TipWithout an agent: write the function and the test yourself

Here you write everything yourself; only make_reference.R and the data are shipped. First, capture and commit the reference as above. A tidy refactor naturally uses the modern .by argument. Write this first attempt in a new file, scripts/functions/summary_functions.R:

# scripts/functions/summary_functions.R: first attempt ----
summarise_metabolic_rate <- function(data) {
  data |>
    dplyr::summarise(
      mean_rate = mean(metabolic_rate_post),
      sd_rate   = stats::sd(metabolic_rate_post),
      n         = dplyr::n(),
      .by       = c(treatment_arm, sex)
    )
}

Now write the test and run it:

# tests/test_summary_functions.R ----
library(testthat)
local_edition(3)
source(here::here("scripts", "functions", "load_voles.R"))
source(here::here("scripts", "functions", "summary_functions.R"))

test_that("summarise_metabolic_rate() reproduces the original summary", {
  reference <- readRDS(here::here("tests", "fixtures", "metabolic_summary.rds"))
  expect_equal(summarise_metabolic_rate(load_voles()), reference, tolerance = 1e-8)
})

Run it as in Step 1: restart R, then run testthat::test_dir(here::here("tests")).

It fails, and not on the numbers. .by returns the groups in order of first appearance. The reference, made with group_by(), has them sorted. The values are right but the rows are in a different order, so expect_equal() reports a mismatch. Add dplyr::arrange(treatment_arm, sex) to the end of the pipeline, and the test passes. That failure is the whole lesson on a small scale: a change that improved the code altered the output, and the characterisation test caught it.

If your test passed first time, the data happen to be stored in sorted order. Check with load_voles() |> dplyr::distinct(treatment_arm, sex).

Do not type the expected numbers into the test as literals. A test that compares the function with numbers you copied by hand proves nothing about whether the refactor kept the original computation. The test must read the .rds.

# scripts/functions/summary_functions.R: refactored ----
#' Summarise post-treatment metabolic rate by treatment arm and sex
#'
#' @param data A data frame with columns treatment_arm, sex and
#'   metabolic_rate_post.
#' @return A tibble with one row per treatment_arm and sex, sorted by both,
#'   giving the mean, standard deviation and number of rows.
summarise_metabolic_rate <- function(data) {
  stopifnot(is.data.frame(data))
  required <- c("treatment_arm", "sex", "metabolic_rate_post")
  missing_cols <- setdiff(required, names(data))
  if (length(missing_cols) > 0) {
    stop(
      "`data` is missing required column(s): ",
      paste(missing_cols, collapse = ", "),
      call. = FALSE
    )
  }

TipReuse the skill on a second step

A skill pays off the second time you use it.

Reuse the skill (15 minutes)

Goal: use the skill on a second step, with a reference you captured and committed yourself, so that you know its discipline holds on code it was not written for.

1. Capture a reference yourself first. Pick a second step. It can be the plotting code in scripts/explore_mass_change_plot.R, which you made in Block 3 (it is on checkpoint-skills if you need it), or a step from your own project. The skill runs only the shipped make_reference.R, so for any other step you do the capture yourself:

  • write a small capture script modelled on make_reference.R (for a plot, save ggplot2::layer_data() of it, as the Copilot cloud-agent page does);
  • restart R, then run the script;
  • commit its output in tests/fixtures/;
  • protect the script with /permissions (choosing .claude/settings.json, as in Step 1).

2. Invoke the skill.

Prompt (Claude Code):

/characterisation-refactor Functionalise the step in
scripts/explore_mass_change_plot.R that I captured in tests/fixtures/.
Start with the plan.

3. Compare. Did the agent still stop between the refactor and the test? Run the whole suite, and check the Git pane for anything changed under tests/fixtures/.

You are done when the whole suite has no failures and the Git pane shows nothing changed under tests/fixtures/ since you committed the new reference.

To make a skill of your own from work like this, see Turn a conversation into a skill in Block 4.

TipAn asynchronous agent: the Copilot cloud agent

The same discipline (your reference first, then a refactor, then a test, each reviewed) works with an agent that runs on GitHub while you do something else. The self-study page Self-study: Hand a task to GitHub Copilot’s cloud agent applies it to the Block 3 plot script.

TipThe environment the test runs in

A characterisation test is only as stable as the environment it runs in. The column types in load_voles() handle the finest-grained part. renv.lock pins the R version and package set. To run the tests on GitHub as well (r-checks.yml) and give a cloud agent the same packages (copilot-setup-steps.yml), see Self-study: Hand a task to GitHub Copilot’s cloud agent.

Glossary

term definition
characterisation test A test that checks new code reproduces the saved output of the original code exactly. It shows the output is unchanged, not that it is correct.
deny rule A permission rule in the deny list of .claude/settings.json that stops Claude Code's built-in tools from editing or reading the matching files. It checks shell output redirects such as > file, but not R code or most other commands that change the same files.
known-answer test A test that checks code against a result worked out independently, for example by hand. It can show code is correct, where a characterisation test only shows it is unchanged.
reference In a characterisation test, the saved output of the original, trusted code (stored in tests/fixtures/). A trusted script captures it once, from the unchanged code, before any refactoring, and you commit it. After that, nothing regenerates it except your own recorded decision.
skill A reusable procedure for one kind of task: a folder containing a SKILL.md file (and optionally scripts and templates) that an assistant loads only when it is invoked by name or judged relevant from its description.
