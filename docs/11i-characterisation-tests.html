Block 9: Functionalise a script step and prove the result is unchanged

By the end of this block you can let an agent turn working code into a function and prove that nothing changed. The proof is a characterisation testA test that checks new code reproduces the saved output of the original code exactly. It shows the output is unchanged, not that it is correct., as in the tidy-evaluation chapter: you freeze the original output, and the new code must reproduce it exactly. One request to a shipped skill does the work in order: take the snapshot, refactor, write the test. It stops twice for you: once to commit the snapshot before any code changes, and once to read the diff.

This block follows the safe vibe-coding recipe: the protections and checks are in place, so your part is one request, one commit, one read of the diff and one test run.

Step 1: snapshot, refactor and test with the skill

The shipped skillA folder containing a SKILL.md file (and optionally scripts and templates) that an assistant loads only when it is invoked by name or judged relevant from its description. characterisation-refactor (/skills lists it) carries every rule you would otherwise type, and works in order:

  1. Snapshot. It runs your make_reference.R on the original code, then stops for you to commit the result. It runs the script only if no reference exists yet and scripts/ has no uncommitted changes.
  2. Refactor only, then stop for your diff review.
  3. Test: a test that reads your committed reference.

Who runs the capture script matters less than when: before any code changes, from a script you trust, and committed by you. After that, git and test_reference_guard.R notice any change to the reference.

# Refactor under a characterisation test

## The reference comes from the original code, and the user commits it
The frozen reference in tests/fixtures/ is written by the user's own capture
script (tests/make_reference.R) from the original, unchanged code, and the
user commits it before anything else changes. A reference made after the code
has changed proves nothing.
- Run tests/make_reference.R at most once, in step 2 below, and only if no
  reference exists yet and git status shows no uncommitted changes under
  scripts/. Never run it at any other time, and never edit the capture script.
- Never edit, regenerate or delete anything under tests/fixtures/.
- If a reference already exists, use it as it is.

## Procedure
1. Present a plan: whether a reference must be captured, the code to move,
   the function name and file, and the test file. Wait for the user to
   confirm.
2. Capture only, if no reference exists. Run git status; if anything under
   scripts/ has uncommitted changes, stop and ask. Otherwise run
   Rscript tests/make_reference.R, report the file it wrote, and stop: ask
   the user to commit it before you change any code. Do not commit it
   yourself.
3. Refactor only. Write the function in scripts/functions/ with a roxygen2
   block and an argument check, and make the original script call it. Do not
   write or edit tests in this step. Stop and let the user review the diff.
4. Test only. Write tests/test_<functions file>.R (for
   scripts/functions/summary_functions.R, that is
   tests/test_summary_functions.R). Start it with library(testthat) and
   testthat::local_edition(3), source the function files with
   here::here(), read the reference from tests/fixtures/ with readRDS(), and
   compare it with the function's output using expect_equal(). Never
   hard-code expected values, and never reimplement the computation inside
   the test. Include an expect_error() test showing that the argument check
   rejects data with a required column missing.
5. Run every test in a fresh R session,
   Rscript -e "testthat::test_dir('tests')", and report the output verbatim,
   including skips.

## Rules
- If the test fails, report the difference. Never change the test, the
  tolerance or the reference to make it pass.
- Sort the output rows explicitly with dplyr::arrange() on the grouping
  columns, so the order never depends on how the data happen to be stored.
- Do not change behaviour, including how missing values are handled. A
  passing test shows the output is unchanged, not that it is correct; list
  anything that looks wrong for the user to decide.

Start state: Step 0 done, the Git pane clean, and Claude Code running in Manual mode in the Terminal tab (/clear if an earlier conversation is still open).

1. Ask.

Prompt (Claude Code):

Read its plan: it should say it will capture the reference first. Choose “Yes, manually approve edits”, and read each request before approving it.

2. Commit the reference when it stops. The only new file in the Git pane should be tests/fixtures/metabolic_summary.rds. Commit it with the message “Capture reference output before refactoring”, then tell the agent to carry on.

3. Read the diff when it stops again. Select each changed file in the Git pane and choose Diff, then tell it to carry on and write the test.

4. Protect the new test. Type /permissions and add the deny rule Edit(/tests/test_summary_functions.R). It takes effect at once, and from now on new tests go in new files.

5. Run the checks. Restart R (Session → Restart R), then in the R console:

testthat::test_dir(here::here("tests"))
Test Passing proves
test_summary_functions.R (written by the agent in this step) the function reproduces your reference exactly
test_reference_guard.R (shipped) the agent’s test reads your reference rather than typing numbers, and the reference is unchanged since you committed it
test_controls.R (shipped, from Block 5) every deny rule is in place, including the new one

The other blocks’ tests run too; they pass, or skip if you did not do that block.

You are done when the suite has no failures and the Git pane shows only the function, 05_analysis.R and the new test as changed. Commit them.

If it goes wrong:

  • The capture. If the agent declines to run make_reference.R, or a guard hook from Block 6 blocks it, capture it yourself: restart R, run source(here::here("tests", "make_reference.R")), commit the .rds, and tell the agent the reference is committed.
  • Changed files. If anything other than the .rds changed before your commit, Revert it and ask again.
  • Row order. A failure on row order, not values, means the function used .by without sorting: ask the agent to add dplyr::arrange(treatment_arm, sex).
  • The new rule. If test_controls.R says the test is unprotected, check the rule’s spelling in /permissions.

Otherwise, Revert the agent’s files and ask again, or switch to block9-done.

Payoff. What did the agent do, how long did checking it take, and would you automate this again?

Step 2: unchanged is not correct

Your test passes, including the NA cell: the refactor faithfully kept a missing mean for one group. If you wanted the mean of the animals that were measured, the original code was wrong all along. A characterisation test cannot tell, because it compares against the past, not against the truth.

Decide, change, and test the change independently (12 minutes)

1. Decide. The mean and standard deviation should use measured animals only, and the count should not include the unmeasured animal (n() counts rows).

2. Ask for the change and a known-answer test.

Prompt (Claude Code):

Handle missing metabolic_rate_post values in summarise_metabolic_rate(): mean
and SD with na.rm = TRUE, and add n_used and n_missing instead of n. Put a
known-answer test on a small tibble in a new file,
tests/test_known_answers.R, and show me the expected values and how you
worked them out. Do not change tests/test_summary_functions.R.

A known-answer testA test that checks code against a result worked out independently, for example by hand. It can show code is correct, where a characterisation test only shows it is unchanged. checks the new behaviour against a result you can work out by hand. Check the arithmetic yourself: the mean of 10, 14 and a missing value is 12, from two measured animals and one missing.

# scripts/functions/summary_functions.R: missing values handled ----
summarise_metabolic_rate <- function(data) {
  stopifnot(is.data.frame(data))
  required <- c("treatment_arm", "sex", "metabolic_rate_post")
  missing_cols <- setdiff(required, names(data))
  if (length(missing_cols) > 0) {
    stop(
      "`data` is missing required column(s): ",
      paste(missing_cols, collapse = ", "),
      call. = FALSE
    )
  }

  data |>
    dplyr::summarise(
      mean_rate = mean(metabolic_rate_post, na.rm = TRUE),
      sd_rate   = stats::sd(metabolic_rate_post, na.rm = TRUE),
      n_used    = sum(!is.na(metabolic_rate_post)),
      n_missing = sum(is.na(metabolic_rate_post)),
      .by       = c(treatment_arm, sex)
    ) |>
    dplyr::arrange(treatment_arm, sex)
}
# tests/test_known_answers.R ----
library(testthat)
testthat::local_edition(3)
source(here::here("scripts", "functions", "summary_functions.R"))

test_that("means ignore missing values and n_used counts measured animals", {
  toy_df <- tibble::tibble(
    treatment_arm       = c("Control", "Control", "Control"),
    sex                 = c("F", "F", "F"),
    metabolic_rate_post = c(10, 14, NA)
  )
  result <- summarise_metabolic_rate(toy_df)

  expect_equal(result$mean_rate, 12)
  expect_equal(result$n_used, 2)
  expect_equal(result$n_missing, 1)
})

3. Watch the characterisation test fail, correctly. Run the suite as in Step 1: the output has changed, and the test tells you so. The known-answer test passes.

4. Re-capture the reference, as a recorded decision. This one is yours, not the skill’s: the skill only captures a reference that does not exist yet. Restart R, then in the R console:

source(here::here("tests", "make_reference.R"))

5. Commit, then run the suite. Commit the reference, the function and the new test file with a message that says why, for example “Exclude missing metabolic rates from mean and SD; report n_used and n_missing”. Only then run the suite as in Step 1. The order matters: until the new reference is committed, test_reference_guard.R fails, because git reports uncommitted changes under tests/fixtures/.

Re-capturing is safe here for three reasons: you decided it, a known-answer test checks the new behaviour, and the commit records why.

You are done when the whole suite passes again and the re-captured reference is committed with its reason.

If it goes wrong: if the known-answer test fails, the arithmetic or the function is wrong; read both before changing either. If time is short, switch to the block9-done branch, which has Step 2 done.

The general rule: characterisation tests protect behaviour you have already judged correct. Judging it correct is a separate step, and it is yours.

TipWhat the skill does, step by step

The skill turns a capture and two prompts into one request. Written out by hand, the capture is yours: restart R, run source(here::here("tests", "make_reference.R")), and commit the .rds. The two prompts are below. Splitting the work matters: a single prompt that writes both the refactor and the test lets one misunderstanding (about row order, say) shape both files at once, producing a passing test that proves nothing.

Prompt 1: the refactor only.

Move the computation in scripts/05_analysis.R into a documented function
summarise_metabolic_rate() in scripts/functions/summary_functions.R, with a
roxygen2 block and an argument check. Make 05_analysis.R call the new function
instead of the inline pipeline. Do not write any tests, and do not touch
anything under tests/.

Prompt 2: the test only.

Add tests/test_summary_functions.R. It must call local_edition(3), source
scripts/functions/load_voles.R and scripts/functions/summary_functions.R,
read tests/fixtures/metabolic_summary.rds, and compare it with
summarise_metabolic_rate(load_voles()) using expect_equal().

Do not create, regenerate or modify anything under tests/fixtures/, and do not
run tests/make_reference.R. I captured that reference myself; a reference you
generate proves nothing.

Before trusting a passing test you would check four things: the test reads the .rds rather than hard-coding numbers; it calls the function rather than reimplementing the pipeline; nothing changed under tests/fixtures/; and the agent’s commands (shown in the conversation) include no run of tests/make_reference.R after the capture you committed. The shipped test_reference_guard.R now checks the first three automatically; the fourth is why you read approval requests in Manual mode.

Warning

What a deny rule does not cover. Claude Code’s deny rules apply to its built-in file tools, and to shell output redirects such as > file, but not to R code or most other commands it runs. The skill relies on that to take the first snapshot; an agent that ran Rscript tests/make_reference.R again later would overwrite your reference without touching an edit tool. That is why git, and test_reference_guard.R, are the final checks.

To use the skill in your own projects, download it and unzip it into your project’s .agents/skills/ (and copy it into .claude/skills/ for Claude Code):

TipWithout an agent: write the function and the test yourself

Everything here is written by you; only make_reference.R and the data are shipped. First capture and commit the reference as above. A tidy refactor naturally reaches for the modern .by argument. Write this first attempt in a new file, scripts/functions/summary_functions.R:

# scripts/functions/summary_functions.R: first attempt ----
summarise_metabolic_rate <- function(data) {
  data |>
    dplyr::summarise(
      mean_rate = mean(metabolic_rate_post),
      sd_rate   = stats::sd(metabolic_rate_post),
      n         = dplyr::n(),
      .by       = c(treatment_arm, sex)
    )
}

Now write the test and run it:

# tests/test_summary_functions.R ----
library(testthat)
local_edition(3)
source(here::here("scripts", "functions", "load_voles.R"))
source(here::here("scripts", "functions", "summary_functions.R"))

test_that("summarise_metabolic_rate() reproduces the original summary", {
  reference <- readRDS(here::here("tests", "fixtures", "metabolic_summary.rds"))
  expect_equal(summarise_metabolic_rate(load_voles()), reference, tolerance = 1e-8)
})

Run it with testthat::test_file(here::here("tests", "test_summary_functions.R")).

It fails, and not on the numbers. .by returns the groups in order of first appearance; the reference, made with group_by(), has them sorted. The values are right but the rows are in a different order, and expect_equal() reports a mismatch. Add dplyr::arrange(treatment_arm, sex) to the end of the pipeline and the test passes. That failure is the lesson in miniature: a change that improved the code altered the output, and the characterisation test caught it.

If your test passed first time, the data happen to be stored in sorted order. Check with load_voles() |> dplyr::distinct(treatment_arm, sex).

Do not type the expected numbers into the test as literals: a test that compares the function with numbers you transcribed proves nothing about whether the refactor preserved the original computation. The test must read the .rds.

# scripts/functions/summary_functions.R: refactored ----
#' Summarise post-treatment metabolic rate by treatment arm and sex
#'
#' @param data A data frame with columns treatment_arm, sex and
#'   metabolic_rate_post.
#' @return A tibble with one row per treatment_arm and sex, sorted by both,
#'   giving the mean, standard deviation and number of rows.
summarise_metabolic_rate <- function(data) {
  stopifnot(is.data.frame(data))
  required <- c("treatment_arm", "sex", "metabolic_rate_post")
  missing_cols <- setdiff(required, names(data))
  if (length(missing_cols) > 0) {
    stop(
      "`data` is missing required column(s): ",
      paste(missing_cols, collapse = ", "),
      call. = FALSE
    )
  }

  data |>
    dplyr::summarise(
      mean_rate = mean(metabolic_rate_post),
      sd_rate   = stats::sd(metabolic_rate_post),
      n         = dplyr::n(),
      .by       = c(treatment_arm, sex)
    ) |>
    dplyr::arrange(treatment_arm, sex)
}
# scripts/05_analysis.R: after refactoring ----
library(tidyverse)
library(here)

source(here("scripts", "functions", "summary_functions.R"))

TipThe environment the test runs in

A characterisation test is only as stable as the environment it runs in. The column types in load_voles() handle the finest-grained part. The R version and the package set are handled by two GitHub Actions workflows. Neither ships with the template: to use them, create each file in .github/workflows/.

r-checks.yml is the independent check. It runs the tests from a clean checkout on every push to main and on every pull request:

name: r-checks
on:
  push:
    branches: [main]
  pull_request:

jobs:
  tests:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: r-lib/actions/setup-r@v2
        with:
          r-version: "4.5.2"   # match the R version in renv.lock
          use-public-rspm: true
      - uses: r-lib/actions/setup-renv@v2
      - name: Run tests
        run: Rscript -e 'testthat::test_dir("tests", stop_on_failure = TRUE)'

It is independent of your machine and of the agent’s environment, but it is not tamper-proof. A pull request can change the workflow file or the reference it checks against. CODEOWNERS and branch protection (above) are what make a passing run meaningful: you review every change to those paths before it merges.

copilot-setup-steps.yml builds the environment the Copilot cloud agent works in. Following GitHub’s documented pattern:

name: "Copilot Setup Steps"

# Runs when this file changes, so you can see whether setup succeeds,
# and can be run by hand from the Actions tab.
on:
  workflow_dispatch:
  push:
    paths:
      - .github/workflows/copilot-setup-steps.yml
  pull_request:
    paths:
      - .github/workflows/copilot-setup-steps.yml

jobs:
  # The job must be called copilot-setup-steps or Copilot will not use it.
  copilot-setup-steps:
    runs-on: ubuntu-latest
    permissions:
      contents: read
    steps:
      - name: Check out repository
        uses: actions/checkout@v4
      - name: Set up R
        uses: r-lib/actions/setup-r@v2
        with:
          r-version: "4.5.2"   # match the R version in renv.lock
          use-public-rspm: true
      - name: Restore packages from renv.lock
        uses: r-lib/actions/setup-renv@v2

Four requirements, each with a different failure mode:

  • The job name must be exactly copilot-setup-steps. If it is not, Copilot ignores the file and works without your packages. That failure is usually loud: the tests error on the first missing function.
  • The file must be on the default branch, or it is not used.
  • The runner must be Ubuntu x64 Linux or Windows 64-bit. The cloud agent does not support macOS runners; Ubuntu is the usual choice for R.
  • The lockfile must be restored. If it restores the wrong versions, the failure is quiet: tests run and pass against different package behaviour. The frozen reference then certifies sameness against the wrong baseline.

When the agent’s test run and the independent r-checks run disagree, suspect the environment before you suspect the code.

Glossary

term definition
characterisation test A test that checks new code reproduces the saved output of the original code exactly. It shows the output is unchanged, not that it is correct.
deny rule A permission rule in the deny list of .claude/settings.json that stops Claude Code's built-in tools from editing or reading the matching files. It checks shell output redirects such as > file, but not R code or most other commands that change the same files.
known-answer test A test that checks code against a result worked out independently, for example by hand. It can show code is correct, where a characterisation test only shows it is unchanged.
skill A folder containing a SKILL.md file (and optionally scripts and templates) that an assistant loads only when it is invoked by name or judged relevant from its description.
