Block 7: Data cleaning and validation with AI

Cleaning mistakes are silent: a missing-value code treated as a measurement, the same animal kept twice, a row quietly dropped. Here an agent writes and runs the whole cleaning script from one command, against a codebookA table describing each variable: its type, valid range, missing-value codes, unit and label mappings. It is the data dictionary from Day 2 with machine-readable rules, and you own it, not the AI. you own, and one test run tells you whether to trust it.

⏱ ~55 minutes · Start on main (or checkpoint-skills), Git pane clean, Claude Code running in Manual mode.

NoteThis block’s files, and how it fits

Nothing needs downloading. Blocks 5 and 6 add no checkpoint, and nothing here needs Block 6’s summaries.R. The cleaned file is used only in this block; Block 8 returns to voles_metabolism.csv. Step 0: Check the safeguards are in place

Recipe check (3 minutes)

Goal: confirm the protections and the checks are in place before any cleaning starts, so that a mistake by the agent is blocked or caught rather than found later.

Start state: as at the top of the page; switch to checkpoint-skills, if you need it, in the Git pane’s branch menu.

1. The protections. In Claude Code, type /permissions and find four deny rulesA permission rule in the deny list of .claude/settings.json that stops Claude Code’s built-in tools from editing or reading the matching files. It checks shell output redirects such as > file, but not R code or most other commands that change the same files.: Edit(/data/raw/**), Read(/docs/data_note.md), Edit(/docs/codebook.csv) and Edit(/tests/test_cleaning.R). They keep the agent’s edit tools off the raw data, your codebook and the tests, and stop it reading the provider’s note (Step 2 shows why).

2. The checks. In the Files pane, tests/ holds test_cleaning.R, written from the agreed codebook before any cleaning code existed, and fixtures/raw_checksum.txt, a checksumA short fingerprint computed from a file’s contents, for example with tools::md5sum(). Any change to the file changes the checksum, so it detects changes made by any route. of the raw file. The raw-data checksum test runs from the start; the others skip until clean data exist.

You are done when you have seen the four rules and the two files.

If it goes wrong: if /permissions lists no rules, check you started claude from the workshop repository’s Terminal tab; if the files are missing, switch to checkpoint-skills.

TipBackground: why not simply ask a chatbot to clean the data?

In a 2025 study, language models given polluted tables missed codes such as -1 (a sentinel valueA number with a special meaning, such as 9999 for “not recorded” or -1 for “run failed”. It must be documented in a codebook and recoded before analysis.) and rarely spotted near duplicates (Spreafico et al., 2025). Those error classes are planted here.

Step 1: Profile the raw data

Profile (5 minutes)

Goal: count what is in the raw file with R rather than the model, so that the codebook draft in Step 2 starts from exact counts, not a model’s impression.

In the R console:

source(here::here("scripts", "00_profile.R"))
View(readr::read_csv(here::here("docs", "profile.csv"), show_col_types = FALSE))

The shipped script reads every column as text, so 9999 and -1 appear exactly as entered, and writes three tables to docs/: profile.csv (per column: missing values, distinct values, numeric minimum and maximum), profile_labels.csv (how often each spelling of sex and treatment_arm occurs) and profile_ids.csv (repeated IDs, and IDs of unusual length). Look for numbers far outside the rest, labels that differ only in spelling or case, and every ID in profile_ids.csv.

You are done when the three profile files exist in docs/ and you have noted anything that looks odd.

If it goes wrong: restart R (Session → Restart R) and run the lines again.

NoteThe shipped scripts/00_profile.R 
# scripts/00_profile.R ----
# Purpose: describe the raw file as entered, before any decision is made.
# Every column is read as character so codes such as 9999 or -1 appear
# exactly as entered.
library(tidyverse)
library(here)

raw_df <- read_csv(
  here("data", "raw", "voles_raw.csv"),
  col_types = cols(.default = col_character())
)

# one row per column: missingness, distinct values, numeric range ----
profile_df <- raw_df |>
  pivot_longer(everything(), names_to = "column", values_to = "value") |>
  # suppressWarnings: text values become NA here by design
  mutate(value_num = suppressWarnings(as.numeric(value))) |>
  summarise(
    n_rows = n(),
    n_missing = sum(is.na(value)),
    n_distinct = n_distinct(value, na.rm = TRUE),
    n_numeric = sum(!is.na(value_num)),
    min_numeric = if (all(is.na(value_num))) NA_real_ else min(value_num, na.rm = TRUE),
    max_numeric = if (all(is.na(value_num))) NA_real_ else max(value_num, na.rm = TRUE),
    .by = column
  )

# every distinct label in the categorical columns ----
labels_df <- raw_df |>
  select(sex, treatment_arm) |>
  pivot_longer(everything(), names_to = "column", values_to = "value") |>
  count(column, value, sort = TRUE)

# identifiers that appear more than once, or whose length differs from the
# usual one (a possible formatting slip) ----
usual_length <- as.integer(names(which.max(table(nchar(raw_df$subject_id)))))
ids_df <- raw_df |>
  count(subject_id) |>
  mutate(unusual_length = nchar(subject_id) != usual_length) |>
  filter(n > 1 | unusual_length)

# print in full, and save each table so it can be opened, pasted or diffed ----
print(profile_df, n = Inf, width = Inf)
print(labels_df, n = Inf, width = Inf)
print(ids_df, width = Inf)
write_csv(profile_df, here("docs", "profile.csv"))
write_csv(labels_df, here("docs", "profile_labels.csv"))
write_csv(ids_df, here("docs", "profile_ids.csv"))

Step 2: Draft the codebook with the agent, then audit it

The codebook is Day 2’s data dictionary (README chapter) with rules code can read. Its facts come from docs/data_note.md, which stands in for the methods sheet or email you would get from whoever collected the data. The agent is denied reading it, so it drafts from the profile alone, like an analyst who never asked for the note: that gap is the point.

Draft and audit the codebook (12 minutes)

Goal: a codebook you own, drafted by the agent, corrected by you against the data note and committed, so that every cleaning rule traces to a fact you can defend.

1. Ask for a draft. The source column shows which entries are the agent’s own assumptions, so you know where to look first.

Prompt (Claude Code):

Draft a codebook for the raw voles data from docs/profile.csv,
docs/profile_labels.csv and docs/profile_ids.csv only, with the columns
column, type, rule, min, max, missing_codes, unit, source. In the source
column, say for every entry whether it comes from the profile or is your
assumption. Write it to scratch/codebook_draft.csv and no other file.

Claude Code asks before it writes the file. Answer each request with plain Yes or No. Never choose an option that says don’t ask again: it saves a rule that skips the question from then on. Approve this write. If the agent asks whether to commit the profile files first, reply No, go ahead: you commit them in step 4.

Approve a run only if you can say what it does and why you want it now; refusing is always safe. The read rule stops Claude Code’s own reads of the note, not R code that opens it, so refuse any code that would.

2. Make it yours. In the R console, copy the draft into place (git ignores scratch/) and open it:

fs::file_copy(here::here("scratch", "codebook_draft.csv"), here::here("docs", "codebook.csv"))
usethis::edit_file("docs/codebook.csv")

The agent is denied editing docs/codebook.csv: the codebook is yours. (Avoid Excel, which can silently change quoted fields.)

3. Audit the draft. Before you open docs/data_note.md, answer:

  • Did the draft list 9999 as a missing-value code, or treat it as a large measurement?
  • Did it notice that -1 is a code?
  • Where did its min and max come from? A range read off the data includes its errors, so valid ranges must come from the biology or the protocol.

4. Correct it against the note, and commit. Open docs/data_note.md (also shown below the task) and edit docs/codebook.csv until every line traces to the note or to a decision you can defend, and its source says which. Where the note gives no unit (metabolic rate), write <unit>, not a guess: a guessed unit is an invented fact. Save, then commit docs/codebook.csv and the three profile files together, so the cleaning starts from a recorded version of your rules and Step 3 starts with a clean Git pane.

You are done when the codebook and the three profile files are committed, and every rule traces to the note or to your own decision.

If it goes wrong: short of time? Paste the codebook below into docs/codebook.csv and commit it with the profile files; it is what most groups converge on.

NoteThe shipped docs/data_note.md (open after step 3 of the task) 
# Data note: vole metabolism experiment

From the colony manager who collected the data. One row per animal.

- **subject_id**: `V` followed by three digits (for example `V007`). Each
  animal appears once.
- **sex**: `M` or `F`.
- **treatment_arm**: `Control`, `Low_dose` or `High_dose`.
- **mass_pre_g**, **mass_post_g**: body mass in grams, before and after
  treatment. Adults in this colony weigh between 15 and 60 g. We entered
  `9999` when an animal could not be weighed.
- **metabolic_rate_post**: metabolic rate after treatment, from the
  respirometer. Valid readings lie between 5 and 30. We entered `-1` when the
  respirometry run failed.
NoteWhy a CSV, not a table in the README?

Code reads it. 01_clean.R reads docs/codebook.csv every time it runs, so the rules are never copied into the script by hand, and the over-cleaning test reads its min, max and missing_codes columns. A Markdown table is for people; a CSV is for people and code.

column,type,rule,min,max,missing_codes,unit,source
subject_id,character,"pattern ^V[0-9]{3}$; unique; pad digits to three",,,,,data note; padding is a decision
sex,character,"allowed M, F; recode male to M, female to F",,,,,data note; recodes are a decision
treatment_arm,character,"allowed Control, Low_dose, High_dose; match case-insensitively",,,,,data note; case-insensitive matching is a decision
mass_pre_g,double,,15,60,9999,g,data note
mass_post_g,double,,15,60,9999,g,data note
metabolic_rate_post,double,,5,30,-1,<unit>,data note; no unit given

The note states the ID pattern, that each animal appears once, the allowed labels, the ranges and the missing-value codes. Padding short IDs and mapping other spellings onto the allowed labels are your decisions, and the source column says so. The note gives no unit for metabolic rate, so <unit> stays until you find it out.

Step 3: Clean with one command

The shipped skill clean-with-codebook holds the procedure; your codebook holds the facts. It writes scripts/01_clean.R, the only new script in this block.

Plan, review, then execute (15 minutes)

Goal: the skill writes and runs scripts/01_clean.R from your codebook, after you have approved its plan, so that every change to the data is made by a script you can rerun and is logged against a codebook rule.

Start state: the codebook and profile files committed, Git pane clean.

1. Invoke the skill.

Prompt (Claude Code):

/clean-with-codebook Clean data/raw/voles_raw.csv using docs/codebook.csv.

2. Review its plan. The skill shows its plan as a message and waits. Read it, then reply in Claude Code: Yes, go ahead, or say what to change. A wrong rule is cheapest to catch here, before any file is written. Check that:

  • every rule cites a codebook row;
  • out-of-range values are set to NA and queried, not “corrected”;
  • no file outside scripts/01_clean.R and data/derived/ will be written;
  • duplicates are handled by a stated rule, with each exclusion logged.

3. Read each request. Claude Code still asks before each write and each run: approve what the plan described, and nothing else. New files should appear in the Git pane only in scripts/ and data/derived/. The skill runs the script twice, then the tests, and reports the output.

You are done when data/derived/ contains voles_clean.csv, cleaning_log.csv and exclusion_log.csv, and the agent has reported the test output.

If it goes wrong: if it stalls, loops or writes elsewhere, press Ctrl+C, Revert in the Git pane, and switch to checkpoint-cleaning (a working 01_clean.R and its outputs).

NoteWhat the skill tells the agent (clean-with-codebook/SKILL.md)

The skill ships in .agents/skills/clean-with-codebook/, copied to .claude/skills/, and runs only when you invoke it by name.

---
name: clean-with-codebook
description: >-
  Writes or revises a reproducible R cleaning script that applies a
  human-authored codebook (docs/codebook.csv) to raw tabular data. Use when
  asked to clean, recode or prepare raw data in a project that has a codebook.
  Not for exploratory analysis or modelling.
disable-model-invocation: true
---

# Clean data against a codebook

## Hard constraints
1. Never modify anything under data/raw/. Read raw files with explicit
   column types.
2. The codebook is the only source of rules. Do not infer units, ranges,
   missing-value codes or label mappings that the codebook does not state.
3. Do not edit docs/, scripts/functions/, scripts/02_validate.R,
   scripts/03_audit_cleaning.R or anything under tests/. If a check fails,
   report it; never change a check to make it pass.
4. Never drop a row silently. Every excluded row goes in the exclusion log
   with a reason.
5. Every changed cell goes in the cleaning log.
6. A value outside a codebook range that no codebook rule explains is set to
   NA, logged with rule "out_of_range_query", and listed in the final report.
   Never correct it by guessing a unit or decimal error.
7. No imputation.
8. Tidyverse style, native pipe, here::here() for all paths.

## Procedure
1. Present a plan before writing anything: every rule you will apply, the
   codebook row it comes from, and the order. Wait for the user to confirm.
2. If the data contain a value the codebook does not cover, stop and ask.
3. Write scripts/01_clean.R. It reads docs/codebook.csv when it runs; do not
   copy rules into the script by hand. Run it in a fresh R session
   (Rscript scripts/01_clean.R), then run it a second time and confirm the
   outputs are identical.
4. Run every test: Rscript -e "testthat::test_dir('tests')". Report the
   output verbatim, including skips.

## Outputs (exact columns)
- data/derived/voles_clean.csv: raw_row, then the codebook columns. raw_row
  is the 1-based row number in the raw file, not counting the header.
- data/derived/exclusion_log.csv: raw_row, subject_id (as it appears in the
  raw file), reason.
- data/derived/cleaning_log.csv: raw_row, subject_id, column, old_value,
  new_value, rule.
- rule is one of: missing_code, label_recode, id_format, out_of_range_query.

## Final report
Row counts in, out and excluded; every value set to NA for query; any gaps
in the codebook you found.

Step 4: One check, in a fresh R session

The agent says its tests pass: that is a claim. One command, in a fresh R sessionAn R session with nothing loaded from earlier work: Session > Restart R in RStudio or Positron (with “never save .RData” set, as on Day 1), callr::rscript() from the console, or Rscript in the terminal. Code that only works in your current session depends on something you did not record., turns it into evidence.

Run the checks (6 minutes)

Goal: run the tests yourself in a fresh R session, then commit, so that the agent’s “tests pass” becomes evidence you have seen.

1. Run every test. Restart R (Session → Restart R), so that nothing left in your session can make a test pass, then in the R console:

testthat::test_dir(here::here("tests"))

2. Read the change and record it. In the Git pane, Diff scripts/01_clean.R for anything the plan did not mention. Add a line to docs/ai-log.md (date; tool and model; task; what you kept or changed), then commit the script, its outputs and the log.

You are done when every cleaning test passes (other blocks’ tests may skip) and the work, with its AI-log line, is committed.

If it goes wrong: a failing test names the problem. Ask the agent to fix 01_clean.R, quoting the test; never the test itself (it is deny-protected). Short of time? Switch to checkpoint-cleaning.

The course team wrote tests/test_cleaning.R from the agreed codebook, before any cleaning code existed, so it checks what the cleaning should do, not what one script happens to do. The agent did not write it and cannot edit it: Edit(/tests/test_cleaning.R) is one of the deny rules you checked in Step 0. In your own projects, write these tests yourself, from your codebook, before you ask an agent to clean.

# tests/test_cleaning.R ----
# Block 7: the raw data are untouched, every row is accounted for, every
# change is logged truthfully, nothing was over-cleaned, and the clean data
# pass every codebook rule. Written from the agreed codebook, before any
# cleaning code existed. Raw values are read as text, exactly as entered, so a
# logged old value can be compared character for character.
library(testthat)
testthat::local_edition(3)

read_chr <- function(...) {
  readr::read_csv(
    here::here(...),
    col_types = readr::cols(.default = readr::col_character())
  )
}

to_long <- function(data, value_name) {
  data |>
    tidyr::pivot_longer(-raw_row, names_to = "column", values_to = value_name)
}

same <- function(x, y) (is.na(x) & is.na(y)) | (!is.na(x) & !is.na(y) & x == y)

clean_path <- here::here("data", "derived", "voles_clean.csv")

cleaning_inputs <- function() {
  raw_df <- read_chr("data", "raw", "voles_raw.csv") |>
    dplyr::mutate(raw_row = as.character(dplyr::row_number()))
  clean_df <- read_chr("data", "derived", "voles_clean.csv")
  list(
    raw = raw_df,
    clean = clean_df,
    excluded = read_chr("data", "derived", "exclusion_log.csv"),
    log = read_chr("data", "derived", "cleaning_log.csv"),
    raw_long = to_long(raw_df, "raw_value"),
    clean_long = to_long(clean_df, "clean_value")
  )
}

test_that("raw data are unchanged", {
  checksum_path <- here::here("tests", "fixtures", "raw_checksum.txt")
  skip_if_not(file.exists(checksum_path), "Block 7 Step 0 not done yet")
  recorded <- readLines(checksum_path)
  current <- unname(tools::md5sum(here::here("data", "raw", "voles_raw.csv")))
  expect_identical(current, recorded)
})

test_that("every raw row is either in the clean data or in the exclusion log", {
  skip_if_not(file.exists(clean_path), "Block 7 not done yet: no clean data")
  x <- cleaning_inputs()

  expect_equal(nrow(x$raw), nrow(x$clean) + nrow(x$excluded))
  expect_setequal(c(x$clean$raw_row, x$excluded$raw_row), x$raw$raw_row)
  expect_false(any(is.na(x$excluded$reason) | x$excluded$reason == ""))
})

test_that("every log entry is truthful: old value from raw, new value in clean", {
  skip_if_not(file.exists(clean_path), "Block 7 not done yet: no clean data")
  x <- cleaning_inputs()
  wrong_old <- x$log |>
    dplyr::left_join(x$raw_long, by = c("raw_row", "column")) |>
    dplyr::filter(!same(old_value, raw_value))
  wrong_new <- x$log |>
    dplyr::inner_join(x$clean_long, by = c("raw_row", "column")) |>
    dplyr::filter(!same(new_value, clean_value))
  expect_equal(nrow(wrong_old), 0)
  expect_equal(nrow(wrong_new), 0)
})

test_that("every changed cell appears in the log", {
  skip_if_not(file.exists(clean_path), "Block 7 not done yet: no clean data")
  x <- cleaning_inputs()
  numeric_cols <- c("mass_pre_g", "mass_post_g", "metabolic_rate_post")
  changed <- x$clean_long |>
    dplyr::left_join(x$raw_long, by = c("raw_row", "column")) |>
    dplyr::mutate(
      # numbers are compared as numbers, so 28.30 and 28.3 count as unchanged
      differs = dplyr::if_else(
        column %in% numeric_cols,
        !same(suppressWarnings(as.numeric(clean_value)),
              suppressWarnings(as.numeric(raw_value))),
        !same(clean_value, raw_value)
      )
    ) |>
    dplyr::filter(differs)
  unlogged <- dplyr::anti_join(changed, x$log, by = c("raw_row", "column"))
  expect_equal(nrow(unlogged), 0)
})

test_that("no more values were set to NA than the codebook explains", {
  skip_if_not(file.exists(clean_path), "Block 7 not done yet: no clean data")
  x <- cleaning_inputs()
  codebook <- read_chr("docs", "codebook.csv")
  numeric_rules <- dplyr::filter(codebook, !is.na(min) | !is.na(max) | !is.na(missing_codes))

  for (i in seq_len(nrow(numeric_rules))) {
    col <- numeric_rules$column[[i]]
    codes <- trimws(strsplit(dplyr::coalesce(numeric_rules$missing_codes[[i]], ""), ";")[[1]])
    lo <- as.numeric(numeric_rules$min[[i]])
    hi <- as.numeric(numeric_rules$max[[i]])

    kept_raw <- x$raw[[col]][match(x$clean$raw_row, x$raw$raw_row)]
    value <- suppressWarnings(as.numeric(kept_raw))
    explained <- !is.na(kept_raw) & (
      kept_raw %in% codes |
        (!is.na(lo) & !is.na(value) & value < lo) |
        (!is.na(hi) & !is.na(value) & value > hi)
    )
    newly_na <- !is.na(kept_raw) & is.na(x$clean[[col]])

    expect_equal(sum(newly_na), sum(explained),
                 label = paste("values newly set to NA in", col))
  }
})

test_that("cleaning is reproducible: a fresh run writes identical files", {

test_that("clean data pass every rule in the agreed codebook", {
  skip_if_not(file.exists(clean_path), "Block 7 not done yet: no clean data")
  clean_df <- readr::read_csv(
    clean_path,
    col_types = readr::cols(
      subject_id = readr::col_character(),
      sex = readr::col_character(),
      treatment_arm = readr::col_character(),
      mass_pre_g = readr::col_double(),
      mass_post_g = readr::col_double(),
      metabolic_rate_post = readr::col_double(),
      .default = readr::col_character()
    )
  )
  expect_equal(nrow(readr::problems(clean_df)), 0)

  # identifiers and labels
  expect_true(all(grepl("^V[0-9]{3}$", clean_df$subject_id)))

  expect_true(in_range(clean_df$mass_post_g, 15, 60))

TipValidation: another view of the same rules

The last test in tests/test_cleaning.R already checks every rule in the agreed codebook. The template also ships the same rules as a report: scripts/functions/validate_voles.R, written with the pointblank package and run by scripts/02_validate.R. The live block does not use them. What they add is a second view: which rules the raw data break, and how often.

validate_voles.R was transcribed from the codebook by a person, not by the agent that writes the cleaning script. Each line is one rule, and interrogate() reports how many rows break it. (pointblank calls the object that holds the rules an “agent”; it has nothing to do with AI agents.)

# scripts/functions/validate_voles.R ----
# Rules transcribed from docs/codebook.csv by a human, not by the agent
# that writes the cleaning script.

voles_col_types <- function() {
  readr::cols(
    subject_id = readr::col_character(),
    sex = readr::col_character(),
    treatment_arm = readr::col_character(),
    mass_pre_g = readr::col_double(),
    mass_post_g = readr::col_double(),
    metabolic_rate_post = readr::col_double(),
    .default = readr::col_character()
  )
}

validate_voles <- function(data, label) {
  data |>
    pointblank::create_agent(label = label) |>
    pointblank::col_vals_not_null(columns = c(subject_id, sex, treatment_arm)) |>
    pointblank::col_vals_regex(columns = subject_id, regex = "^V[0-9]{3}$") |>
    pointblank::rows_distinct(columns = subject_id) |>
    pointblank::col_vals_in_set(columns = sex, set = c("M", "F")) |>
    pointblank::col_vals_in_set(
      columns = treatment_arm,
      set = c("Control", "Low_dose", "High_dose")
    ) |>
    pointblank::col_vals_between(
      columns = c(mass_pre_g, mass_post_g),
      left = 15, right = 60, na_pass = TRUE
    ) |>
    pointblank::col_vals_between(
      columns = metabolic_rate_post,
      left = 5, right = 30, na_pass = TRUE
    ) |>
    pointblank::interrogate()
}

scripts/02_validate.R runs the rules on the raw data, which should fail (for example Raw data (expected to FAIL): 7 of 10 rules fail), and, once the cleaning has run, on the clean data, which should pass. It also lists any value that could not be read as a number: such a value would become NA and slip past the range rules. In an interactive session it opens the full report in the Viewer.

In the R console:

source(here::here("scripts", "02_validate.R"))
# scripts/02_validate.R ----
# Runs the codebook rules on the raw data (expected to FAIL) and, once
# 01_clean.R has run, on the clean data (expected to PASS). In an interactive
# session the full pointblank report also opens in the Viewer.
library(tidyverse)
library(here)
source(here("scripts", "functions", "validate_voles.R"))

report_validation <- function(validation) {
  steps <- validation$validation_set
  n_failed <- sum(!steps$all_passed)
  cat(
    validation$label, ": ",
    if (n_failed == 0) "all rules pass" else paste(n_failed, "of", nrow(steps), "rules fail"),
    "\n",
    sep = ""
  )
  if (interactive()) print(validation)
  invisible(validation)
}

raw_df <- read_csv(here("data", "raw", "voles_raw.csv"), col_types = voles_col_types())
# values that could not be read as numbers become NA and would pass the
# range rules, so list them
print(problems(raw_df), width = Inf)
report_validation(validate_voles(raw_df, "Raw data (expected to FAIL)"))

clean_path <- here("data", "derived", "voles_clean.csv")
if (file.exists(clean_path)) {
  clean_df <- read_csv(clean_path, col_types = voles_col_types())
  report_validation(validate_voles(clean_df, "Clean data (expected to PASS)"))
}
Warning

na_pass = TRUE lets genuine missing values through, as the test’s range checks do. It would also let through a cleaning script that replaced every mass with NA. Rule checks alone cannot catch over-cleaning; the over-cleaning test in tests/test_cleaning.R can.

TipHow the template’s safeguards were made

The checksum. The template’s tests/fixtures/raw_checksum.txt was written once, from the shipped raw file, like this:

fs::dir_create(here::here("tests", "fixtures"))
writeLines(
  unname(tools::md5sum(here::here("data", "raw", "voles_raw.csv"))),
  here::here("tests", "fixtures", "raw_checksum.txt")
)

Do the same for your own raw data, then commit it. The template’s .gitattributes contains two lines, data/raw/** -text and data/derived/** -text, so git never changes the line endings of the data files when it checks them out. The tests compare those files byte for byte: the raw file against its checksum, and the clean files against a fresh run of the cleaning. Line endings converted by git, as can happen on Windows, would fail both tests with no real change to the data.

The deny rules. This is the .claude/settings.json in your workshop repository, the same file you read in Block 5:

{
  "permissions": {
    "defaultMode": "default",
    "deny": [
      "Edit(/data/raw/**)",
      "Read(/docs/data_note.md)",
      "Edit(/docs/data_note.md)",
      "Edit(/docs/codebook.csv)",
      "Edit(/scripts/02_validate.R)",
      "Edit(/scripts/03_audit_cleaning.R)",
      "Edit(/scripts/functions/validate_voles.R)",
      "Edit(/tests/fixtures/**)",
      "Edit(/tests/make_reference.R)",
      "Edit(/tests/test_cleaning.R)",
      "Edit(/renv.lock)",
      "Edit(/.github/**)",
      "Edit(/.claude/**)",
      "Edit(/.posit/**)",
      "Edit(/hooks/**)",
      "Read(/.Renviron)",
      "Read(/.env)"
    ]
  }
}

A leading / anchors each pattern to the project root. The rules protect specific files rather than whole folders, so the agent can still write scripts/01_clean.R and data/derived/. To protect files of your own, add rules with /permissions. Posit Assistant has no documented path rules for file edits; use the guard hook from the Going further section of Block 5 instead.

Warning

What each control covers. The deny rule blocks the agent’s file-editing tools, and shell output redirects such as > file. It does not cover R code the agent runs: an R script that writes to data/raw/ is a different route. The checksum test catches a change made by any route, but only after the fact. Use both: one prevents, the other detects. A deny rule on reading does not stop data reaching the model provider by other routes; see Block 3.

The skill. The skill ships in .agents/skills/ and .claude/skills/. To use it in another project, download it and unzip it into that project’s .agents/skills/ (unzip(file.choose(), exdir = here::here(".agents", "skills"))), then copy the folder into .claude/skills/ with fs::dir_copy().

Glossary

term definition
checksum A short fingerprint computed from a file's contents, for example with tools::md5sum(). Any change to the file changes the checksum, so it detects changes made by any route.
codebook A table describing each variable: its type, valid range, missing-value codes, unit and label mappings. It is the data dictionary from Day 2 with machine-readable rules, and you own it, not the AI.
deny rule A permission rule in the deny list of .claude/settings.json that stops Claude Code's built-in tools from editing or reading the matching files. It checks shell output redirects such as > file, but not R code or most other commands that change the same files.
fresh R session An R session with nothing loaded from earlier work: Session > Restart R in RStudio or Positron (with "never save .RData" set, as on Day 1), callr::rscript() from the console, or Rscript in the terminal. Code that only works in your current session depends on something you did not record.
lockfile The renv.lock file that records the R version and the exact package versions a project uses, so renv::restore() can rebuild the same environment.
sentinel value A number with a special meaning, such as 9999 for "not recorded" or -1 for "run failed". It must be documented in a codebook and recoded before analysis.
