Block 7: Data cleaning and validation with AI

Cleaning is where an AI assistant looks most useful and where its mistakes are hardest to see. A cleaning script can run without error, return the right columns and produce plausible values while having treated a missing-value code as a measurement, kept the same animal twice, or dropped a row nobody noticed. None of these raises an error.

By the end of this block you will have checks that catch each of these automatically, every time the cleaning runs: a test that fails if any value changed without a log entry, one that fails if a row disappears, one that fails if more values became missing than the codebook explains, and one that fails if the raw data change at all. That is what makes it safe to let an agent write the cleaning script.

This block treats cleaning as four artefacts, each with a different owner:

Artefact Owner Why
Codebook (docs/codebook.csv) You Missing-value codes, units, valid ranges and label mappings are facts about how the data were collected. They cannot be inferred reliably from the values.
Cleaning skill Reusable How you clean: never touch raw data, log every change, never drop a row silently. The same for every dataset.
Validation and audit scripts You, or a separate AI conversation Written from the codebook, independently of the cleaning code, so one misunderstanding cannot pass both.
Enforcement Configuration Rules that hold whether or not the agent follows its instructions.

The codebookA table describing each variable: its type, valid range, missing-value codes, unit and label mappings. It is the data dictionary from Day 2 with machine-readable rules, and you own it, not the AI. is the hub. The cleaning and the checks both read it, but neither reads the other, so a misunderstanding in one is caught by the other:

Facts first

data/raw/voles_raw.csv, pinned by a checksum

profiled in R

00_profile.R output

plus the provider’s note

docs/codebook.csv

Two branches that read the codebook, never each other

Skill writes and runs scripts/01_clean.R

writes

Clean data, cleaning log, exclusion log

Validation rules in validate_voles.R, transcribed from the codebook

Then compare

Tests and audit: raw data unchanged, every row accounted for, every change logged

Independence is the point: one misunderstanding cannot pass both branches.

You will work on a version of the voles data with errors planted in it. Your instructor holds the answer key, so at the end you can measure what your pipeline caught and what it missed.

⏱ ~54 minutes

Note

Why not simply ask the AI to clean the data? In a 2025 study, language models given deliberately polluted tables found missing values in standard formats but struggled with codes such as -1 (a sentinel valueA number with a special meaning, such as 9999 for “not recorded” or -1 for “run failed”. It must be documented in a codebook and recoded before analysis.), rarely detected non-exact duplicates, and did worse as errors increased (Spreafico et al., 2025). The models were older than those you will use and did not write or run code, so treat this as a map of where to look. Those error classes are planted in this block’s data.

Step 0: Lock the raw data

Everything later depends on the raw file being exactly what the data provider sent. The deny rules from Block 6 already protect it; here you add a checksumA short fingerprint computed from a file’s contents, for example with tools::md5sum(). Any change to the file changes the checksum, so it detects changes made by any route. and confirm the rules work.

Start: your workshop repository open, committed and clean, on the main branch. (If you are behind and need Block 5’s files, switch to block5-done from the Git pane’s branch menu first.)

1. Record a checksum and commit it. Run this once, yourself.

In the R console:

raw_path <- here::here("data", "raw", "voles_raw.csv")
checksum_path <- here::here("tests", "fixtures", "raw_checksum.txt")
fs::dir_create(here::here("tests", "fixtures"))
writeLines(unname(tools::md5sum(raw_path)), checksum_path)

Then commit tests/fixtures/raw_checksum.txt from the Git pane.

2. Confirm the deny rules are active. In Claude Code, run /permissions. The rules from .claude/settings.json should be listed, including the deny ruleA permission rule in the deny list of .claude/settings.json that stops Claude Code’s built-in tools from editing or reading the matching files. It checks shell output redirects such as > file, but not R code or most other commands that change the same files. Edit(/data/raw/**).

3. Test the control, do not assume it. Ask:

Prompt (Claude Code):

Add a comment line to the top of data/raw/voles_raw.csv.

It should be refused. Then confirm the file is unchanged.

In the R console:

raw_path <- here::here("data", "raw", "voles_raw.csv")
checksum_path <- here::here("tests", "fixtures", "raw_checksum.txt")
identical(unname(tools::md5sum(raw_path)), readLines(checksum_path))

R returns TRUE. (The test file in Step 5 checks this too; its other tests skip until the cleaned data exist.)

You are done when the checksum is committed, the edit was refused and R returned TRUE.

If it goes wrong: if R returns FALSE, the raw file changed: open the Git pane, Revert data/raw/voles_raw.csv, and run the check again. If the agent offers another way to make the edit after the refusal (a shell command, say), decline it.

The deny rule prevents one route; the checksum detects a change made by any route. Going further lists the full settings file and what each control covers.

Step 1: Profile the raw data (R, not AI)

Profiling is counting, and counting is something you should compute rather than ask a model to estimate. Run the provided script yourself.

In the R console:

source(here::here("scripts", "00_profile.R"))
# scripts/00_profile.R ----
# Purpose: describe the raw file as entered, before any decision is made.
# Every column is read as character so codes such as 9999 or -1 appear
# exactly as entered.
library(tidyverse)
library(here)

raw_df <- read_csv(
  here("data", "raw", "voles_raw.csv"),
  col_types = cols(.default = col_character())
)

# one row per column: missingness, distinct values, numeric range ----
profile_df <- raw_df |>
  pivot_longer(everything(), names_to = "column", values_to = "value") |>
  # suppressWarnings: text values become NA here by design
  mutate(value_num = suppressWarnings(as.numeric(value))) |>
  summarise(
    n_rows = n(),
    n_missing = sum(is.na(value)),
    n_distinct = n_distinct(value, na.rm = TRUE),
    n_numeric = sum(!is.na(value_num)),
    min_numeric = if (all(is.na(value_num))) NA_real_ else min(value_num, na.rm = TRUE),
    max_numeric = if (all(is.na(value_num))) NA_real_ else max(value_num, na.rm = TRUE),
    .by = column
  )

# every distinct label in the categorical columns ----
labels_df <- raw_df |>
  select(sex, treatment_arm) |>
  pivot_longer(everything(), names_to = "column", values_to = "value") |>
  count(column, value, sort = TRUE)

# identifiers that appear more than once ----
repeated_ids_df <- raw_df |>
  count(subject_id) |>
  filter(n > 1)

# print in full, and save the profile so it can be opened, pasted or diffed ----
print(profile_df, n = Inf, width = Inf)
print(labels_df, n = Inf, width = Inf)
print(repeated_ids_df, width = Inf)
write_csv(profile_df, here("docs", "profile.csv"))

It prints the profile in full and also saves it as docs/profile.csv, which you can open with View(readr::read_csv(here::here("docs", "profile.csv"), show_col_types = FALSE)) (in Positron, the Data Explorer) and paste from in Step 2. Keep it: it is the factual input to the codebook.

Step 2: Draft the codebook, then audit it

The codebook is the data dictionary you wrote for the README on Day 2 (Fixing it with structure, cleaning and a README), with machine-readable rules added: valid ranges, missing-value codes and label mappings that both the cleaning skill and the validation rules can read.

Draft and audit the codebook (12 minutes)

1. Let an AI draft it from the profile alone. Use a browser chat window, not Claude Code: started in your workshop repository, Claude Code could open docs/data_note.md itself, and the point of this step is to see what the AI infers without it. Paste only the profile output.

Prompt (browser chat):

Here is a profile of a raw data file. Draft a codebook as CSV with the
columns: column, type, rule, min, max, missing_codes, unit, source.
In the source column, state for every entry whether it comes from the
profile or is your assumption.

[paste the contents of docs/profile.csv]

Save the draft as docs/codebook.csv yourself, in the RStudio or Positron editor (File → New File → Text File). Avoid Excel: it can change the quoted rule fields and the encoding without telling you. The deny rules stop the agent from writing that file: the codebook is yours.

2. Audit the draft. Before you open docs/data_note.md, answer:

  • Did the draft list 9999 as a missing-value code, or treat it as a large measurement?
  • Did it notice that -1 is a code?
  • Where did its min and max come from? A range read off the data includes the errors in the data, so it cannot be used to detect them. Valid ranges must come from the biology or the protocol.

3. Correct it against the data provider’s note. Open docs/data_note.md and edit the codebook yourself. Every line should be traceable to the note or to a decision you can defend. Where the note does not give a unit (it does not for metabolic rate), write <unit> rather than a guess: Block 10’s README check relies on unknowns staying visible. Commit it.

You are done when docs/codebook.csv is committed, with every rule traceable to the note or to your own decision.

If it goes wrong: if you are short of time, copy the codebook below into docs/codebook.csv and commit it; it is what most groups converge on.

column,type,rule,min,max,missing_codes,unit,source
subject_id,character,"pattern ^V[0-9]{3}$; unique; pad digits to three",,,,,data note
sex,character,"allowed M, F; recode male to M, female to F",,,,,data note
treatment_arm,character,"allowed Control, Low_dose, High_dose; match case-insensitively",,,,,data note
mass_pre_g,double,,15,60,9999,g,data note (range from colony records)
mass_post_g,double,,15,60,9999,g,data note (range from colony records)
metabolic_rate_post,double,,5,30,-1,<unit>,data note (range from equipment)

Step 3: Run the validation rules

Validation rules are transcribed from the codebook, not from the cleaning script. If the same AI conversation writes both, a single misunderstanding (for example, that -1 is a valid reading) passes both.

The template provides scripts/functions/validate_voles.R, written from the codebook by a person. It uses the pointblank package: each line is one rule, and interrogate() reports how many rows break it. (pointblank calls the object that holds the rules an “agent”; it has nothing to do with AI agents.) You do not need to write pointblank code today.

# scripts/functions/validate_voles.R ----
# Rules transcribed from docs/codebook.csv by a human, not by the agent
# that writes the cleaning script.

voles_col_types <- function() {
  readr::cols(
    subject_id = readr::col_character(),
    sex = readr::col_character(),
    treatment_arm = readr::col_character(),
    mass_pre_g = readr::col_double(),
    mass_post_g = readr::col_double(),
    metabolic_rate_post = readr::col_double(),
    .default = readr::col_character()
  )
}

validate_voles <- function(data, label) {
  data |>
    pointblank::create_agent(label = label) |>
    pointblank::col_vals_not_null(columns = c(subject_id, sex, treatment_arm)) |>
    pointblank::col_vals_regex(columns = subject_id, regex = "^V[0-9]{3}$") |>
    pointblank::rows_distinct(columns = subject_id) |>
    pointblank::col_vals_in_set(columns = sex, set = c("M", "F")) |>
    pointblank::col_vals_in_set(
      columns = treatment_arm,
      set = c("Control", "Low_dose", "High_dose")
    ) |>
    pointblank::col_vals_between(
      columns = c(mass_pre_g, mass_post_g),
      left = 15, right = 60, na_pass = TRUE
    ) |>
    pointblank::col_vals_between(
      columns = metabolic_rate_post,
      left = 5, right = 30, na_pass = TRUE
    ) |>
    pointblank::interrogate()
}

Run the rules on the raw data. They should fail. If raw data pass every rule, either the data are already clean or the rules are too weak, and you should suspect the second. Run the provided script.

In the R console:

source(here::here("scripts", "02_validate.R"))

It prints one line per data set, for example Raw data (expected to FAIL): 7 of 10 rules fail, and opens the full report in the Viewer, where you can see which rules fail and how many rows each flags. It also lists any value that could not be read as a number: such a value would become NA and slip past the range rules, so the list should be empty. Once the cleaning has run, the same script also validates the clean data, which should pass.

# scripts/02_validate.R ----
# Runs the codebook rules on the raw data (expected to FAIL) and, once
# 01_clean.R has run, on the clean data (expected to PASS). In an interactive
# session the full pointblank report also opens in the Viewer.
library(tidyverse)
library(here)
source(here("scripts", "functions", "validate_voles.R"))

report_validation <- function(validation) {
  steps <- validation$validation_set
  n_failed <- sum(!steps$all_passed)
  cat(
    validation$label, ": ",
    if (n_failed == 0) "all rules pass" else paste(n_failed, "of", nrow(steps), "rules fail"),
    "\n",
    sep = ""
  )
  if (interactive()) print(validation)
  invisible(validation)
}

raw_df <- read_csv(here("data", "raw", "voles_raw.csv"), col_types = voles_col_types())
# values that could not be read as numbers become NA and would pass the
# range rules, so list them
print(problems(raw_df), width = Inf)
report_validation(validate_voles(raw_df, "Raw data (expected to FAIL)"))

clean_path <- here("data", "derived", "voles_clean.csv")
if (file.exists(clean_path)) {
  clean_df <- read_csv(clean_path, col_types = voles_col_types())
  report_validation(validate_voles(clean_df, "Clean data (expected to PASS)"))
}

Every failure is a problem that the cleaning must resolve or log.

Warning

na_pass = TRUE lets genuine missing values through. It would also let through a cleaning script that replaced every mass with NA. Validation alone cannot catch over-cleaning; tests/test_audit.R in Step 5 can.

Step 4: Clean with the skill, plan first

The skill holds the procedure; the codebook holds the facts. It sets disable-model-invocation: true, so it runs only when you invoke it by name. That is appropriate for a workflow that writes files.

Note.agents/skills/clean-with-codebook/SKILL.md 
---
name: clean-with-codebook
description: >-
  Writes or revises a reproducible R cleaning script that applies a
  human-authored codebook (docs/codebook.csv) to raw tabular data. Use when
  asked to clean, recode or prepare raw data in a project that has a codebook.
  Not for exploratory analysis or modelling.
disable-model-invocation: true
---

# Clean data against a codebook

## Hard constraints
1. Never modify anything under data/raw/. Read raw files with explicit
   column types.
2. The codebook is the only source of rules. Do not infer units, ranges,
   missing-value codes or label mappings that the codebook does not state.
3. Do not edit docs/, scripts/functions/, scripts/02_validate.R,
   scripts/03_audit_cleaning.R or anything under tests/. If a check fails,
   report it; never change a check to make it pass.
4. Never drop a row silently. Every excluded row goes in the exclusion log
   with a reason.
5. Every changed cell goes in the cleaning log.
6. A value outside a codebook range that no codebook rule explains is set to
   NA, logged with rule "out_of_range_query", and listed in the final report.
   Never correct it by guessing a unit or decimal error.
7. No imputation.
8. Tidyverse style, native pipe, here::here() for all paths.

## Procedure
1. Present a plan before writing anything: every rule you will apply, the
   codebook row it comes from, and the order. Wait for the user to confirm.
2. If the data contain a value the codebook does not cover, stop and ask.
3. Write scripts/01_clean.R. It reads docs/codebook.csv when it runs; do not
   copy rules into the script by hand. Run it in a fresh R session
   (Rscript scripts/01_clean.R), then run it a second time and confirm the
   outputs are identical.
4. Run scripts/02_validate.R (raw data should fail, clean data should pass)
   and every test: Rscript -e "testthat::test_dir('tests')". Report both
   outputs verbatim, including skips.

## Outputs (exact columns)
- data/derived/voles_clean.csv: raw_row, then the codebook columns. raw_row
  is the 1-based row number in the raw file, not counting the header.
- data/derived/exclusion_log.csv: raw_row, subject_id (as it appears in the
  raw file), reason.
- data/derived/cleaning_log.csv: raw_row, subject_id, column, old_value,
  new_value, rule.
- rule is one of: missing_code, label_recode, id_format, out_of_range_query.

## Final report
Row counts in, out and excluded; every value set to NA for query; any gaps
in the codebook you found.

Step 5: Check the result

Start: the three files in data/derived/ exist, whether the agent wrote them or you switched to block7-done.

Five checks, each catching something the others cannot. Checks 1 to 3 are the core; if the room is behind, your instructor runs 4 and 5.

1. The tests (the core check). Two provided test files check everything that can be checked mechanically. Restart R (Session → Restart R), then:

In the R console:

testthat::test_file(here::here("tests", "test_cleaning.R"))
testthat::test_file(here::here("tests", "test_audit.R"))

tests/test_cleaning.R checks that the raw data are unchanged (the checksum from Step 0), that every raw row is either in the clean data or in the exclusion log with a reason, and that the clean data pass every codebook rule.

tests/test_audit.R checks the agent’s record of its own work, reading the raw data as text, exactly as entered:

  • every old value in the cleaning log matches the raw file, so the log tells the truth;
  • every new value in the log is the value in the clean file;
  • every cell that changed appears in the log, so nothing was altered without a record (the most dangerous outcome in this block);
  • every rule named in the log is one of the agreed four (missing_code, label_recode, id_format, out_of_range_query);
  • every excluded row’s subject_id is the one in the raw file;
  • no more values became NA than the codebook’s missing-value codes and ranges explain, which catches over-cleaning that validation alone misses.

You are done when both files pass with no failures.

If it goes wrong: a failing test names the problem. Ask the agent to fix 01_clean.R, not the test: the tests and checks are deny-protected, and a check changed to pass proves nothing. If time is short, switch to block7-done and run the tests there.

# tests/test_cleaning.R ----
# Block 7: the raw data are untouched, every row is accounted for, and the
# clean data pass every codebook rule.
library(testthat)
testthat::local_edition(3)
source(here::here("scripts", "functions", "validate_voles.R"))

read_chr <- function(...) {
  readr::read_csv(
    here::here(...),
    col_types = readr::cols(.default = readr::col_character())
  )
}

clean_path <- here::here("data", "derived", "voles_clean.csv")

test_that("raw data are unchanged", {
  checksum_path <- here::here("tests", "fixtures", "raw_checksum.txt")
  skip_if_not(file.exists(checksum_path), "Block 7 Step 0 not done yet")
  recorded <- readLines(checksum_path)
  current <- unname(tools::md5sum(here::here("data", "raw", "voles_raw.csv")))
  expect_identical(current, recorded)
})

test_that("every raw row is either in the clean data or in the exclusion log", {
  skip_if_not(file.exists(clean_path), "Block 7 not done yet: no clean data")
  raw_df <- read_chr("data", "raw", "voles_raw.csv")
  clean_df <- read_chr("data", "derived", "voles_clean.csv")
  excluded_df <- read_chr("data", "derived", "exclusion_log.csv")

  expect_equal(nrow(raw_df), nrow(clean_df) + nrow(excluded_df))
  expect_setequal(
    c(clean_df$raw_row, excluded_df$raw_row),
    as.character(seq_len(nrow(raw_df)))
  )
  expect_false(any(is.na(excluded_df$reason) | excluded_df$reason == ""))
})

test_that("clean data pass every codebook rule", {
  skip_if_not(file.exists(clean_path), "Block 7 not done yet: no clean data")
  clean_df <- readr::read_csv(clean_path, col_types = voles_col_types())
  expect_equal(nrow(readr::problems(clean_df)), 0)
  validation <- validate_voles(clean_df, "Clean data")
  expect_true(pointblank::all_passed(validation))
})
# tests/test_audit.R ----
# Block 7: the cleaning log is truthful and complete, and the cleaning did no
# more than the codebook allows. Raw values are read as text, exactly as
# entered, so a logged old value can be compared character for character.
library(testthat)
testthat::local_edition(3)

log_path <- here::here("data", "derived", "cleaning_log.csv")

allowed_rules <- c("missing_code", "label_recode", "id_format", "out_of_range_query")

read_chr <- function(...) {
  readr::read_csv(
    here::here(...),
    col_types = readr::cols(.default = readr::col_character())
  )
}

to_long <- function(data, value_name) {
  data |>
    tidyr::pivot_longer(-raw_row, names_to = "column", values_to = value_name)
}

same <- function(x, y) (is.na(x) & is.na(y)) | (!is.na(x) & !is.na(y) & x == y)

audit_inputs <- function() {
  raw_df <- read_chr("data", "raw", "voles_raw.csv") |>
    dplyr::mutate(raw_row = as.character(dplyr::row_number()))
  clean_df <- read_chr("data", "derived", "voles_clean.csv")
  log_df <- read_chr("data", "derived", "cleaning_log.csv")
  list(
    raw = raw_df,
    clean = clean_df,
    log = log_df,
    raw_long = to_long(raw_df, "raw_value"),
    clean_long = to_long(clean_df, "clean_value")
  )
}

test_that("every logged old value matches the raw file", {
  skip_if_not(file.exists(log_path), "Block 7 not done yet: no cleaning log")
  x <- audit_inputs()
  untruthful <- x$log |>
    dplyr::left_join(x$raw_long, by = c("raw_row", "column")) |>
    dplyr::filter(!same(old_value, raw_value))
  expect_equal(nrow(untruthful), 0)
})

test_that("every logged new value is the value in the clean file", {
  skip_if_not(file.exists(log_path), "Block 7 not done yet: no cleaning log")
  x <- audit_inputs()
  mismatched <- x$log |>
    dplyr::inner_join(x$clean_long, by = c("raw_row", "column")) |>
    dplyr::filter(!same(new_value, clean_value))
  expect_equal(nrow(mismatched), 0)
})

test_that("every changed cell appears in the log", {
  skip_if_not(file.exists(log_path), "Block 7 not done yet: no cleaning log")
  x <- audit_inputs()
  numeric_cols <- c("mass_pre_g", "mass_post_g", "metabolic_rate_post")
  changed <- x$clean_long |>
    dplyr::left_join(x$raw_long, by = c("raw_row", "column")) |>
    dplyr::mutate(
      # numbers are compared as numbers, so 28.30 and 28.3 count as unchanged
      differs = dplyr::if_else(
        column %in% numeric_cols,
        !same(suppressWarnings(as.numeric(clean_value)),
              suppressWarnings(as.numeric(raw_value))),
        !same(clean_value, raw_value)
      )
    ) |>
    dplyr::filter(differs)
  unlogged <- dplyr::anti_join(changed, x$log, by = c("raw_row", "column"))
  expect_equal(nrow(unlogged), 0)
})

test_that("every cleaning-log rule comes from the agreed list", {
  skip_if_not(file.exists(log_path), "Block 7 not done yet: no cleaning log")
  rules <- unique(audit_inputs()$log$rule)
  expect_true(all(rules %in% allowed_rules),
              label = paste("unexpected rule(s):",
                            paste(setdiff(rules, allowed_rules), collapse = ", ")))
})

test_that("each excluded row's subject_id is the one in the raw file", {
  skip_if_not(file.exists(log_path), "Block 7 not done yet: no cleaning log")
  x <- audit_inputs()
  excluded <- read_chr("data", "derived", "exclusion_log.csv") |>
    dplyr::left_join(dplyr::select(x$raw, raw_row, raw_id = subject_id),
                     by = "raw_row")
  expect_true(all(same(excluded$subject_id, excluded$raw_id)))
})

test_that("no more values were set to NA than the codebook explains", {
  skip_if_not(file.exists(log_path), "Block 7 not done yet: no cleaning log")
  x <- audit_inputs()
  codebook <- read_chr("docs", "codebook.csv")
  numeric_rules <- dplyr::filter(codebook, !is.na(min) | !is.na(max) | !is.na(missing_codes))

  for (i in seq_len(nrow(numeric_rules))) {
    col <- numeric_rules$column[[i]]
    codes <- trimws(strsplit(dplyr::coalesce(numeric_rules$missing_codes[[i]], ""), ";")[[1]])
    lo <- as.numeric(numeric_rules$min[[i]])
    hi <- as.numeric(numeric_rules$max[[i]])

    kept_raw <- x$raw[[col]][match(x$clean$raw_row, x$raw$raw_row)]
    value <- suppressWarnings(as.numeric(kept_raw))
    explained <- !is.na(kept_raw) & (
      kept_raw %in% codes |
        (!is.na(lo) & !is.na(value) & value < lo) |
        (!is.na(hi) & !is.na(value) & value > hi)
    )
    newly_na <- !is.na(kept_raw) & is.na(x$clean[[col]])

    expect_equal(sum(newly_na), sum(explained),
                 label = paste("values newly set to NA in", col))
  }
})

The Step 0 controls in full

Line endings. The template’s .gitattributes contains this line, so git does not convert line endings, which would change the checksum on Windows:

data/raw/** -text

Deny rules. This is the .claude/settings.json in your workshop repository, the same file you read in Block 6:

{
  "permissions": {
    "deny": [
      "Edit(/data/raw/**)",
      "Edit(/docs/data_note.md)",
      "Edit(/docs/codebook.csv)",
      "Edit(/scripts/02_validate.R)",
      "Edit(/scripts/03_audit_cleaning.R)",
      "Edit(/scripts/functions/validate_voles.R)",
      "Edit(/tests/fixtures/**)",
      "Edit(/tests/make_reference.R)",
      "Edit(/tests/test_cleaning.R)",
      "Edit(/renv.lock)",
      "Edit(/.github/**)",
      "Edit(/.claude/**)",
      "Edit(/.posit/**)",
      "Edit(/hooks/**)",
      "Read(/.Renviron)",
      "Read(/.env)"
    ]
  }
}

A leading / anchors each pattern to the project root. The rules protect specific files rather than whole folders, so the agent can still write scripts/01_clean.R and data/derived/. Posit Assistant has no documented path rules for file edits; use the guard hook from the Going further section of Block 6 instead.

Warning

What each control covers. The deny rule blocks the agent’s file-editing tools, and shell output redirects such as > file. It does not cover R code the agent runs: an R script that writes to data/raw/ is a different route. The checksum test catches a change made by any route, but only after the fact. On the Copilot cloud agent, where you have no local permission file, the checksum test running in CI plus branch protection is your control. Use both where you can: one prevents, the other detects.

Data governance. A deny rule on editing does not stop data reaching the model provider; see Block 4.

Glossary

term definition
checksum A short fingerprint computed from a file's contents, for example with tools::md5sum(). Any change to the file changes the checksum, so it detects changes made by any route.
codebook A table describing each variable: its type, valid range, missing-value codes, unit and label mappings. It is the data dictionary from Day 2 with machine-readable rules, and you own it, not the AI.
deny rule A permission rule in the deny list of .claude/settings.json that stops Claude Code's built-in tools from editing or reading the matching files. It checks shell output redirects such as > file, but not R code or most other commands that change the same files.
fresh R session An R session with nothing loaded from earlier work: Session > Restart R in RStudio or Positron (with "never save .RData" set, as on Day 1), callr::rscript() from the console, or Rscript in the terminal. Code that only works in your current session depends on something you did not record.
lockfile The renv.lock file that records the R version and the exact package versions a project uses, so renv::restore() can rebuild the same environment.
sentinel value A number with a special meaning, such as 9999 for "not recorded" or -1 for "run failed". It must be documented in a codebook and recoded before analysis.
