Part 1: Why code review matters

⏱ ~15 minutes

This morning, in the reproducibility chapter, you ran the many-analysts activity: the same C. elegans reproduction dataset, the same broad question, meaningfully different results from different participants. That illustrated the problem of underspecified methods: analytical decisions that are not documented produce variable, non-transparent science. You then cleaned the raw data and built a documented project.

Code review addresses a related but distinct failure: the code does not actually do what the analyst thinks it does. It is possible to write a fully specified, well-documented analysis plan, implement it in R, and still have the code contain errors that silently produce wrong results. No amount of pre-registration prevents this; only someone actually reading the code can catch it.

The paper for this chapter:

Ivimey-Cook, E.R., Pick, J.L., Bairos-Novak, K.R., Culina, A., Gould, E., Grainger, M.J., Marshall, B.M., Moreau, D., Paquet, M., Royauté, R., Sánchez-Tójar, A., Silva, I., & Windecker, S.M. (2023). Implementing code review in the scientific workflow: Insights from ecology and evolutionary biology. Journal of Evolutionary Biology, 36(10), 1347–1356. https://doi.org/10.1111/jeb.14230

Spend five minutes reading the abstract and Figure 1 now.

Types of coding error

Errors take three forms, all of which are common:

Conceptual: the wrong model for the data type, such as Gaussian errors on offspring counts (which are non-negative integers and often overdispersed); a fixed effect where a random effect is needed; comparing models that are not comparable.

Programmatic: the right model implemented incorrectly, such as selecting columns by position rather than name; an operator-precedence slip that quietly changes which rows are analysed; a column name that breaks on a round-trip through disk.

Syntactic: misspelled function names, wrong argument orders. These at least cause a visible error rather than a silent wrong result.

Quick check

What type of error is this? A Gaussian model fitted to offspring counts.

Conceptual: the wrong model for the data. Offspring counts are non-negative whole numbers and often overdispersed, so a count model fits them better.

What type of error is this? names(dat1)[c(2, 5)] <- ... renames the wrong columns after someone reorders the data file.

Programmatic: the idea (rename these columns) is right, but choosing them by position breaks silently when the column order changes. Rename by name, for example with rename().

True or false? Syntactic errors are usually the least dangerous of the three, because R stops with a visible error.

True. A misspelled function or a wrong argument usually stops R with an error you can see. Conceptual and programmatic errors often run without complaint and give wrong numbers.

Part 2: The 4Rs framework

⏱ ~20 minutes

Ivimey-Cook et al. (2023) organise what a code reviewer should evaluate around four questions, the 4Rs (Figure 1 of the paper):

The 4Rs of code review (Ivimey-Cook et al. 2023, Figure 1)
# R Question Tagline
1 Reported Is the code as reported? Methods and code must match (note in this case we are simply using the code to help us link to the methods)
2 Run Does the code run? Code must be executable
3 Reliable Is the code reliable? Code runs and completes as intended
4 Reproducible Are the results reproducible? Results must be able to be reproduced

Each R in the context of ANALYSIS.R

Reported. A reviewer should be able to hold the methods section in one hand and the code in the other and verify they describe the same analysis. ANALYSIS.R has no header and almost no comments: a reviewer cannot tell what the intended analysis is, why one worm is dropped, or which of the three models that get fitted is meant to be the result. Its variable names (block, total_offspring) also drift from the data dictionary you wrote this morning (B, TO).

Run. Can the code be executed on a different machine, in a clean R session? ANALYSIS.R reads its data from an absolute OneDrive path, and lines 23–24 call libray(), a typo for library(), so the script does not even run to the end. Failing at this stage is common: when Trisovic et al. (2022) re-ran more than 9,000 archived R files, 74% failed on the first attempt.

Reliable. The hardest R. Code can run without error and still produce a wrong result every time. In ANALYSIS.R: an operator-precedence slip changes which worms are analysed; the 9999 “not recorded” sentinel you met this morning is never handled; and a count outcome is fitted with a Gaussian model. None of these throw an error.

Reproducible. Given the same data and code, does re-running produce the reported outputs? ANALYSIS.R fits three models, designates none of them as the answer, saves no model output to disk, and writes a figure called final2.jpg, whose “2” hints at undocumented earlier versions.

Activity: map ANALYSIS.R to the 4Rs (5 minutes)

Open ANALYSIS.R. Without running it, post one specific example for each R in Slack:

  • Reported: Something a reader could not understand without asking the author
  • Run: Something that would stop it running on your machine right now
  • Reliable: Something that could produce a silently wrong result
  • Reproducible: Something that would prevent recovering the reported numbers

Quick check

Which R does libray(tidyverse) fail first?

Run. libray() is not a function, so R stops at that line and nothing after it runs.

Which R does it fail first? The 9999 sentinel is never handled.

Reliable. The script runs, but every 9999 enters the models as a real count, so the estimates are wrong every time.

Which R does it fail first? Three models are fitted, and none is named as the result.

Reproducible. Without knowing which model is the result, and with nothing saved to disk, nobody can recover the reported numbers.

Which R does it fail first? The script calls the batch column block, but the data dictionary calls it B.

Reported. The code and the documented data no longer describe the same thing, so a reader has to work out the mapping for themselves.

Step 1: First read (3 minutes)

Read the script end to end without annotating. Ask yourself:

  • What does this script try to do?
  • What is the intended analysis?
  • What immediately strikes you as wrong?
  • Could the style be improved? Would an automatic code formatter such as styler or Air help?

Then move to the checklist.

The problems revealed

Issues in ANALYSIS.R
# R Lines Issue Severity
P1 Run 23–24 libray(tidyverse) and libray(hablar) are typos for library(). R throws 'could not find function libray' and execution stops here, if it gets this far (see P3). (library(lme4) is also loaded twice — lines 1 and 16.) Critical
P2 Run 26, 35, 37, 78 Absolute OneDrive paths in read.csv(), write.csv(), the re-read, and ggsave(). The script only runs on the original author's machine. Critical
P3 Run / Reported 1–24 About 22 library() calls, the great majority unused (xgboost, glmnet, caret, randomForest, rpart, rvest, shiny, plotly, gplots, ggridges, ...). Slows loading, hides the real dependencies, and any one missing package aborts the script: on a machine without gplots, it stops at line 13. One real dependency is hidden altogether: stat_summary(fun.data = 'mean_cl_boot') needs Hmisc, which is never loaded. No versions recorded. High
P4 Reliable 45 Operator-precedence bug. filter(strain == 'daf' | strain == 'empty_vector' & total_offspring > 0) is meant to drop impossible negative counts, but & binds tighter than |, so R reads it as daf OR (empty_vector AND count above 0). The check only applies to empty_vector worms, and the one negative count (TO = -46) belongs to a daf worm, so it goes into the models. Critical
P5 Reliable 28, 35–37, 41, 43–46 Line 28 names column 5 'total offspring', with a space. After write.csv() then read.csv() (lines 35–37) it becomes total.offspring, so full_dat$total_offspring on line 41 silently returns NULL (the plot shows strain counts, not offspring), and the pipeline at lines 43–46 stops with 'object total_offspring not found'. Critical
P6 Reliable 28 names(dat1)[c(2, 5)] renames columns by position. If the column order ever changes, the wrong columns are renamed — with no error. High
P7 Reliable / Reported 31, 45 Rows disappear without a word. filter(worm_id != 5) drops worm 5 with no reason given, and also drops the two worms with a missing worm_id. The exact-match strain filter (line 45) quietly loses the 24 'DAF' and 3 'empty_vector ' rows, while 'eodf' stays in as a third diet level and the duplicated rows are never removed. High
P8 Reliable 33 complete.cases() on 'total offspring' removes only NA. It does NOT handle the 9999 'not recorded' sentinel from the raw data (reproducibility chapter): all three 9999s enter the models as real offspring counts, and the empty_vector/EODF mean jumps from about 185 to about 590. Critical
P9 Reliable 66 anova(m1a, m1b, m1c) puts two lmer models and an lm in one call. R refits the mixed models with ML (with only a brief message), reorders all three by number of parameters and tests each against the next. That chain compares m1a with m1c, which are not nested (they differ in both fixed and random effects), so that row's test is meaningless; no hypothesis says which comparison matters. Critical
P10 Reliable 48–64 total_offspring is a count, but all three models are Gaussian (lmer / lm). A count GLMM (Poisson or negative binomial) is not considered; no residual or distributional checks. High
P11 Reliable 70–76 geom_smooth(method = 'lm') over a categorical x (as.factor(strain)) with colour groups draws nothing at all: each strain × diet group has only one x value, so there is no line to fit. Both stat_summary() calls pass a parameter their geom does not use (shape to the errorbar, width to the point); ggplot2 ignores them with a warning. Medium
P12 Reproducible 48–66, 78 Three models are fitted but none is designated as the result and no model output is saved to disk. The figure is saved as final2.jpg (the '2' implies undocumented earlier versions). No sessionInfo(), no renv, no versions; full.dat / full_dat / Na are confusingly similar names, and after a run the folder holds two different 'final' data files, celegans_repro_final.csv and the script's own celegans_datafinal.csv. Medium

The three that matter most:

  • P1 stops the script at line 23 (libray), but fixing it doesn’t make the script right.
  • P4 is the dangerous one: the author did try to remove impossible counts, the code looks fine, and the precedence slip quietly lets the −46 through.
  • P8 is this morning’s 9999: complete.cases() only drops NA, so every “not recorded” worm enters the models with 9,999 offspring.

Once the crashes (P1, P2, P5, and any missing packages from P3) are fixed, the script runs, and P4, P7, P8, P10 and P12 make its numbers wrong without a single error.

Quick check

filter(strain == "daf" | strain == "empty_vector" & total_offspring > 0) meets a daf worm with total_offspring of −46. Is the worm kept or dropped?

Kept. & binds more tightly than |, so R reads the filter as daf | (empty_vector & total_offspring > 0). The check only applies to empty_vector worms, so every daf worm is kept, including the one with −46 offspring.

Which filter does what the author intended (both strains, and only positive counts)?

%in% keeps both strains, and & total_offspring > 0 then applies to all of them. The second option is how R actually reads the original. The last one compares row by row against a recycled c('daf', 'empty_vector'), so it runs without an error (at most a recycling warning) and quietly drops about half the worms.

x <- c(250, NA, 9999). What does sum(complete.cases(x)) return?

2. complete.cases() only drops NA. 9999 is an ordinary number, so it counts as complete, which is exactly why P8 slips through.

Line 28 renames column 5 to total offspring (with a space). After write.csv() and read.csv(), what is the column called?

total.offspring. read.csv() cleans the header with make.names(), which turns the space into a dot. The script then asks for total_offspring, which does not exist.

True or false? In the original figure, geom_smooth(method = "lm") draws one line per diet across the two strains.

False. With a categorical x, each strain × diet group has only one x value, so there is no line to fit and geom_smooth() draws nothing.

Part 4: Fixing the script

⏱ ~30 minutes

Most of the twelve problems disappear when the script is rewritten as a plain, linear, well-commented analysis: relative paths, a documented sample, the sentinel handled, one model fitted and saved on purpose. No clever functions needed: a flat script a reviewer can read top to bottom is the easiest to check.

A corrected version

Here is ANALYSIS.R rewritten. It also slots into the project structure you built this morning: the cleaning happens in 01_data_cleaning.R, so this script reads the cleaned file and only analyses. Each numbered section names the problems (P1–P12) it resolves, and it uses the documented data-dictionary names (TO, B).

# analysis/02_analysis.R  -- corrected analysis script
# Author:  [your name]
# Date:    [today]
# Purpose: C. elegans total-offspring analysis -- daf-2 RNAi x diet
#
# Input:   data/processed/celegans_clean.csv   (produced by 01_data_cleaning.R)
# Output:  results/model_summary.csv
#          figures/offspring_by_strain.png
#          results/sessionInfo.txt
#
# Pre-specified model (as in the write-up, celegans_analysis.Rmd, on osf.io/jgeq9/):
#   TO ~ strain * diet + (1 | B)        TO = total offspring (a count)

# -- Packages: load only what is used --------------------------------- fixes P1, P3
library(tidyverse)    # readr, dplyr, ggplot2
library(lme4)         # glmer.nb
library(broom.mixed)  # tidy() for mixed models
library(here)         # project-relative paths -- fixes P2

# -- 1. Load the cleaned data ----------------------------------------- fixes P2, P8
# Cleaning -- including dropping the 9999 "not recorded" sentinel -- is done
# in 01_data_cleaning.R. This script only analyses; it never re-cleans.
dat <- read_csv(here("data", "processed", "celegans_clean.csv"),
                show_col_types = FALSE) |>
  mutate(
    strain = factor(strain, levels = c("empty_vector", "daf")),
    diet   = factor(diet),
    B      = factor(B)
  )

# -- 2. Select the analysis sample ------------------------------------ fixes P4, P7
# No worm is dropped here without a reason (P7): every exclusion is made,
# and logged, in 01_data_cleaning.R. Flagged values are kept there, marked
# flag_implausible, and left out here, in one visible line.
# Keep the two strains of interest AND require diet to be recorded.
# %in% plus a separate condition is the fix for P4: the original wrote
#   strain == "daf" | strain == "empty_vector" & total_offspring > 0
# which R reads as  daf | (empty_vector & count > 0)  -- not the intent.
# (Impossible counts such as -46 are now removed, and logged, in cleaning.)
dat <- dat |>
  filter(strain %in% c("empty_vector", "daf") & !is.na(diet)) |>
  # pre-specified: flagged values stay out until verified;
  # rerun without this line as a sensitivity check
  filter(!flag_implausible)

# -- 3. Fit ONE pre-specified model ----------------------------------- fixes P9, P10
# TO is a count, so a Gaussian lmer is the wrong family. Fit one
# negative-binomial GLMM (handles the overdispersion typical of brood
# counts) and report it -- no comparing across model classes.
m <- glmer.nb(TO ~ strain * diet + (1 | B), data = dat)

# -- 4. Diagnostics --------------------------------------------------- fixes P10
plot(m)                                   # residuals vs fitted
if (isSingular(m)) warning("Model is singular -- check the batch (B) random effect.")

# -- 5. Save the reported model --------------------------------------- fixes P12
write_csv(tidy(m, conf.int = TRUE),
          here("results", "model_summary.csv"))

# -- 6. Figure: categorical x, so show data + group means ------------- fixes P11
p <- ggplot(dat, aes(x = strain, y = TO, colour = diet)) +
  geom_jitter(width = 0.15, alpha = 0.3) +
  stat_summary(fun.data = mean_se, geom = "errorbar", width = 0.3) +
  stat_summary(fun = mean, geom = "point", size = 3) +
  labs(x = "Strain (RNAi)", y = "Total offspring", colour = "Diet") +
  theme_classic()

ggsave(here("figures", "offspring_by_strain.png"), p,
       width = 7, height = 5, dpi = 300)

# -- 7. Record the computational environment -------------------------- fixes P12
writeLines(capture.output(sessionInfo()),
           here("results", "sessionInfo.txt"))
Note

Notice what this rewrite does not do: it does not wrap every step in a bespoke function. For a script this size, a flat sequence of clearly commented blocks is easier to review than a set of custom functions, because the reviewer sees exactly what happens, in order, with nothing hidden behind a call. Reach for a function only when you genuinely repeat a block three or more times.

Tidy the project, not just the script

ANALYSIS.R reads its data from one folder and writes its outputs back to the same folder. Look at what is actually in that folder on the OSF page: the data files, ANALYSIS.R, an old_code.R, celegans_analysis.Rmd and its rendered .html, and five loose image files, all in one flat directory.

That is exactly the messy structure you saw in Part 4 of the reproducibility chapter, and the folder structure you built there fixes it. Three things a reviewer should flag:

  • old_code.R should not be there. It is a superseded earlier version. Dead code left in the project root invites a collaborator to run the wrong script. Move it to an archive/ folder, or, once the project is under version control, delete it: Git keeps the old version.
  • The five image files are loose. Generated outputs belong in figures/, produced by the code, not committed by hand next to the scripts.
  • There is no README. You built one this morning in the reproducibility chapter, and that same README.md belongs in the project root here. It is what lets a reviewer answer the Reported questions at all.

Re-using the structure you created in the reproducibility chapter (data/raw, data/processed, analysis/, figures/, results/) makes the project navigable and makes the Run check (“can I tell which script to run, and in what order?”) answerable at a glance.

Reviewing the whole archive: the SORTEE stages

The 4Rs are a lens for reviewing a script. The SORTEE Guidelines (Pick et al. 2026) provide the complementary lens for reviewing a whole archive (the data, the code and the metadata together) as six ordered Stages of Review:

The six SORTEE Stages of Review (Pick et al. 2026)
Stage Stage of review Goal it serves
1 Data are archived and adhere to the FAIR principles Data re-use
2 Archived data correspond to the data reported in the manuscript Data re-use
3 Code is archived and adheres to the FAIR principles Transparency
4 Archived code corresponds to the workflow reported in the manuscript Transparency
5 Archived code runs with the archived data Reproducibility
6 Results can be computationally reproduced by running the code Reproducibility

The stages build on each other: Stages 1–2 deliver data re-use, Stages 1–4 deliver transparency, and all six together deliver full computational reproducibility.

DCQC, the SORTEE Data and Code Quality Control Shiny app (https://github.com/SORTEE/DCQC), does not check anything automatically. It is a structured walk-through: it takes a reviewer (a journal data editor, or you, reviewing your own archive before submission) through these six stages in order, recording the outcome of each. Think of it as the counterpart, for the whole data-and-code package, of the 4Rs checklist you used on the script.

Note

What no tool can do for you. DCQC structures the review; it does not pass judgement. Stage 5 (“does the code run?”) and Stage 6 (“do the results reproduce?”) still require you to run the code. And the 4Rs Reliable question (does the code do what the analyst intended?) is the one neither DCQC nor an AI assistant can answer for you. That is the human reading you did in Part 3.

Part 5: Building the review habit

⏱ ~15 minutes

Setting up a code review group

Most code review never happens because no one organises it. Ivimey-Cook et al. (2023), drawing on their experience building SORTEE’s peer code review club, set out five practical considerations for getting a group off the ground. They aren’t novel, but they’re the ones that decide whether a group survives past meeting three or quietly dies.

  1. Start collaborating early. Review works best when it’s continuous, not a one-off pre-submission check. Build in regular sessions from project kickoff and use GitHub issues or pull requests to anchor discussion to specific lines rather than vague impressions.
  2. Set a clear goal for each session. “Learn together” and “find the bug in my analysis before I submit” need different time, different reviewers and different rules. Decide which one you’re doing before people show up.
  3. Normalise errors and make it judgement-free. There is no such thing as bad code (Barnes 2010) and there are usually multiple defensible ways to solve the same problem (Silberzahn et al. 2018; Gould et al. 2025). The fastest way to kill a group is to let it become a place where the most confident voice rewrites everyone else’s style.
  4. Mind the group size. Small (even 1-on-1) is better for focused review of specific code; larger groups work for general principles and discussion. Pick on purpose.
  5. Think about credit up front. A reviewer who catches a meaningful bug deserves more than a thank-you: MeRIT acknowledgement (Nakagawa et al. 2023) or co-authorship where the fix changes the conclusions. Agree the default before the first review, not after.
Tip

Plan your group (~5 min — post in Slack)

Without overthinking it, commit to specifics on the following five questions. Two-line answers are fine; the point is to write them down, because “we should review each other’s code” without specifics is a sentence that ages badly.

  1. Who: name 2–4 people you’d actually invite in the next month.
  2. What: readability/learning, or pre-submission error-checking? (Pick one for the first meeting.)
  3. When and where: cadence and platform (in-person, Zoom, async via GitHub).
  4. First case: whose code goes first, and what’s the explicit scope of that review (which of the four Rs)?
  5. Credit: what’s your default acknowledgement, and what triggers escalating to MeRIT or co-authorship?

When you’ve written your five, post the one you’re least sure about and we’ll workshop it briefly as a group.

Online lab culture

For groups working entirely online, the pull request model on GitHub provides the most practical structure for code review. The author opens a PR, writes a description explaining what the code does and why, and requests review. The reviewer comments on specific lines. Nothing merges until approved. We cover this in the GitHub session tomorrow.

Glossary

Term Definition
4Rs Reported, Run, Reliable, Reproducible — evaluation criteria for code review (Ivimey-Cook et al. 2023)
Reported Code matches the methods; packages and versions documented
Run Code executes from a clean session on any machine
Reliable Code does what the author intended; no silent errors
Reproducible Running the code produces the outputs stated in the paper
Operator precedence The order R applies operators; & binds tighter than |, so a | b & c means a | (b & c) — a frequent source of silent filter() bugs
Sentinel value A number used to encode a special meaning (e.g. 9999 = 'not recorded'); must be handled before any model is fitted
Count GLMM A generalised linear mixed model for count outcomes (Poisson or negative binomial); appropriate for offspring counts, unlike a Gaussian lmer
isSingular() lme4 function checking whether a model has converged to a singular fit (random-effect variance ~ 0)
SORTEE Stages of Review The SORTEE Guidelines' six-stage framework for reviewing an archive, from data archiving (Stage 1) to computational reproducibility (Stage 6)
DCQC SORTEE Data and Code Quality Control Shiny app; a structured walk-through of the six SORTEE Stages of Review — it organises a review, it does not automate one
Pull request GitHub mechanism for proposing changes; a natural structure for code review in online collaborative groups
