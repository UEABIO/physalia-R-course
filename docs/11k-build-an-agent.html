Build your own agent in R

Self-study: about 45 minutes, not part of the timed day.

All day you have worked with Claude Code. At its core it is a model, a harnessThe software around a model that keeps the conversation, sends it to the model, runs the tools the model asks for and sends back their results. Claude Code is a harness; so is a chat object made with ellmer. and a few toolsR functions (or other programs) that an agent may ask to have run, each described to the model by a name, a description and its arguments. The model only asks; the harness runs the tool on your computer and sends back the result. in a loop. On this page you build that loop yourself in R, in under 100 lines, with the ellmer package. Once you have built it, every control from Blocks 4 to 6 is something you can see in your own code: what Manual mode approves, what a deny rule blocks, and what leaves your machine.

The page follows the order of Hadley Wickham’s explainer What is an agent?: first a conversation, then a tool, then the loop. Joseph Barbier’s talk 50 lines of code to rebuild Claude Code in R builds the same kind of agent; the version here is our own.

Before you start

You need:

  • ellmer, which talks to Claude and runs the loop: install.packages("ellmer"). The agent also uses callr and fs, which the course install script includes.
  • An Anthropic API key from a Console account. A Claude Pro or Max subscription does not include API use. ellmer reads it from the environment variable ANTHROPIC_API_KEY. Open your user-level .Renviron with usethis::edit_r_environ(), add the line ANTHROPIC_API_KEY=your-key-here, save, and restart R.
  • The key kept out of every repository. Your user-level .Renviron is outside your projects; never paste the key into a script. The workshop repository’s .gitignore lists .Renviron, and its deny rule Read(/.Renviron) stops Claude Code reading a project copy (Block 6).

Every request costs money. chat$get_cost() shows what a conversation has cost so far, so check it after each task. The code names its model explicitly, claude-opus-5-5, so your AI-use log can record it; you can swap in another Claude model ID.

A conversation is turns

library(ellmer)

chat <- chat_anthropic(model = "claude-opus-5-5")
chat$chat("Tell me a joke about R.")
chat$chat("Explain why it is funny, in one sentence.")
chat

Printing chat shows the conversation as a list of turnsOne message in a conversation with a model: either yours (the user turn) or the model’s reply (the assistant turn). Tool results go back to the model inside a user turn., in pairs: your user turn, then the model’s assistant turn. chat$get_turns() returns them as R objects.

The second question works because of the harness, not the model. The model keeps nothing between requests, so for each new question ellmer sends the whole conversation so far. That is why a long conversation costs more per question: you pay for every tokenThe unit a model reads and writes, roughly three-quarters of an English word. Providers charge per token, and because the whole conversation is re-sent with each request, a long conversation costs more per question. of it again. It is also the context window from Block 1, seen from the inside.

A tool is an R function, run on your computer

A model can only produce text. A tool lets it ask for something to be done:

today <- tool(
  function() format(Sys.Date()),
  name = "today",
  description = "Get today's date."
)

chat <- chat_anthropic(model = "claude-opus-5-5")
chat$register_tool(today)
chat$chat("How many days until 25 December?")

The model never sees your function, only its name and description, so the description is everything it knows about the tool. When it wants the date, its reply is not an answer but a request: “call today with no arguments”. ellmer runs today() on your computer and sends the result back in a new user turn. The model then answers, using the date it was given.

That is two roundsOne request to the model and its reply. A single question can take several rounds when the model asks for tools before it answers. for one question: one request that ended in a tool request, and one that ended in the answer. chat$get_rounds() shows them.

The loop, with no model at all

You can run this section without an API key. It replaces the model with a pretend one that follows a script, so that you can see the loop the harness runs. Each pass of repeat is one round.

# the tools, as plain R functions
tools <- list(
  n_rows = function(name) {
    nrow(get(name, envir = as.environment("package:datasets")))
  }
)

# a pretend model: asks for a tool until it has two results, then answers
pretend_model <- function(turns) {
  results <- Filter(function(t) t$role == "tool result", turns)
  if (length(results) == 0) {
    list(role = "assistant", tool = "n_rows", args = list(name = "mtcars"))
  } else if (length(results) == 1) {
    list(role = "assistant", tool = "n_rows", args = list(name = "iris"))
  } else {
    list(role = "assistant",
         text = paste("iris has", results[[2]]$text, "rows and mtcars has",
                      results[[1]]$text, "so iris has more."))
  }
}

# the harness: send the conversation, run any tool asked for, repeat
question <- "Which has more rows, mtcars or iris?"
turns <- list(list(role = "user", text = question))
repeat {
  reply <- pretend_model(turns)
  turns <- c(turns, list(reply))
  if (is.null(reply$tool)) break # no tool asked for: this is the answer
  result <- do.call(tools[[reply$tool]], reply$args)
  turns <- c(turns, list(list(role = "tool result", text = result)))
}

for (t in turns) {
  what <- if (is.null(t$tool)) t$text else
    paste0("call ", t$tool, "(", t$args, ")")
  cat(sprintf("%-12s %s\n", t$role, what))
}
user         Which has more rows, mtcars or iris?
assistant    call n_rows(mtcars)
tool result  32
assistant    call n_rows(iris)
tool result  150
assistant    iris has 150 rows and mtcars has 32 so iris has more.

Three things to notice:

  • The model only asks. do.call() in the harness is the only line that does anything to your computer. Every control in the course acts at that line: Manual mode asks you before it runs, a deny rule refuses it, a hook inspects it.
  • Results go back to the model. Whatever a tool returns joins the conversation, and the conversation is sent to the provider. That is Block 4’s disclosure route: a tool that reads a data file sends that data.
  • The model decides when to stop. The loop ends when a reply asks for no tool. A real model can also loop for longer than you expected, which is why a real harness has limits and a stop key.

In the real API the tool result goes back inside a user turn; ellmer does that for you.

What an agent is

An agentAn assistant that can read across a project’s files and, depending on its permission mode, edit them and run commands, such as Claude Code. An agent acts; a chat window only advises. is a model in a harness, calling tools in a loop. Read tools let it look around: list files, read them. Write tools let it change things: edit a file, run code. With both, it can explore, make a change, check the result and try again, which is what Claude Code did for you all day.

The write tools are where the risk is. Wickham’s article warns with a tool that deletes files: give an agent one without confirmation and it may use it.

Build a mini coding agent

The agent below has four tools and three safeguards. Download it and save it outside your workshop repository, for example in your Downloads folder, so the agent cannot edit its own rules, just as Block 6 protects .claude/settings.json.

The walkthrough below explains each part of the file.

TipReference: the full mini_agent.R 
# mini_agent.R ----
# A small coding agent: Claude, four tools, and the loop ellmer runs for you.
# Source it from the root of your workshop repository, then talk to `chat`.
library(ellmer)

# the agent's own deny rule: stay inside the project, out of data/raw/,
# and away from credentials files
inside_project <- function(path) {
  root <- fs::path_abs(getwd())
  full <- fs::path_norm(fs::path_abs(path, start = root))
  inside <- full == root || fs::path_has_parent(full, root)
  if (!inside || fs::path_has_parent(full, fs::path(root, "data", "raw")) ||
      fs::path_file(full) %in% c(".Renviron", ".env")) {
    stop("Refused: ", path, " is outside the project, under data/raw/, ",
         "or a credentials file")
  }
  full
}

# read tools: they observe the project and change nothing
list_files <- tool(
  function(path = ".") list.files(inside_project(path), recursive = TRUE),
  name = "list_files",
  description = "List the files in a folder of the project.",
  arguments = list(path = type_string("A folder, relative to the project.")),
  annotations = tool_annotations(read_only_hint = TRUE)
)
read_file <- tool(
  function(path) {
    paste(readLines(inside_project(path), warn = FALSE), collapse = "\n")
  },
  name = "read_file",
  description = "Read a text file in the project.",
  arguments = list(path = type_string("A file, relative to the project root.")),
  annotations = tool_annotations(read_only_hint = TRUE)
)

# write tools: they change the project, so they need your approval
write_file <- tool(
  function(path, content) {
    writeLines(content, inside_project(path))
    paste("Wrote", path)
  },
  name = "write_file",
  description = "Replace the whole contents of a text file in the project.",
  arguments = list(
    path = type_string("A file, relative to the project root."),
    content = type_string("The complete new contents of the file.")
  )
)
run_r <- tool(
  function(code) {
    out <- callr::r(function(code) utils::capture.output(
      tryCatch(source(exprs = parse(text = code), print.eval = TRUE),
               error = function(e) cat("Error:", conditionMessage(e), "\n"))
    ), list(code = code))
    paste(utils::head(out, 60), collapse = "\n") # keep long output short
  },
  name = "run_r",
  description = "Run R code in a fresh R session; return its printed output.",
  arguments = list(code = type_string("The R code to run."))
)

# Manual mode: show every write or run request, and ask before it happens
ask_first <- function(request) {
  if (request@name %in% c("write_file", "run_r")) {
    cat("\nThe agent wants to call", request@name, "with:\n")
    for (arg in names(request@arguments)) {
      cat("--", arg, "--\n", request@arguments[[arg]], "\n")
    }
    # outside an interactive session there is no one to ask, so refuse
    if (!interactive() || utils::menu(c("Yes", "No"), title = "Allow it?") != 1) {
      tool_reject()
    }
  }
}

chat <- chat_anthropic(
  model = "claude-opus-5-5",
  system_prompt = paste(
    "You are a careful R assistant working in this project.",
    "Read files before you change them, and check your work by running it.",
    "Never touch data/raw/. Say what you changed,",
    "and stop when the task is done."
  )
)
chat$register_tools(list(list_files, read_file, write_file, run_r))
chat$on_tool_request(ask_first)

Each part matches something you met during the day:

  • Read and write tools. list_files() and read_file() only observe; tool_annotations(read_only_hint = TRUE) labels them, but a label is only a hint and enforces nothing. write_file() and run_r() change things.
  • inside_project() is the agent’s deny rule. Every file tool calls it, and it refuses paths outside the project, under data/raw/, or to a credentials file (.Renviron or .env, in any folder). An error in a tool does not stop the agent: ellmer sends the error message back to the model, which can try something else.
  • ask_first() is Manual mode. chat$on_tool_request() runs it before every tool call. Read calls go straight through; for a write or a run it prints the arguments, the file contents or the code, and calls tool_reject() unless you choose Yes.
  • run_r() uses a fresh R session. callr::r() runs the code in a new R process, so it cannot change the objects in yours, and only the first 60 lines of output go back to the model.
  • The system prompt is its AGENTS.md. The system promptStanding instructions sent with every request, before the conversation itself. It does the job an instruction file such as AGENTS.md does for Claude Code. is sent with every request, and like an instruction file it is only a request.

run_r() shows the limit Block 6 found in deny rules. inside_project() guards the file tools, but R code run by run_r() can write anywhere, data/raw/ included. Only your approval stands in the way, which is why you read the code before you choose Yes, and why the raw-data checksum test checks the result whatever route a change took.

Run your agent (20 minutes)

Start state: your workshop repository open in RStudio or Positron, committed and clean in the Git pane. If scripts/explore_voles.R already has a mass_change_g line from Block 4, delete that line and commit first. The working directory must be the repository’s root, as it is when you open the project.

1. Load the agent. In the R console, with the path to where you saved it:

source("~/Downloads/mini_agent.R")

2. Give it the task.

chat$chat(paste(
  "Add a mass_change_g column (mass_post_g minus mass_pre_g) to the voles",
  "data in scripts/explore_voles.R, then run",
  "testthat::test_file('tests/test_explore.R') to check it."
))

3. Watch and decide. The read calls run without asking. For each write_file or run_r request, read what it prints, then choose Yes only if you would have written it yourself. Try choosing No once and watch how the agent responds.

4. Look inside. In the console:

chat                # the turns, with tokens and cost
chat$get_rounds()   # one entry per request to the model
chat$get_cost()

5. Check its work. Open the Git pane and read the diff of explore_voles.R. Then restart R (Session → Restart R) and run the test yourself, as in checking work:

testthat::test_file(here::here("tests", "test_explore.R"))

6. Record it. Add a line to docs/ai-log.md, for example:

2026-10-22; mini agent (ellmer, claude-opus-5-5); added mass_change_g; kept after reading the diff and running the test

You are done when the test passes when you run it yourself, the Git pane shows only the change you approved, and you can say how many rounds the task took and what it cost.

If it goes wrong: if the agent changed something you did not want, revert the file in the Git pane. If chat_anthropic() reports a missing key, check Sys.getenv("ANTHROPIC_API_KEY") != "" and restart R after editing .Renviron. If the agent refuses a path you expected it to reach, check getwd() is the repository’s root.

What Claude Code adds

Your mini agent Claude Code
ask_first() and tool_reject() Manual mode (default) and the other permission modes
inside_project() Deny rules in .claude/settings.json, such as Read(/.Renviron)
The system prompt AGENTS.md, read at the start of each session
run_r() in a fresh R session with callr::r() Commands it runs in the Terminal; you check results in a fresh R session
get_turns(), get_rounds(), get_cost() The conversation itself, and the model shown above the prompt
Git Git

Claude Code also has what this agent lacks: plan mode, hooks, skills, compaction of long conversations, many more tools, and far more checks around each one. Building the small version is not a reason to use it for real work. It is a way to understand what the big one is doing.

NoteCheck · Reproduce · Record
  • You can now: explain an agent as a model, a harness and tools in a loop, and build one in R, trusted because you wrote every line that touches your files, and a test you did not write decides whether its change is right.
  • Check: every write and every run is shown to you before it happens; the Git pane shows what changed; the test runs in a fresh R session.
  • Reproduce: run_r() runs in a fresh R session, so the agent’s checks do not depend on what is loaded in yours.
  • Record: chat$get_turns() is the full record of what was sent and received; your AI-use log records the tool, model and what you kept.

Going further (not covered live)

This material is not covered in the live session. Work through it afterwards if it is useful to you.

TipAdd a run_tests tool

Replace general-purpose run_r() for checking with a tool that can only run the project’s tests, function() testthat::test_dir("tests") run through callr::r(). A narrow tool needs less approval than a general one: you might let it through without asking, and keep asking for run_r().

TipA restricted mode

Change ask_first() so it asks before every call, reads included. You then see every file the agent wants to read before it is sent to the provider, which is the habit Block 4 recommends near confidential data.

TipPackages that do more
  • btw gives ellmer agents ready-made tools for R: package documentation, your live session’s objects and your project’s files.
  • mcptools connects R to the Model Context Protocol, so R functions can be tools for other assistants, including Claude Code.
TipAnother provider

ellmer has a chat_*() function for each provider it supports, and the tools and loop stay the same. Tool calling can be much less reliable with small local models, so start with a hosted model.

Glossary

term definition
agent An assistant that can read across a project's files and, depending on its permission mode, edit them and run commands, such as Claude Code. An agent acts; a chat window only advises.
harness The software around a model that keeps the conversation, sends it to the model, runs the tools the model asks for and sends back their results. Claude Code is a harness; so is a chat object made with ellmer.
round One request to the model and its reply. A single question can take several rounds when the model asks for tools before it answers.
system prompt Standing instructions sent with every request, before the conversation itself. It does the job an instruction file such as AGENTS.md does for Claude Code.
token The unit a model reads and writes, roughly three-quarters of an English word. Providers charge per token, and because the whole conversation is re-sent with each request, a long conversation costs more per question.
tools R functions (or other programs) that an agent may ask to have run, each described to the model by a name, a description and its arguments. The model only asks; the harness runs the tool on your computer and sends back the result.
turn One message in a conversation with a model: either yours (the user turn) or the model's reply (the assistant turn). Tool results go back to the model inside a user turn.
