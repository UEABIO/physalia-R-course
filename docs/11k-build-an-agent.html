Block 6: Build your own agent in R

You build the two parts of an agent yourself, a conversation and a tool, then run a complete agent on a real task and approve every step it takes. After this, every control from Blocks 3 to 5 is something you can see in code.

⏱ ~45 minutes · Start on main, Git pane clean, with your API key saved as AGENT_ANTHROPIC_KEY (setup). Claude Code is not used in this block.

NoteThis block’s files, and how it fits

You stay in your workshop repository, on main, straight after lunch. Claude Code is set aside: you use an agent you can read line by line, and give it the translation that the shipped tests/test_translation.R checks. Nothing later in the day uses its output, so if time is short your instructor may run Task 2 on screen while you decide each approval in the chat.

Before you start. ellmer, the package that talks to Claude and runs the loop, is pinned in your repository’s renv.lock, so renv::restore() installed it; never run install.packages() inside the project. Your key comes from an Anthropic Console account, separate from a Claude subscription, and lives in your user-level .Renviron, outside every repository. Every request costs a little; Task 2 shows you how much the agent used.

The page follows the order of Hadley Wickham’s explainer What is an agent?: a conversation, then a tool, then the loop. Joseph Barbier’s talk 50 lines of code to rebuild Claude Code in R builds the same kind of agent; the version here is our own.

Task 1: a conversation, then a tool

Talk to a model, then give it a tool (8 minutes)

Goal: see what one request to a model is, and what a tool request is, so that nothing your agent does in Task 2 is a surprise.

1. Have a conversation. In the R console:

library(ellmer)

key <- function() Sys.getenv("AGENT_ANTHROPIC_KEY")
chat <- chat_anthropic(model = "claude-sonnet-5-5", credentials = key)
chat$chat("Tell me a joke about R.")
chat$chat("Explain why it is funny, in one sentence.")
chat

Printing chat shows the conversation as turnsOne message in a conversation with a model: either yours (the user turn) or the model’s reply (the assistant turn). Tool results go back to the model inside a user turn.. The second question works only because ellmer sends the whole conversation so far with each request: the model keeps nothing between requests. That is the context window from Block 1, and why a long conversation costs more per question.

2. Give it a tool. A tool is an R function the model may ask you to run:

today <- tool(
  function() format(Sys.Date()),
  name = "today",
  description = "Get today's date."
)

chat <- chat_anthropic(model = "claude-sonnet-5-5", credentials = key)
chat$register_tool(today)
chat$chat("How many days until 25 December?")
chat

The model sees only the tool’s name and description. Its first reply is a request, “call today”; ellmer runs today() on your computer and sends the result back; then the model answers. That is two requestsOne call to the model, with the whole conversation so far, and its reply. A single question can take several requests when the model asks for tools before it answers. for one question.

You are done when you can point, in the printed chat, to the tool request and to the tool result, and say which of them ran on your computer.

If it goes wrong: if the first chat$chat() reports a missing or invalid key, check Sys.getenv("AGENT_ANTHROPIC_KEY") != "", and restart R after editing .Renviron.

The loop

An agentAn assistant that can read across a project’s files and, depending on its permission mode, edit them and run commands, such as Claude Code. An agent acts; a chat window only advises. repeats that exchange: the harness sends the conversation, runs any tool the model asks for, adds the result, and sends it all again, until a reply asks for no tool. Every control in this course acts on one of three facts:

  • The model only asks. The harness runs each tool on your computer, so that is where Manual mode asks you, a deny rule refuses, and a hook inspects.
  • Results go back to the model. A tool that reads a data file sends that data to the provider: Block 3’s disclosure route.
  • The model decides when to stop. It can loop longer than you expect, which is why a real harness has limits and a stop key.
TipHow it works: the loop with no model at all

This code runs without an API key. It replaces the model with a pretend one that follows a script; each pass of repeat is one request.

# the tools, as plain R functions
tools <- list(
  n_rows = function(name) {
    nrow(get(name, envir = as.environment("package:datasets")))
  }
)

# a pretend model: asks for a tool until it has two results, then answers
pretend_model <- function(turns) {
  results <- Filter(function(t) t$role == "tool result", turns)
  if (length(results) == 0) {
    list(role = "assistant", tool = "n_rows", args = list(name = "mtcars"))
  } else if (length(results) == 1) {
    list(role = "assistant", tool = "n_rows", args = list(name = "iris"))
  } else {
    list(role = "assistant",
         text = paste("iris has", results[[2]]$text, "rows and mtcars has",
                      results[[1]]$text, "so iris has more."))
  }
}

# the harness: send the conversation, run any tool asked for, repeat
question <- "Which has more rows, mtcars or iris?"
turns <- list(list(role = "user", text = question))
repeat {
  reply <- pretend_model(turns)
  turns <- c(turns, list(reply))
  if (is.null(reply$tool)) break # no tool asked for: this is the answer
  result <- do.call(tools[[reply$tool]], reply$args)
  turns <- c(turns, list(list(role = "tool result", text = result)))
}

for (t in turns) {
  what <- if (is.null(t$tool)) t$text else
    paste0("call ", t$tool, "(", t$args, ")")
  cat(sprintf("%-12s %s\n", t$role, what))
}
user         Which has more rows, mtcars or iris?
assistant    call n_rows(mtcars)
tool result  32
assistant    call n_rows(iris)
tool result  150
assistant    iris has 150 rows and mtcars has 32 so iris has more.

do.call() is the only line that does anything to your computer: that is where Manual mode, deny rules and hooks act. In the real API the tool result goes back inside a user turn; ellmer does that for you.

Your agent: agent/mini_agent.R

Your repository ships a complete agent built from the same parts, about 120 lines. Your instructor walks through it; each part matches something from this morning:

  • Four tools. list_files() and read_file() look around; write_file() and run_r() change things.
  • inside_project() is its deny rule. It may read inside the project, except raw data and credentials files, and write only under scripts/, so it cannot edit its checks in tests/ or its own rules in agent/.
  • ask_first() is Manual mode. Reads go straight through; every write and every run is shown to you first, and refused unless you choose Yes.
  • The system prompt is its instruction file. It is not given your AGENTS.md (it could still open the file, like any other), and like AGENTS.md its prompt is only a request.

run_r() shows the gap Block 5 found: R code can write anywhere, data/raw/ included, and read anything you can, your .Renviron included. Only your approval stands in the way, which is why you read the code before you choose Yes; afterwards the Git pane shows any change.

TipReference: the full agent/mini_agent.R 
# agent/mini_agent.R ----
# A small coding agent: Claude, four tools, and the loop ellmer runs for you.
# Load it from your workshop repository with
#   source(here::here("agent", "mini_agent.R"))
# then talk to `chat`.
library(ellmer)

# the model: "claude-opus-5-5" is a larger model, at a higher price per token
model <- "claude-sonnet-5-5"

# your API key, from the AGENT_ANTHROPIC_KEY line in your user-level .Renviron;
# it has its own name so that Claude Code never offers to use it
agent_key <- function() Sys.getenv("AGENT_ANTHROPIC_KEY")
if (agent_key() == "") {
  stop("No AGENT_ANTHROPIC_KEY found: add it with usethis::edit_r_environ(), ",
       "then restart R.")
}

# the agent's own permission rules: it may read inside the project, except raw
# data and credentials files, and it may write only under scripts/ ----
root <- here::here()
inside_project <- function(path, write = FALSE) {
  full <- fs::path_norm(fs::path_abs(path, start = root))
  allowed <- (full == root || fs::path_has_parent(full, root)) &&
    !fs::path_has_parent(full, fs::path(root, "data", "raw")) &&
    !fs::path_file(full) %in% c(".Renviron", ".env")
  if (write) {
    allowed <- allowed && fs::path_has_parent(full, fs::path(root, "scripts"))
  }
  if (!allowed) {
    stop("Refused: ", path, if (write) {
      " (the agent may write only under scripts/)"
    } else {
      " is outside the project, under data/raw/, or a credentials file"
    })
  }
  full
}

# read tools: they observe the project and change nothing ----
list_files <- tool(
  # one folder at a time, at most 100 names: a recursive listing would include
  # every package installed in renv/, and all of it would be sent to the model
  function(path = ".") utils::head(list.files(inside_project(path)), 100),
  name = "list_files",
  description = "List the files and folders in one folder of the project.",
  arguments = list(path = type_string("A folder, relative to the project root.")),
  annotations = tool_annotations(read_only_hint = TRUE)
)
read_file <- tool(
  function(path) {
    lines <- readLines(inside_project(path), warn = FALSE)
    paste(utils::head(lines, 300), collapse = "\n") # keep long files short
  },
  name = "read_file",
  description = "Read a text file in the project.",
  arguments = list(path = type_string("A file, relative to the project root.")),
  annotations = tool_annotations(read_only_hint = TRUE)
)

# write tools: they change the project, so they need your approval ----
write_file <- tool(
  function(path, content) {
    writeLines(content, inside_project(path, write = TRUE))
    paste("Wrote", path)
  },
  name = "write_file",
  description = "Replace the whole contents of a text file under scripts/.",
  arguments = list(
    path = type_string("A file under scripts/, relative to the project root."),
    content = type_string("The complete new contents of the file.")
  )
)
run_r <- tool(
  function(code) {
    out <- callr::r(function(code) utils::capture.output(
      tryCatch(source(exprs = parse(text = code), print.eval = TRUE),
               error = function(e) cat("Error:", conditionMessage(e), "\n"))
    ), list(code = code))
    paste(utils::head(out, 60), collapse = "\n") # keep long output short
  },
  name = "run_r",
  description = "Run R code in a fresh R session; return its printed output.",
  arguments = list(code = type_string("The R code to run."))
)

# Manual mode: show every write or run request, and ask before it happens ----
ask_first <- function(request) {
  if (request@name %in% c("write_file", "run_r")) {
    cat("\nThe agent wants to call", request@name, "with:\n")
    for (arg in names(request@arguments)) {
      cat("--", arg, "--\n", request@arguments[[arg]], "\n")
    }
    # outside an interactive session there is no one to ask, so refuse
    if (!interactive() || utils::menu(c("Yes", "No"), title = "Allow it?") != 1) {
      tool_reject()
    }
  }
}

chat <- chat_anthropic(
  model = model,
  credentials = agent_key,
  system_prompt = paste(
    "You are a careful R assistant working in this project.",
    "Read files before you change them, and check your work by running it.",
    "Write files only under scripts/; never edit tests/ or data/raw/.",
    "Code you write must work in a fresh R session, so load packages with",
    "library() or call them with pkg::. Say what you changed, and stop when",
    "the task is done."
  )
)
chat$register_tools(list(list_files, read_file, write_file, run_r))
chat$on_tool_request(ask_first)

# how many requests the agent has sent to the model: one per assistant turn ----
count_requests <- function() {
  sum(vapply(chat$get_turns(), function(turn) turn@role == "assistant", logical(1)))
}

list_files() lists one folder and at most 100 names, and read_file() returns at most 300 lines: a recursive listing would include every package in renv/, and all of it would be sent to the model. An error in a tool does not stop the agent: ellmer sends the error message back to the model, which can try something else. run_r() uses a fresh R session (callr::r()), so it cannot change the objects in yours, and only the first 60 lines of its output go back to the model.

Task 2: run your agent

Run your agent (20 minutes)

Goal: watch your own agent write, test and fix a translation while you approve every write and run, so that you see exactly where Manual mode and a deny rule act.

Start state: main, Git pane clean, R’s working directory at the repository’s root (as it is when you open the project).

1. Load the agent. Nothing is sent to the model yet:

source(here::here("agent", "mini_agent.R"))

2. Give it the task. The original base R code is legacy_rate_summary() in tests/test_translation.R, which also checks the translation:

chat$chat(paste(
  "Write a function summarise_rate_tidy(data) in scripts/functions/summaries.R",
  "whose output matches legacy_rate_summary() in tests/test_translation.R.",
  "Use dplyr and the native pipe; it must work in a fresh R session.",
  "Write only that file, and no tests. Then run",
  "testthat::test_file('tests/test_translation.R') with run_r, and fix the",
  "function until the test passes."
))

3. Decide each request. Reads run without asking. For a write_file or run_r request, read what it prints and choose Yes only for a write to scripts/functions/summaries.R or a run of the test. Refuse the first test run on purpose: the agent stops and explains. Then let it continue:

chat$chat("Go ahead and run the test.")

4. Look inside.

chat               # every turn: your prompt, its tool requests, the results
count_requests()   # how many requests it sent to the model
chat$get_tokens()  # the tokens it sent and received

5. Check its work yourself. The agent’s “the test passes” is a claim. Read the diff of scripts/functions/summaries.R in the Git pane, then restart R (Session → Restart R) and run:

testthat::test_dir(here::here("tests"))

6. Record and commit. Add a line to docs/ai-log.md with today’s date, for example 2026-10-22; mini agent (ellmer, claude-sonnet-5-5); translated the rate summary to tidyverse; kept after reading the diff and running the tests, then commit summaries.R and the log.

aggregate() with a formula silently drops the animal whose metabolic_rate_post is missing, so the original’s mean and count leave it out. A literal tidyverse translation keeps it: an NA mean and a count one too high. The test compares against the original, so the agent had to match that behaviour, and if it read the test it probably did so without comment. The test checks “the same as the original”, not “correct”: Block 8 returns to that difference.

You are done when test_translation.R passes in your own run, the Git pane showed only summaries.R and your log changed, you can say how many requests and tokens the task took, and both are committed.

If it goes wrong:

  • The agent loops or goes off course: answer No, then steer it with chat$chat("…"), or source() the file again to start a new conversation.
  • A refused path you expected to work: check getwd() is the repository’s root.
  • An unwanted change: Revert it in the Git pane.
TipWhat did it cost?

chat$get_cost() turns the tokens into money when ellmer knows the model’s price. If it shows NA, run ellmer::models_update_prices() once to refresh ellmer’s price list, or multiply the tokens from chat$get_tokens() by the prices on Anthropic’s pricing page. claude-opus-5-5, set at the top of mini_agent.R, is a larger model at a higher price per token.

What Claude Code adds

Your mini agent Claude Code
ask_first() and tool_reject() Manual mode (default) and the other permission modes
inside_project(): writes only under scripts/ Deny rules in .claude/settings.json, such as Edit(/data/raw/**)
The system prompt AGENTS.md, read at the start of each session
run_r() in a fresh R session Commands it runs in the Terminal; you check results in a fresh R session
chat, count_requests(), chat$get_tokens() The conversation itself, and the model shown in Claude Code
Git Git

Claude Code adds plan mode, hooks, skills, compaction of long conversations, many more tools and far more checks around each one. Building the small version is a way to understand the big one, not a reason to use it for real work. In Block 7 you hand Claude Code a much bigger job under the same controls.

NoteCheck · Reproduce · Record
  • You can now: explain an agent as a model, a harness and tools in a loop, and run one in R, trusted because you can read every line that touches your files, and a test you did not write decides whether its change is right.
  • Check: every write and every run is shown to you before it happens; the Git pane shows what changed; the test runs in a fresh R session.
  • Reproduce: run_r() runs in a fresh R session, so the agent’s checks do not depend on what is loaded in yours.
  • Record: chat holds the full record of what was sent and received; your AI-use log records the tool, the model and what you kept.

Going further (not covered live)

This material is not covered in the live session. Work through it afterwards if it is useful to you.

TipAdd a run_tests tool

Replace general-purpose run_r() for checking with a tool that can only run the project’s tests, function() testthat::test_dir("tests") run through callr::r(). A narrow tool needs less approval than a general one: you might let it through without asking, and keep asking for run_r().

TipA restricted mode

Change ask_first() so it asks before every call, reads included. You then see every file the agent wants to read before it is sent to the provider, which is the habit Block 3 recommends near confidential data.

TipPackages that do more
  • btw gives ellmer agents ready-made tools for R: package documentation, your live session’s objects and your project’s files.
  • mcptools connects R to the Model Context Protocol, so R functions can be tools for other assistants, including Claude Code.
TipAnother provider

ellmer has a chat_*() function for each provider it supports, and the tools and loop stay the same. Tool calling can be much less reliable with small local models, so start with a hosted model.

Glossary

term definition
agent An assistant that can read across a project's files and, depending on its permission mode, edit them and run commands, such as Claude Code. An agent acts; a chat window only advises.
request One call to the model, with the whole conversation so far, and its reply. A single question can take several requests when the model asks for tools before it answers.
turn One message in a conversation with a model: either yours (the user turn) or the model's reply (the assistant turn). Tool results go back to the model inside a user turn.
