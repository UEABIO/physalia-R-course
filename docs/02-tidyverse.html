Block 2: Getting more out of tidyverse

Roughly 55 minutes. We assume the core verbs are familiar and spend the time on the patterns that remove repetition: working across many columns, reshaping, and the nesting idea that the afternoon depends on.

Throughout this block we use a cleaned copy of the raw file you saved in Block 1, data/raw/penguins_raw.csv. The palmerpenguins package also has a ready-cleaned version, palmerpenguins::penguins, but here you do the cleaning yourself, so you can see every step (Which penguins?):

library(tidyverse)
library(here)
library(janitor)

# the raw file you saved in Block 1
penguins_raw <- readr::read_csv(here("data", "raw", "penguins_raw.csv"),
                                show_col_types = FALSE)

penguins_clean <- penguins_raw |>
  janitor::clean_names() |>
  # match the names used in palmerpenguins::penguins
  dplyr::rename(bill_length_mm = culmen_length_mm,
                bill_depth_mm  = culmen_depth_mm) |>
  # "Adelie Penguin (Pygoscelis adeliae)" -> "Adelie"
  dplyr::mutate(species = stringr::word(species, 1)) |>
  tidyr::drop_na(body_mass_g, flipper_length_mm, species)

A 5-minute refresher (diagnostic, not teaching)

Before the new material, a quick check that the foundation is solid. Predict the output of each line before running it, then run it.

penguins_clean |> dplyr::filter(body_mass_g > 5000)               # which rows?
penguins_clean |> dplyr::filter_out(body_mass_g > 5000)           # which rows? (Hint this is a new function)
penguins_clean |> dplyr::select(species, body_mass_g)             # which columns?
penguins_clean |> dplyr::mutate(mass_kg = body_mass_g / 1000)     # new column?
penguins_clean |> dplyr::summarise(m = mean(body_mass_g, na.rm = TRUE), .by = species)

If those five lines hold no surprises, you have everything you need for the day. Note the modern .by = species argument to summarise(): it groups for that one operation and returns an ungrouped result, which avoids the classic forgotten ungroup() bug.

Working across many columns with across()

A recurring issue in analysis scripts is the same operation written out once per column:

penguins_clean |>
  dplyr::summarise(
    mean_body_mass      = mean(body_mass_g, na.rm = TRUE),
    mean_flipper_length = mean(flipper_length_mm, na.rm = TRUE),
    .by = species
  )

across() says “apply this function to these columns” in one place. It works only inside a dplyr verb, and takes three arguments worth knowing: .cols (which columns, using tidy-selection), .fns (the function to apply), and .names (how to name the results).

penguins_clean |>
  dplyr::summarise(
    dplyr::across(
      .cols  = where(is.numeric),
      .fns   = \(x) mean(x, na.rm = TRUE),
      .names = "mean_{.col}"
    ),
    .by = species
  )

Two modern points. The function is written as \(x) mean(x, na.rm = TRUE), the R 4.1 anonymous-function shorthand, rather than the older ~ mean(.x, na.rm = T) formula-lambda you will still see in the wild. And na.rm = TRUE is spelled out; T and F are ordinary variables that can be reassigned, so they are best avoided in code you intend to keep.

The same pattern coerces a set of columns to factors:

penguins_clean |>
  dplyr::mutate(
    dplyr::across(.cols = c(species, island), 
    .fns = as.factor)
  ) |>
  dplyr::select(where(is.factor)) |>
  dplyr::glimpse()

across()’s row-wise cousins: if_any() and if_all()

To filter rows on a condition applied across several columns, use if_any() (the condition holds for at least one of the columns) or if_all() (it holds for all of them).

# Keep rows where ALL numeric measurements are present (no NA)
penguins_clean |>
  dplyr::filter(
    dplyr::if_all(.cols = where(is.numeric), .fns = \(x) !is.na(x))
  )
Tip

The line above reads slightly backwards at first. if_all() asks whether all the chosen columns satisfy “is not NA”. Try swapping if_all for if_any, and try removing the !, and predict each result before running it.

Activity: one summary, every numeric column

One summary, every numeric column

Write a single summarise() that returns, for each species, both the mean and the standard deviation of every numeric column, with names like mean_body_mass_g and sd_body_mass_g. Hint: .fns can be a named list of functions.

penguins_clean |>
  dplyr::summarise(
    dplyr::across(
      .cols  = where(is.numeric),
      .fns   = list(mean = \(x) mean(x, na.rm = TRUE),
                    sd   = \(x) sd(x, na.rm = TRUE)),
      .names = "{.fn}_{.col}"
    ),
    .by = species
  )

When .fns is a named list, {.fn} in .names expands to each function’s name. This replaces a quarter-page of repeated mean_x =, sd_x = lines with four lines that cannot drift out of step with each other.

A note on factors

Categorical variables are often better as factors than as character strings, and forcats (part of the tidyverse) provides verbs for managing their levels.

penguins_clean |>
  dplyr::mutate(
    # collapse rare levels into "Other", keeping the 2 most frequent
    island_lumped = forcats::fct_lump_n(island, n = 2),
    # order species by their mean body mass, for sensible plot ordering
    species       = forcats::fct_reorder(species, body_mass_g, .fun = mean,
                                         na.rm = TRUE)
  )

fct_reorder() is the one to remember: it reorders a factor’s levels by a summary of another variable, which is what you almost always want for an ordered axis or legend.

Reshaping with pivot_longer() and pivot_wider()

Tidy data has one variable per column and one observation per row. Data collected in the field often violates this, most commonly by spreading one variable across several columns. Consider weekly observation counts:

peng_obs <- tibble::tibble(
  penguin_id = c("N15A1", "N15A2", "N18A1", "N71A2"),
  wk1 = c(1, 2, 4, 5),
  wk2 = c(3, 4, 1, 0),
  wk3 = c(0, 0, 2, 0)
)

This is untidy: wk1, wk2, wk3 are three columns holding one variable (the count), recorded at three values of another variable (the week). pivot_longer() repairs it:

peng_obs |>
  tidyr::pivot_longer(
    cols            = wk1:wk3,
    names_to        = "week",
    names_prefix    = "wk",            # strip the "wk" so "wk2" becomes "2"
    names_transform = as.integer,      # and make week an integer, not a string
    values_to       = "observations"
  )

pivot_wider() is the inverse, and is most useful for turning a tidy summary into a human-readable table:

penguins_clean |>
  dplyr::summarise(mean = mean(body_mass_g, na.rm = TRUE),
                   .by = c(species, island)) |>
  tidyr::pivot_wider(
    names_from   = island,
    values_from  = mean,
    names_prefix = "mean_"
  )
Note

Keep analysis in long (tidy) form and pivot wide only at the very end, for display. Long data is what ggplot2 and the modelling functions expect; wide data is for human eyes in a printed table.

Slicing rows

slice() and its helpers select rows by position or by an ordering, which is often cleaner than a filter() with an arithmetic threshold.

# The three heaviest penguins per species
penguins_clean |>
  dplyr::slice_max(order_by = body_mass_g, n = 3, by = species) |>
  dplyr::select(species, body_mass_g)

The relatives are slice_head(), slice_tail(), slice_min() and slice_sample(). The modern by = argument applies the slice within each group without a separate group_by()/ungroup() pair.

The bridge to the afternoon: nesting

The afternoon’s iteration work rests on one idea introduced here. A tibble cell usually holds a single value. It can instead hold an entire tibble. group_by() followed by nest() collapses each group’s rows into one cell:

penguins_clean |>
  tidyr::drop_na(body_mass_g, flipper_length_mm) |>
  dplyr::group_by(species) |>
  tidyr::nest()

The data column is a list-column: each cell is a tibble holding one species’ observations. This is not exotic; it is an ordinary column whose values happen to be tibbles. We do nothing further with it now. Hold the picture in mind: in Block 4 we will apply a function to each of those cells and fit one model per species in a single pipeline.

Reading many files (a preview of iteration)

The same nesting and iteration ideas read a folder of files at once. Suppose a directory holds one CSV per sampling site:

# List the files (full paths, so they can be opened from anywhere)
csv_files <- list.files(
  path       = here::here("data", "many_files"),
  pattern    = "\\.csv$",
  full.names = TRUE
)

# Read every file and stack the results into one tibble.
# The modern idiom is map() then list_rbind(); the older map_dfr() is superseded.
all_sites <- csv_files |>
  purrr::map(\(f) readr::read_csv(f, show_col_types = FALSE)) |>
  purrr::list_rbind()

map() reads each file into a list of tibbles; list_rbind() binds that list into one tibble. We will unpack map() properly in Block 4. For now, notice that “do the same thing to every element of a collection” is the shape of almost all the work ahead.

Data validation with tidylog and assertr

A robust analysis makes every transformation visible and checks that your assumptions about the data actually hold. Two useful tools for this are tidylog, which reports what dplyr is doing, and assertr, which enforces explicit checks during a pipeline.

We’ll use a small simulated dataset of insect reproduction to illustrate both ideas.

library(tidyverse)
library(dplyr)
library(tidylog)
library(assertr)

set.seed(123)
n <- 200

female_egg_data <- tibble(
  female_id = 1:n,
  treatment = rep(c("A","B"), times = 100),
  age_days = sample(1:30, n, replace = TRUE),
  eggs_laid = rpois(n, lambda = 50),
  eggs_hatched = pmin(eggs_laid, rpois(n, lambda = 45)),
  body_mass  = rnorm(n, mean = 0.2, sd = 0.05)
)

# introduce a few intentional problems
female_egg_data$age_days[1] <- 0
female_egg_data$eggs_laid[2] <- 120
female_egg_data$eggs_hatched[3] <- female_egg_data$eggs_laid[3] + 5
female_egg_data$body_mass[4] <- -0.2   # a negative mass
female_egg_data$body_mass[5] <- 15     # far too heavy

Making transformations visible with tidylog

When tidylog is loaded, standard dplyr verbs report what they change. This is particularly helpful in pipelines where rows are filtered or variables are modified without leaving any obvious trace.

female_egg_data_clean <- female_egg_data |>
  filter(age_days > 0) |>
  mutate(eggs_per_day = eggs_laid / age_days)
filter: removed one row (<1%), 199 rows remaining
mutate: new variable 'eggs_per_day' (double) with 169 unique values and 0% NA

Rows are no longer dropped, or variables created, in silence: the console output summarises exactly what was removed or added, which makes the workflow easier to audit and debug.

Enforcing assumptions with assertr

tidylog shows you what happened to the data; assertr checks that the data meet your expectations before the analysis continues.

The core idea is that validation lives inside your pipeline, right next to the data it is checking. If an assertion fails, the pipeline stops and tells you exactly what went wrong and in which rows. If everything passes, execution continues as normal.

We will use the female_egg_data_clean dataset created above.

verify(): check a logical condition

verify() is the simplest function. It evaluates a logical expression against the whole dataframe and stops if it is FALSE. Think of it as stopifnot() with better error messages and pipeline compatibility.

# Check that all rows of eggs laid are positive — this should pass
# (verify() returns the data unchanged, so we hide the printed tibble)
female_egg_data_clean |>
  verify(eggs_laid > 0)
# Check something that will fail — no female can hatch more eggs than she laid
female_egg_data_clean |>
  verify(eggs_hatched <= eggs_laid)
Error:
! assertr stopped execution
verification [eggs_hatched <= eggs_laid] failed! (1 failure)

    verb redux_fn                 predicate column index value
1 verify       NA eggs_hatched <= eggs_laid     NA     2    NA
Note

verify() operates on the whole dataframe. It is good for checking structural properties: expected number of rows, expected columns, range constraints you know in advance.

assert(): check a predicate column by column

assert() applies a predicate function to one or more columns and reports which rows fail. This is more useful for checking individual variables.

# Check that eggs_hatched is within a plausible biological range
female_egg_data_clean |>
  assert(within_bounds(30, 60), eggs_hatched)

# Check that treatment only contains expected values
female_egg_data_clean |>
  assert(in_set("B", "A"), treatment)

# Check that age_days has no NAs
female_egg_data_clean |>
  assert(not_na, age_days)

You can check multiple columns at once by listing them:

# Check both egg measurements are within plausible ranges
female_egg_data_clean |>
  assert(within_bounds(0, 150), eggs_laid, eggs_hatched)

Built-in predicates

assertr ships with several predicates. The first four are used directly with assert(); the last two are predicate generators, which must be used with insist() (see below):

Predicate What it checks Example
within_bounds(a, b) Value falls within [a, b] `within_bounds(0, 100)`
not_na Value is not NA `not_na`
is_uniq Value is unique across rows `is_uniq`
in_set(...) Value belongs to an expected set `in_set("A", "B", "C")`
within_n_sds(n) Value is within n standard deviations of the mean `insist(within_n_sds(3), x)`
within_n_mads(n) Value is within n median absolute deviations (more robust to outliers) `insist(within_n_mads(3), x)`

insist(): generate bounds from the data itself

insist() is like assert(), but instead of a fixed predicate it takes a predicate generator: a function that first looks at the whole column (for example, to compute its mean and standard deviation) and then returns a predicate with bounds built from those values. That predicate is applied to every value in the column. within_n_sds() and within_n_mads() are predicate generators, so they work with insist(), not assert() (with assert() they stop with an error). They are particularly useful for flagging potential outliers without hard-coding exact bounds:

# Flag any eggs_laid values more than 3 SDs from the mean
female_egg_data_clean |>
  insist(within_n_sds(3), eggs_laid)
Error:
! assertr stopped execution
# within_n_mads is more robust to skewed distributions
female_egg_data_clean |>
  insist(within_n_mads(3), eggs_laid)
Error:
! assertr stopped execution
Column 'eggs_laid' violates assertion 'within_n_sds(3)' 1 time
    verb redux_fn       predicate    column index value
1 insist       NA within_n_sds(3) eggs_laid     1   120

Column 'eggs_laid' violates assertion 'within_n_mads(3)' 2 times
    verb redux_fn        predicate    column index value
1 insist       NA within_n_mads(3) eggs_laid     1   120
2 insist       NA within_n_mads(3) eggs_laid   105    26

assert_rows(): check row-level conditions

Sometimes the condition is not about a single column but about a combination of values across columns in the same row. assert_rows() handles this. It applies a row-reduction function first, then checks the result.

# Check that no row has more than 2 missing values across the numeric columns
female_egg_data_clean |>
  assert_rows(num_row_NAs, within_bounds(0, 2),
              eggs_laid, eggs_hatched, age_days, body_mass)

num_row_NAs counts the number of NAs per row across the specified columns. You can supply your own row-reduction function; it just needs to return a single value per row.

Chaining assertions

You can chain several checks together in a single pipeline. By default the pipeline stops at the first failing check. If you wrap the checks in chain_start() and chain_end(), every assertion runs and the errors are reported together at the end, so you get a complete picture of what is wrong rather than having to fix one thing at a time.

female_egg_data_clean |>
  chain_start() |>
  # Structural checks
  verify(has_all_names("female_id", "treatment", "eggs_laid", "eggs_hatched")) |>
  verify(length(female_id) > 0) |>   # at least one row
  # Column-level checks
  assert(in_set("A", "B"), treatment) |>
  assert(within_bounds(0, 100), eggs_laid) |>
  assert(within_bounds(1, 30), age_days) |>
  assert(within_bounds(0, 10), body_mass) |>
  chain_end(error_fun = error_stop)
Error:
! assertr stopped execution
Column 'eggs_laid' violates assertion 'within_bounds(0, 100)' 1 time
    verb redux_fn             predicate    column index value
1 assert       NA within_bounds(0, 100) eggs_laid     1   120

Column 'body_mass' violates assertion 'within_bounds(0, 10)' 2 times
    verb redux_fn            predicate    column index value
1 assert       NA within_bounds(0, 10) body_mass     3  -0.2
2 assert       NA within_bounds(0, 10) body_mass     4  15.0
Tip

You may see examples such as verify(nrow(.) > 0). The . placeholder only works with the magrittr pipe %>%; with the native pipe |> it gives “object ‘.’ not found”. Refer to a column instead, as above, or use has_all_names() to check structure.

Note

Two checks fail: the eggs_laid value of 120 we introduced earlier, and the two body masses we planted (-0.2 and 15). They are reported as rows 3 and 4 because the filter removed the first row. The other checks pass. This is a good example of why assertions are useful: they force you to make explicit decisions about what you consider valid data.

Using assertr in a cleaning pipeline

The natural place for assertr checks is immediately after loading raw data and again after cleaning (here with the raw penguins file you saved in Block 1). This gives you confidence that:

  1. The raw data is what you expect before you do anything to it
  2. The cleaned data is valid before any analysis runs
# ── Load and validate raw data ─────────────────────────────────────────────────
dat_raw <- read_csv(here("data", "raw", "penguins_raw.csv")) |>
  janitor::clean_names() |>
  rename(bill_length_mm = culmen_length_mm,
         bill_depth_mm  = culmen_depth_mm) |>
  mutate(species = stringr::word(species, 1)) |>

  # Validate structure before cleaning
  verify(has_all_names("species", "island", "bill_length_mm", "bill_depth_mm",
                       "flipper_length_mm", "body_mass_g", "sex")) |>
  assert(in_set("Adelie", "Chinstrap", "Gentoo"), species) |>
  assert(within_bounds(2500, 6500), body_mass_g) |>

# ── Clean ──────────────────────────────────────────────────────────────────────
  filter(!is.na(sex)) |>
  mutate(species = factor(species)) |>

# ── Validate cleaned data ──────────────────────────────────────────────────────
  assert(not_na, bill_length_mm, bill_depth_mm, flipper_length_mm, body_mass_g) |>
  verify(length(species) > 100)   # more than 100 rows retained

cat("Data validated and cleaned:", nrow(dat_raw), "rows retained\n")

If this pipeline runs without error, you have documented proof that your data meets your stated expectations at the point it enters the analysis.

Summary

Together, tidylog and assertr support a workflow where:

  • every data manipulation step is explicitly reported
  • key assumptions are tested during the pipeline
  • failures are caught early and clearly explained

Used together, they help make analysis code transparent and self-checking, and reduce the risk that unnoticed data problems carry through into your results.

Note

Where this leaves us. We can now operate on many columns at once, reshape between long and wide, slice by order, and collapse groups into list-columns. We can also make every data step visible with tidylog and check our assumptions about the data with assertr.
