Block 5: Instructions and skills

Note

Last verified: 9 October 2026, against GitHub’s Copilot documentation (custom instructions, agent skills), the Claude Code documentation (features overview, skills) and the Posit Assistant documentation (docs version 1.7: memory, skills).

The previous block showed that the further up the autonomy ladder an assistant works, the more its unstated assumptions land in your files. This block is how you state your conventions once, so you do not repeat them in every prompt.

There are two mechanisms, distinguished by when they load:

  • Instructions load into every session automatically. Use them for what is always true of the project: structure, style, reproducibility rules.
  • Skills load only when invoked by name or judged relevant from their description. Use them for procedures you need sometimes: producing a publication figure, cleaning data against a codebook, reviewing code.

Both are requests. The model usually follows them, but nothing guarantees it. Rules that must hold every time belong in the enforced controls of the next block.

⏱ ~55 minutes

Part A: Instructions

Where each tool looks

File Claude Code Posit Assistant GitHub Copilot
AGENTS.md (repository root) Via an import in CLAUDE.md Read as project memory Read by the cloud agent, agent mode and the CLI
CLAUDE.md Read every session — Read by the cloud agent
.github/copilot-instructions.md — — Read by Copilot; also offered for conversion by /import-instructions in Posit Assistant
Path-scoped rules .claude/rules/*.md with paths No equivalent found .github/instructions/*.instructions.md with applyTo

This course uses one source of truth: conventions live in AGENTS.md, and CLAUDE.md contains a single line that imports it:

@AGENTS.md

Copilot’s cloud agent reads both files, so it may see the conventions twice. That is harmless but wasteful, so keep CLAUDE.md to that one line.

Writing instructions that work

  • One instruction per line. Short, concrete statements are easier to check than paragraphs, for the model and for you.
  • Describe what you actually do. An instruction your existing code breaks sends the model mixed signals. The test is whether your own scripts obey it.
  • Be specific. “Use the native pipe |>” can be checked; “write clean, idiomatic code” cannot.
  • Keep it short. The file loads into every request. Anthropic advises keeping Claude Code’s always-loaded file under about 200 lines; aim far lower.
  • Add a rule when a mistake repeats. If the assistant gets the same convention wrong twice, that convention belongs in the file. A one-off correction in chat is forgotten next session.
  • Do not put guarantees here. “Never edit raw data” is worth stating, but enforce it with the controls in the next block.
# Project conventions: voles analysis

## Canary
When you write or edit R code, make the first line of the first code block:
# agents-md: active v1

## Structure
- Raw data live in data/raw/ and are never modified.
- Derived data go to data/derived/; figures and tables go to outputs/.
- Reusable functions live in scripts/functions/.

## R style
- Tidyverse style, native pipe |>, snake_case names, <- for assignment.
- Write TRUE and FALSE, never T and F.
- Build every path with here::here(). Never use setwd() or rm(list = ls()).
- Read CSV files with readr and explicit col_types.

## Reproducibility
- Packages are managed with renv. Do not call install.packages(); ask before
  adding a package.
- Set a seed immediately before any random step.
- Every script must run in a fresh R session.

## Data integrity
- Never drop rows silently; state the reason for every filter in a comment.
- Report the number of observations behind every summary statistic.

## Statistics
- Label each analysis as exploratory or confirmatory.
- Never type numerical results into text; compute them in code.

## Working with me
- Before changing more than one file, present a plan and wait for approval.
- Do not edit anything under data/raw/, tests/fixtures/ or .github/.

Activity: Build and test your AGENTS.md

Write, trim, verify (20 minutes)

Work in your forked workshop repository, committed and clean.

1. Baseline. With no AGENTS.md present, ask your assistant (rung 1, Ask):

Read data/raw/voles_metabolism.csv and make a quick exploratory plot of
mass_post_g by treatment arm.

Keep the answer.

2. Draft. Ask the assistant to draft an AGENTS.md by reading the repository. In Posit Assistant you can instead have a short conversation about your conventions and run /savememory. Expect the draft to be long and generic.

3. Trim hard. Delete anything the model padded or guessed. Keep only what is always true of this project.

4. Make it yours. Make sure the file states at least:

  1. one style convention you genuinely follow and the draft did not infer;
  2. one structural fact the model cannot guess, such as where raw data live and that they are immutable;
  3. one reproducibility or statistical convention you always apply;
  4. a canary: a fixed first line for any R code block, such as # agents-md: active v1.

5. Connect Claude Code. Create CLAUDE.md containing only @AGENTS.md.

6. Verify in each tool you use. Commit, open a new session, and repeat the Step 1 prompt.

  • If the canary appears, the file is being loaded.
  • If the canary is missing, the file is not reaching that tool. Check the file location, that the change is committed (for the Copilot cloud agent, pushed to the default branch), and, in Posit Assistant, that you trusted the workspace.
  • A canary shows that the file was loaded, not that every rule was followed. Check the plot code against each rule you wrote.

Activity: A rule for Quarto files only

Some rules are right for one kind of file and wrong elsewhere. A chunk option such as #| echo: false is meaningful in a .qmd file and meaningless in an .R script. The test for a scoped rule: would it be wrong, not merely irrelevant, in the files it excludes? If not, put it in AGENTS.md.

Create and test a scoped rule (10 minutes)

The rules themselves:

# Quarto document conventions

- Set chunk options with the hashpipe (#|) inside the chunk, not in the
  {r} header.
- Give every chunk a label; prefix figure chunks with fig-.
- Every figure chunk sets #| fig-cap:, #| fig-width: and #| fig-height:.
- Refer to figures in the text with @fig-..., never by a typed number.
- Default to #| echo: false unless the document is a code walkthrough.
- Resolve paths with here::here(); never assume the working directory is the
  document's folder.

Place them where your tool looks:

  • Copilot: .github/instructions/quarto.instructions.md, beginning with this front matter:

    ---
applyTo: "**/*.qmd"
---

  • Claude Code: .claude/rules/quarto.md, beginning with front matter that restricts it to Quarto files:

    ---
paths:
  - "**/*.qmd"
---

  • Posit Assistant: no path-scoped instruction file is documented. Add the rules to AGENTS.md under a heading such as “When editing .qmd files”, or rely on its built-in quarto-authoring skill.

Test. Open a .qmd file and ask for a chunk that plots mass_post_g by treatment_arm. A correct answer uses hashpipe options, a fig- label, a caption and here::here(). Then ask for the same plot in an .R script; the Quarto rules should not appear. If they do not appear in the .qmd either, the rule is not loading on your surface. Report what you found; behaviour differs between tools.

Every scoped rule is a second copy of a convention to keep in step, once per tool. Use scoped rules sparingly.

Part B: Skills

A skill is a folder containing a SKILL.md file, and optionally scripts, templates and reference files. The front matter carries a name and a description. Skills follow the open Agent Skills specification, so one skill can serve several tools.

Two parts decide whether a skill works:

  • The description is the trigger. The assistant reads descriptions to decide which skill is relevant. “Use when producing a ggplot2 figure for a report, poster or paper” loads when it should; “for plots” loads erratically. Invoking a skill by name (/skill-name) does not depend on the description.
  • The body is a procedure: when to use the skill, the steps, hard rules, and a final check. Because a skill loads only when used, it can be longer than an instruction file.

For a skill that writes files or has other side effects, set disable-model-invocation: true in the front matter, so it runs only when you invoke it by name. Claude Code and Posit Assistant both support this field.

Where each tool looks

Location in the repository Claude Code Posit Assistant GitHub Copilot
.agents/skills/<name>/ — Yes Yes
.claude/skills/<name>/ Yes — Yes
.posit/assistant/skills/<name>/ — Yes —
.github/skills/<name>/ — — Yes

Keep the single copy in .agents/skills/ and link it into .claude/skills/ for Claude Code, which follows symbolic links. On macOS or Linux, from the repository root:

mkdir -p .claude/skills
ln -s ../../.agents/skills/house-figures .claude/skills/house-figures

On Windows, symbolic links in git need extra configuration; copying the folder works, but you then maintain two copies. Copilot reads both .agents/skills/ and .claude/skills/. If it lists the skill twice, remove one route for Copilot.

Activity: Write a skill and test it

A house figure style (20 minutes)

1. Create .agents/skills/house-figures/SKILL.md:

---
name: house-figures
description: >-
  Applies this project's conventions to any ggplot2 figure that will appear
  in a report, poster or paper. Use when asked to create, revise or polish a
  figure for presentation. Not for quick exploratory plots.
---

# House figure style

## Rules
1. Where any group has fewer than 30 observations, show every observation
   (jittered points or a dot plot) with a summary overlaid. Never draw a bar
   with error bars ("dynamite plot").
2. Colour categorical groups with the Okabe-Ito palette
   (grDevices::palette.colors(palette = "Okabe-Ito")), and map the same
   variable to point shape so the figure works without colour.
3. Axis titles give the quantity and its unit, for example "Body mass (g)".
4. Use theme_classic(base_size = 12).
5. Show the number of observations per group on the figure.
6. Never add p-values or significance markers unless the user supplies a
   fitted model and asks for them.

## Before returning code
List which rules you applied, and any you could not apply and why.

2. Without the skill. In a session where the skill is not invoked, ask:

Make a figure of mass_post_g by treatment_arm for the voles data, for a
lab report.

3. With the skill. In a new session, invoke it by name (/house-figures) and ask the same thing.

4. Grade it. For each of the six rules, record whether the output complies:

Rule Without skill With skill
1. Raw data shown; no dynamite plot
2. Okabe-Ito colour plus shape
3. Units in axis titles
4. theme_classic(base_size = 12)
5. n per group shown
6. No unrequested p-values

Run the code and look at the figure. Code that names the right functions can still produce the wrong picture.

5. Test the trigger. Without naming the skill, ask “Give me a quick look at mass_post_g by arm” (exploratory, so the skill should not load), then “Polish this figure for the poster” (it should load). If either goes the wrong way, rewrite the description and test again.

6. Test a rule under pressure. Ask the assistant to “add significance stars between the groups”. Rule 6 says it should decline without a fitted model. Note whether it did. A skill is an instruction, not a guarantee.

Skills you did not write

Each tool ships built-in skills. Claude Code bundles skills such as /code-review and /debug. Posit Assistant includes quarto-authoring and r-package-development. Collections of shared skills are published online, for example Anthropic’s anthropics/skills repository.

Before installing a skill someone else wrote, read it. A skill can include scripts that the assistant may run on your machine, and its instructions shape what the assistant does with your files and data. Treat it as you would any code from the internet.
