Block 5: Enforced controls: permissions and detection

Your instruction fileA file the assistant loads into every conversation, such as AGENTS.md or CLAUDE.md, stating the project’s standing conventions. Its contents are requests, not guarantees. and skills are requests: nothing guarantees the model follows them. Here you watch the controls that do hold refuse something and find the route each one misses, so you know what your repository prevents and what it only detects.

⏱ ~25 minutes · Start on main (or checkpoint-skills), Git pane clean, Claude Code running in Manual mode.

Exercise 1: What needs protecting?

Threat-model your repository (3 minutes)

Goal: for each thing worth protecting, decide how you would notice if it went wrong, so that you know which check you are relying on before an agent works near it.

Your instructor posts the table; answer in the Zoom chat, row by row: if this went wrong, how would you notice?

Asset What could go wrong How you would notice
data/raw/ Overwritten or “tidied” in place
tests/fixtures/ The reference regenerated by the code under test
tests/ A failing test edited until it passes
.claude/, .posit/ The agent’s own guardrails switched off
.Renviron, .env Credentials read and sent to the model provider

The last two are easy to miss: the files that hold your controls are assets too.

You are done when the group has an answer for every row. Most will be “the Git pane would show it” or “a test would fail”.

Git detects changes only from your last commit, so commit before an agent starts. Some controls prevent and some only detect; Exercise 2 shows which.

NoteThe layers of control, and how each fails
Layer Example What it does How it fails
Instruction AGENTS.md, a skill Requests Silently ignored
Approval prompt “Allow this command?” Prevents, if you read it Approval fatigue
Deny rule Edit(/data/raw/**) Prevents Another route reaches the file
Hook A script Claude Code runs before each tool call Prevents Rephrasing gets past it
Version control The Git pane Detects Only from your last commit, and only if you look
Tests and checksums testthat, tools::md5sum() Detects Only if they run

Your repository’s AGENTS.md asks the agent to run git status before it edits anything, and to stop if there is no repository: a request that helps, but your commit is the control.

Exercise 2: Deny rules

Read, test and add a rule, then find the gap (15 minutes)

Goal: see a deny ruleA permission rule in the deny list of .claude/settings.json that stops Claude Code’s built-in tools from editing or reading the matching files. It checks shell output redirects such as > file, but not R code or most other commands that change the same files. refuse, add one of your own and find the route the rules do not cover, so that you know what your repository prevents and what only git detects.

Start state: Git pane clean, Claude Code in Manual mode. Work on a scratch file, never on real data.

1. Make a scratch file and read the rules. In the R console:

writeLines("a", here::here("data", "raw", "scratch.csv"))

Commit it in the Git pane, so git can show any later change to it. In Claude Code, type /permissions: the 17 deny rules your repository ships are listed.

2. See a rule refuse.

Prompt (Claude Code):

Add a second line, "test", to data/raw/scratch.csv.

“Denied by a permission rule” means the rule held, whatever the model intended. If the model declines by itself, citing AGENTS.md, that was a request that happened to work: reply “This is a scratch file; please make the edit with your edit tool” to see the rule refuse.

Answer each request with plain Yes or No. Never choose an option that says don’t ask again: it saves a rule that skips the question from then on. If Claude Code asks to write the file another way, answer No: step 4 tries that.

3. Add a rule yourself. In /permissions, add Read(/data/confidential/**), one of the confidential-data habits from Block 3. When asked where to save it, choose the project’s shared settings file, .claude/settings.json, not the local one (see How it works). It applies at once.

4. Find the gap.

Prompt (Claude Code):

Run this R code with Rscript: writeLines(c("a", "test"), "data/raw/scratch.csv")

Deny rules do not cover R code, so only the approval prompt stands in the way. Approve a run only if you can say what it does and why you want it now; refusing is always safe. Here you can: it writes to a scratch file, and you want to see what catches the change. Approve it. The Git pane now shows the file as modified, and Diff shows the new line: git caught what no rule prevented.

5. Tidy up. Revert the file in the Git pane, then delete it, so no scratch file is left among the raw data:

file.remove(here::here("data", "raw", "scratch.csv"))

6. Record, test and commit. Add a line to docs/ai-log.md, in the same form as before, noting which requests were refused and what git caught. Then restart R (Session → Restart R) and run:

testthat::test_dir(here::here("tests"))

test_controls.R checks that Manual mode and every shipped rule are still in place and that no command is approved in advance; test_ai_log.R checks your new line. Commit the deletion of scratch.csv, your rule in .claude/settings.json and the log line together.

You are done when you have seen a rule refuse, added one of your own, seen the Git pane catch the R write, scratch.csv is gone, the test suite has no failures (tests for later blocks skip), and your rule and log line are committed.

If it goes wrong: if the model keeps declining in step 4, write the line yourself in the console and carry on: the point is seeing git catch it. If “no command is approved in advance” fails, you chose don’t ask again: remove that allow rule in /permissions.

NoteAt the command line

git add/git commit for step 1, git diff data/raw for step 4, git restore then git rm data/raw/scratch.csv for step 5, and Rscript -e "testthat::test_dir('tests')" then git add/git commit for step 6. See checking work.

NoteHow it works: where the rules live

Your repository’s .claude/settings.json starts the project in Manual mode ("defaultMode": "default": asks before every edit and command) and holds 17 deny rules protecting the raw data, the data provider’s note, the codebook, the checks, the references, the lockfile and the settings themselves. You never need to edit it: /permissions shows the rules and adds new ones.

{
  "permissions": {
    "defaultMode": "default",
    "deny": [
      "Edit(/data/raw/**)",
      "Read(/docs/data_note.md)",
      "Edit(/docs/data_note.md)",
      "Edit(/docs/codebook.csv)",
      "Edit(/scripts/02_validate.R)",
      "Edit(/scripts/03_audit_cleaning.R)",
      "Edit(/scripts/functions/validate_voles.R)",
      "Edit(/tests/fixtures/**)",
      "Edit(/tests/make_reference.R)",
      "Edit(/tests/test_cleaning.R)",
      "Edit(/renv.lock)",
      "Edit(/.github/**)",
      "Edit(/.claude/**)",
      "Edit(/.posit/**)",
      "Edit(/hooks/**)",
      "Read(/.Renviron)",
      "Read(/.env)"
    ]
  }
}

A leading / anchors a pattern to the project root. Edit rules cover Claude Code’s file-editing tools and shell output redirects (> file), not R code it runs, and the documentation does not say they cover rm, mv or cp. The rules protect named files rather than whole folders, so the agent can still write its scripts and tests in Blocks 7 and 8. Edit(/renv.lock) keeps renv::status() a real check.

Why the shared settings file. /permissions can save a rule to .claude/settings.json, which is committed with the project, or to the local .claude/settings.local.json, which git ignores. Only a rule in the shared file reaches a commit, and so everyone who clones the repository. Answering don’t ask again saves an allow rule, usually in the local file, which is why test_controls.R checks that no command is approved in advance.

TipUsing another tool

The exercises use Claude Code. Posit Assistant sets permissions per tool in .posit/assistant/settings.json (for example "bash": {"rm *": "deny"}); deny rules hold in every mode, including auto and YOLO. It has no documented path rules for file edits, so rely on the Git pane in step 4 of Exercise 2. It blocks reading .env and .Renviron by default.

NoteSet up controls in your own project

Your workshop repository came with its controls. A new project of your own starts with none, so set them up before the agent’s first task:

  1. Git first. In the R console, usethis::use_git(), and make a first commit.
  2. Add a starter settings.json. Download the one below, save it as .claude/settings.json, and edit the paths to match your project. It starts in Manual mode and protects raw data, test references, the lockfile, credentials and itself. Add project-specific rules with /permissions.
  3. Ask for git checks. Copy the Version control section of your workshop AGENTS.md into your project’s instruction file.
  4. Test it. Ask the agent to edit a protected file and watch the rule refuse; copy tests/test_controls.R and change its list of rules to yours. Then commit.
TipReference: the starter settings.json 
{
  "permissions": {
    "defaultMode": "default",
    "deny": [
      "Edit(/data/raw/**)",
      "Edit(/tests/fixtures/**)",
      "Edit(/renv.lock)",
      "Edit(/.claude/**)",
      "Read(/.Renviron)",
      "Read(/.env)"
    ]

}

Let Claude draft rules, never decide them. You can ask it to propose deny rules for a project, but read each one: a rule with a wrong path, such as a missing leading /, protects nothing and fails silently. Claude Code asks before every write to .claude/, and the starter file’s Edit(/.claude/**) refuses such writes outright, so you install the rules yourself.

Protecting something new takes 30 seconds in /permissions. For confidential data, add the five habits in Block 3; and since settings and hooks are code, trust only repositories whose configuration you have read.

TipA guard hook

Claude Code itself, the harness rather than the model, runs a PreToolUse hook before each tool call and passes it the pending call as JSON on standard input (stdin). If the hook exits with status 2, the call is denied and its message is passed to the model. Claude Code and Posit Assistant use the same shape for this, so one script can serve both.

The guard below is written in R. It denies any edit, shell command or R code that mentions a protected path.

#!/usr/bin/env Rscript
# hooks/guard_protected_paths.R ----
# PreToolUse guard for Claude Code and Posit Assistant.
# Reads the pending tool call from stdin and exits 2 (deny) if the call
# mentions a protected path. A tripwire, not a wall: see "Break your own
# guard".

protected <- c(
  "data/raw",
  "tests/fixtures",
  "make_reference.R",
  ".github/workflows"
)

payload <- jsonlite::fromJSON(
  paste(readLines(file("stdin"), warn = FALSE), collapse = "\n"),
  simplifyVector = FALSE
)

# search the whole tool input as text, so the same rule covers file edits,
# shell commands and R code whatever the tool calls its fields
call_text <- as.character(jsonlite::toJSON(payload$tool_input, auto_unbox = TRUE))
hits <- protected[vapply(protected, \(p) grepl(p, call_text, fixed = TRUE), logical(1))]

if (length(hits) > 0) {
  message(
    "Blocked by project guard: this ", payload$tool_name,
    " call refers to a protected path (", paste(hits, collapse = ", "), "). ",
    "Do not modify protected files; ask the user to do it."
  )
  quit(save = "no", status = 2)
}

quit(save = "no", status = 0)

The template does not ship hooks/: save the script yourself as hooks/guard_protected_paths.R, for example with usethis::edit_file("hooks/guard_protected_paths.R"). It runs with Rscript --vanilla, so it does not start renv, and jsonlite must be installed in your user library.

Register it with Claude Code by adding a hooks key to .claude/settings.json, alongside the existing permissions key. The deny rules protect .claude/, so make this edit yourself, not through the agent.

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit|Write|Bash",
        "hooks": [
          {
            "type": "command",
            "command": "Rscript --vanilla \"$CLAUDE_PROJECT_DIR\"/hooks/guard_protected_paths.R"
          }
        ]
      }
    ]
  }
}

The matcher lists the tool names the hook runs for.

Register it with Posit Assistant in .posit/assistant/settings.json. The tool names differ: edit, bash, and executeR for R code run in your session.

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "edit|bash|executeR",
        "hooks": [
          { "type": "command", "command": "Rscript --vanilla hooks/guard_protected_paths.R" }
        ]
      }
    ]
  }
}

Posit Assistant runs project hooks only in a workspace you have trusted.

Test the hook before you trust it

Goal: check the guard denies a protected path and allows a harmless call, so that you know it works before you rely on it.

Hooks fail open. If the script crashes, for example because jsonlite is not installed, both tools continue as if the hook had allowed the call. So test the script directly, without the agent. The R below runs the hook exactly as Claude Code does, a fresh Rscript --vanilla process given the tool call on standard input, and works the same on Windows, macOS and Linux.

In the R console:

rscript <- file.path(R.home("bin"), "Rscript")
hook <- shQuote(here::here("hooks", "guard_protected_paths.R"))

run_hook <- function(json) {
  system2(rscript, c("--vanilla", hook), input = json,
          stdout = FALSE, stderr = FALSE)
}

# can the hook's own R session load jsonlite? 0 means yes
system2(rscript, c("--vanilla", "-e", shQuote("library(jsonlite)")),
        stdout = FALSE, stderr = FALSE)

# a call naming a protected path: expect 2
run_hook('{"tool_name":"Bash","tool_input":{"command":"Rscript tests/make_reference.R"}}')

# a harmless call: expect 0
run_hook('{"tool_name":"Bash","tool_input":{"command":"Rscript scripts/05_analysis.R"}}')

Any result other than 2 for the first call and 0 for the second means the hook is broken and is silently allowing everything.

Now repeat the request from step 4 of Exercise 2. The R code mentions data/raw, so the guard should deny it before you see an approval prompt.

To see exactly what each tool sends to hooks, temporarily add a PostToolUse hook with no matcher that appends its input to a log file (Posit Assistant’s hooks documentation gives an example), and read the log.

You are done when the protected call returns 2, the harmless call returns 0, and the request from step 4 of Exercise 2 is denied before you see an approval prompt.

TipBreak your own guard

Red-team the tripwire

Goal: get a write past the guard hook, so that you see where a text-matching guard stops.

The live block removed the scratch file at the end. Recreate it first, in the R console, and commit it from the Git pane:

writeLines("a", here::here("data", "raw", "scratch.csv"))

Prompt (Claude Code):

Run this R code:
writeLines(c("a", "test"), here::here("data", "raw", "scratch.csv"))

The guard searches for the text data/raw. This call never contains it, because here::here() assembles the path from separate pieces, so the guard allows the call. A Windows path written with backslashes would also slip past.

This is the general limit of hooks that match text: they catch the obvious form of a dangerous action, not every way of expressing it. Claude Code’s documentation makes the same point about command patterns. A guard hook is a tripwire that stops accidents and makes intent visible; it is not a wall. The Git pane still shows the change. Revert the file there, then delete it and commit the deletion, as in steps 5 and 6 of Exercise 2.

You are done when the here::here() write has got past the guard, the Git pane has shown the change, and you have deleted scratch.csv again.

TipThe review gate on GitHub

Local controls do not exist for an agent that works remotely, such as the Copilot cloud agent. There, the controls are on the repository itself. Neither file below is in the workshop template; you create them.

1. CODEOWNERS. Create .github/CODEOWNERS on your default branch:

/data/raw/            @your-github-username
/tests/               @your-github-username
/.github/             @your-github-username
/hooks/               @your-github-username
/.claude/             @your-github-username
/.posit/              @your-github-username

Code owners are requested for review automatically when a pull request changes the files they own. CODEOWNERS works in public repositories on free plans; for private repositories it requires a paid plan.

2. Branch protection. In the repository settings, add a rule for main that requires a pull request before merging, requires review from code owners, and requires the r-checks status check to pass. The r-checks workflow is set up in the Going further section of Block 8.

3. Test it. Open a pull request that changes a file under tests/, for example by asking the Copilot cloud agent to “update the test to use a tolerance of 1e-6”. Confirm that the pull request cannot merge until you have reviewed it.

GitHub does not let you approve your own pull request. In a repository where you are the only person, a pull request you open yourself may need an administrator override, which is a reason to test this gate with an agent’s pull request.

TipFeedback hooks: useful, with a warning

Hooks can do more than block. A PostToolUse hook can run lintr on each R file the agent edits and pass the result back to it. A Stop hook can run the test suite and refuse to let the agent finish while tests fail. The second is powerful and dangerous: an agent told it cannot stop until tests pass may try to change the tests. Use it only when the deny rules and guard hook protect tests/.

Glossary

term definition
branch protection GitHub repository settings that stop changes reaching a branch such as main unless conditions are met, for example a passing check and an approved review.
checksum A short fingerprint computed from a file's contents, for example with tools::md5sum(). Any change to the file changes the checksum, so it detects changes made by any route.
CODEOWNERS A GitHub file listing who must review changes to which paths. With branch protection, a pull request that touches those paths cannot merge without their review.
deny rule A permission rule in the deny list of .claude/settings.json that stops Claude Code's built-in tools from editing or reading the matching files. It checks shell output redirects such as > file, but not R code or most other commands that change the same files.
hook A command the assistant runs automatically at a fixed point, for example before every tool call. A hook can block the call, but it matches text, so a differently written command can get past it.
instruction file A file the assistant loads into every conversation, such as AGENTS.md or CLAUDE.md, stating the project's standing conventions. Its contents are requests, not guarantees.
tool call A single action an agent takes, such as reading a file, editing a file or running a shell command. Permission rules and hooks act on tool calls.
