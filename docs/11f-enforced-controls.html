Block 6: Enforced controls: permissions, hooks and review gates

Everything you have written so far to steer an assistant (custom instructions, CLAUDE.md, AGENTS.md, skills) is a request. The model reads it and usually follows it, but nothing guarantees that it will. Anthropic’s own documentation for Claude Code makes the same distinction: a “never edit this file” line in an instruction file is a request, while a hook that blocks the edit is enforcement.

For research code, a few things must hold every time: raw data are never modified, a frozen reference output is never regenerated by the code it is meant to check, and the checks themselves are not quietly edited to pass. This block builds the controls that make those rules hold, and shows you where each control stops working.

The protections you build here are reused in the data-cleaning and characterisation-test blocks.

⏱ ~50 minutes

Layers of control

Layer Example Prevents or detects What it covers How it fails
Instruction CLAUDE.md, AGENTS.md, a skill Neither; it requests Whatever the model chooses to follow Silently ignored
Approval prompt “Allow this command?” Prevents, if you read it Every action you are shown Approval fatigue; permissive modes skip it
Permission rule Edit(/data/raw/**) deny Prevents One tool, by name or path Another tool reaches the same file
Hook A script run before each tool call Prevents Whatever its matcher and logic see Bypassed by rephrasing; fails open if it crashes
Version control git status, git diff Detects Any route Only if you look
Tests and checksums testthat, tools::md5sum() Detects Any route Only if they run
Review gate CODEOWNERS, branch protection, CI Blocks merging Any change that arrives as a pull request Only on protected branches

Two principles follow from the table:

  1. Prevent where you can, detect everywhere. Each preventive control covers some routes and misses others. Detection by git and tests covers every route, but only after the fact.
  2. Test every control. A control you have not seen refuse something is a control you are assuming.

Exercise 1: What needs protecting?

Threat-model your repository (5 minutes)

For the workshop repository, list each asset, what could go wrong, and how you would notice. Start from this table and add to it:

Asset What could go wrong How you would notice
data/raw/ Overwritten or “tidied” in place
tests/fixtures/ Reference output regenerated by the code under test
tests/ A failing test edited until it passes
.github/workflows/ The CI check weakened or removed
.claude/, .posit/, hooks/ The agent’s own guardrails switched off
.Renviron, .env Credentials read and sent to the model provider

The last two rows are easy to miss. Configuration files that hold your controls are themselves assets: an agent that can edit its settings can remove its own restrictions.

Exercise 2: Permission rules

Claude Code

Permission rules live in .claude/settings.json, which is committed and shared with everyone who uses the repository:

{
  "permissions": {
    "deny": [
      "Edit(/data/raw/**)",
      "Edit(/tests/fixtures/**)",
      "Edit(/tests/make_reference.R)",
      "Edit(/.github/**)",
      "Edit(/.claude/**)",
      "Edit(/.posit/**)",
      "Edit(/hooks/**)",
      "Read(/.Renviron)",
      "Read(/.env)"
    ]
  }
}

A leading / anchors the pattern to the project root. Edit rules apply to all of Claude Code’s built-in file-editing tools; use Edit, not Write, for path rules.

Posit Assistant

Posit Assistant’s permissions are set per tool in .posit/assistant/settings.json, with pattern matching for shell commands:

{
  "permission": {
    "bash": {
      "rm *": "deny"
    },
    "edit": "ask"
  }
}

deny rules are enforced in every approval mode, including auto and YOLO. The documentation does not describe path patterns for file edits, so protection of specific paths comes from the hook in Exercise 3. Posit Assistant blocks reading .env and .Renviron by default.

Test the rule, then find the gap (10 minutes)

Work in the practice repository, not on real data. Create a scratch file data/raw/canary.csv containing one line, and commit it.

1. Confirm the rule refuses. Ask your assistant:

Add a second line, "test", to data/raw/canary.csv.

In Claude Code, the edit should be refused. Run /permissions to see which rule refused it.

2. Find the gap. Now ask:

Run this R code: writeLines(c("a", "test"), "data/raw/canary.csv")

Claude Code’s deny rules apply to its built-in file tools, not to commands it runs through the shell or R. What stops this second request? In normal mode, the approval prompt: you are asked before the command runs. In a mode that auto-approves commands, nothing in this exercise does.

3. Detect it. Whatever happened, run:

git status --short data/raw

If the file changed, git shows it. Restore it with git restore data/raw/canary.csv.

Exercise 3: A guard hook

A hook is a command the assistant runs at a fixed point, for example before every tool call. A PreToolUse hook receives the pending tool call as JSON on standard input. If it exits with status 2, the call is denied and its message is passed to the model. Claude Code and Posit Assistant use the same shape for this, so one script can serve both.

The guard below is written in R. It denies any edit, shell command or R code that mentions a protected path.

#!/usr/bin/env Rscript
# hooks/guard_protected_paths.R ----
# PreToolUse guard for Claude Code and Posit Assistant.
# Reads the pending tool call from stdin and exits 2 (deny) if the call
# mentions a protected path. A tripwire, not a wall: see Exercise 4.

protected <- c(
  "data/raw",
  "tests/fixtures",
  "make_reference.R",
  ".github/workflows"
)

payload <- jsonlite::fromJSON(
  paste(readLines(file("stdin"), warn = FALSE), collapse = "\n"),
  simplifyVector = FALSE
)

# search the whole tool input as text, so the same rule covers file edits,
# shell commands and R code whatever the tool calls its fields
call_text <- as.character(jsonlite::toJSON(payload$tool_input, auto_unbox = TRUE))
hits <- protected[vapply(protected, \(p) grepl(p, call_text, fixed = TRUE), logical(1))]

if (length(hits) > 0) {
  message(
    "Blocked by project guard: this ", payload$tool_name,
    " call refers to a protected path (", paste(hits, collapse = ", "), "). ",
    "Do not modify protected files; ask the user to do it."
  )
  quit(save = "no", status = 2)
}

quit(save = "no", status = 0)

The script runs with Rscript --vanilla, so it does not start renv, and jsonlite must be installed in your user library.

Register it with Claude Code by adding a hooks key to .claude/settings.json:

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit|Write|Bash",
        "hooks": [
          {
            "type": "command",
            "command": "Rscript --vanilla \"$CLAUDE_PROJECT_DIR\"/hooks/guard_protected_paths.R"
          }
        ]
      }
    ]
  }
}

Register it with Posit Assistant in .posit/assistant/settings.json. The tool names differ: edit, bash, and executeR for R code run in your session.

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "edit|bash|executeR",
        "hooks": [
          { "type": "command", "command": "Rscript --vanilla hooks/guard_protected_paths.R" }
        ]
      }
    ]
  }
}

Posit Assistant runs project hooks only in a workspace you have trusted.

Test the hook before you trust it (10 minutes)

Hooks fail open. If the script crashes, for example because jsonlite is not installed, both tools continue as if the hook had allowed the call. So test the script directly, without the agent, from the repository root:

echo '{"tool_name":"Bash","tool_input":{"command":"Rscript tests/make_reference.R"}}' \
  | Rscript --vanilla hooks/guard_protected_paths.R
echo "exit status: $?"

Expect a message and exit status: 2. Then test a harmless call:

echo '{"tool_name":"Bash","tool_input":{"command":"Rscript scripts/02_analysis.R"}}' \
  | Rscript --vanilla hooks/guard_protected_paths.R
echo "exit status: $?"

Expect exit status: 0. Any other status means the hook is broken and is silently allowing everything.

Now repeat request 2 from Exercise 2. The R code mentions data/raw, so the guard should deny it before you see an approval prompt.

To see exactly what each tool sends to hooks, temporarily add a PostToolUse hook with no matcher that appends its input to a log file (Posit Assistant’s hooks documentation gives an example), and read the log.

Exercise 4: Break your own guard

Red-team the tripwire (5 minutes)

Ask the assistant to run:

Run this R code:
writeLines(c("a", "test"), here::here("data", "raw", "canary.csv"))

The guard searches for the text data/raw. This call never contains it, because here::here() assembles the path from separate pieces, so the guard allows the call. A Windows path written with backslashes would also slip past.

This is the general limit of hooks that match text: they catch the obvious form of a dangerous action, not every way of expressing it. Claude Code’s documentation makes the same point about command patterns. A guard hook is a tripwire that stops accidents and makes intent visible; it is not a wall. git status still catches the change. Restore the file before moving on.

Exercise 5: The review gate on GitHub

Local controls do not exist for an agent that works remotely, such as the Copilot cloud agent. There, the controls are on the repository itself.

1. CODEOWNERS. Create .github/CODEOWNERS on your default branch:

/data/raw/            @your-github-username
/tests/               @your-github-username
/.github/             @your-github-username
/hooks/               @your-github-username
/.claude/             @your-github-username
/.posit/              @your-github-username

Code owners are requested for review automatically when a pull request changes the files they own. CODEOWNERS works in public repositories on free plans; for private repositories it requires a paid plan.

2. Branch protection. In the repository settings, add a rule for main that requires a pull request before merging, requires review from code owners, and requires the r-checks status check to pass.

3. Test it. Open a pull request that changes a file under tests/, for example by asking the Copilot cloud agent to “update the test to use a tolerance of 1e-6”. Confirm that the pull request cannot merge until you have reviewed it.

GitHub does not let you approve your own pull request. In a repository where you are the only person, a pull request you open yourself may need an administrator override, which is a reason to test this gate with an agent’s pull request.

Feedback hooks: useful, with a warning

Hooks can do more than block. A PostToolUse hook can run lintr on each R file the agent edits and pass the result back to it. A Stop hook can run the test suite and refuse to let the agent finish while tests fail. The second is powerful and dangerous: an agent told it cannot stop until tests pass may try to change the tests. Use it only when the deny rules and guard from this block protect tests/.

Data governance

A deny rule on reading a file stops the agent’s read tool. It does not stop R code or a shell command that reads the file and prints its contents, and anything printed enters the model’s context and is sent to the provider. Restricting tools reduces accidental exposure. It does not make an agent safe for confidential data. For personal or confidential data, work on a synthetic copy and run the final code yourself, outside the agent’s workspace.

Hooks and project settings are also code that runs on your machine. A cloned repository can carry its own settings and hooks, which is why Posit Assistant asks you to trust a workspace before using them. Trust only repositories whose configuration you have read.
