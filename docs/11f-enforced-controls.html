Block 6: Enforced controls: permissions and detection

Everything you have written so far to steer an assistant (the instruction filesA file the assistant loads into every conversation, such as AGENTS.md or CLAUDE.md, stating the project’s standing conventions. Its contents are requests, not guarantees. AGENTS.md and CLAUDE.md, and skills) is a request. The model reads it and usually follows it, but nothing guarantees that it will. Anthropic’s own documentation for Claude Code makes the same distinction: a “never edit this file” line in an instruction file is a request, while a hookA command the assistant runs automatically at a fixed point, for example before every tool call. A hook can block the call, but it matches text, so a differently written command can get past it. that blocks the edit is enforcement.

For research code, a few things must hold every time: raw data are never modified, the reference (in tests/fixtures/) is never regenerated by the code it is meant to check, and the checks themselves are not quietly edited to pass. This block tests the controls that make those rules hold, and shows you where each control stops working. By the end you will know exactly what your repository prevents, what it detects, and how to check both yourself in a few seconds: that knowledge is what lets you hand an agent real work.

The same controls protect your work in Block 7 and Block 9.

⏱ ~30 minutes

Layers of control

Two principles follow:

  1. Prevent where you can, detect everywhere. Each preventive control covers some routes and misses others. Detection by git, tests and a checksumA short fingerprint computed from a file’s contents, for example with tools::md5sum(). Any change to the file changes the checksum, so it detects changes made by any route. covers every route, but only after the fact.
  2. Test every control. A control you have not seen refuse something is a control you are assuming.

Exercise 1: What needs protecting?

Threat-model your repository (5 minutes)

As a quick group discussion, go through each asset in your workshop repository: what could go wrong, and how would you notice?

Asset What could go wrong How you would notice
data/raw/ Overwritten or “tidied” in place
tests/fixtures/ The reference regenerated by the code under test
tests/ A failing test edited until it passes
.github/workflows/ The CI check weakened or removed
.claude/, .posit/, hooks/ The agent’s own guardrails switched off
.Renviron, .env Credentials read and sent to the model provider

The last two rows are easy to miss. Configuration files that hold your controls are themselves assets: an agent that can edit its settings can remove its own restrictions.

You are done when every row has an entry in the last column. Most answers will be “git would show it” or “a test would fail”: that is where this block is heading.

Exercise 2: Deny rules

Claude Code’s permission rules live in .claude/settings.json. The file ships with your workshop repository and is committed, so everyone who clones the repository gets the same rules. Open it in the editor and read it. This is the file in your workshop repository, with 16 rules:

{
  "permissions": {
    "deny": [
      "Edit(/data/raw/**)",
      "Edit(/docs/data_note.md)",
      "Edit(/docs/codebook.csv)",
      "Edit(/scripts/02_validate.R)",
      "Edit(/scripts/03_audit_cleaning.R)",
      "Edit(/scripts/functions/validate_voles.R)",
      "Edit(/tests/fixtures/**)",
      "Edit(/tests/make_reference.R)",
      "Edit(/tests/test_cleaning.R)",
      "Edit(/renv.lock)",
      "Edit(/.github/**)",
      "Edit(/.claude/**)",
      "Edit(/.posit/**)",
      "Edit(/hooks/**)",
      "Read(/.Renviron)",
      "Read(/.env)"
    ]
  }
}

Each entry is a deny ruleA permission rule in the deny list of .claude/settings.json that stops Claude Code’s built-in tools from editing or reading the matching files. It checks shell output redirects such as > file, but not R code or most other commands that change the same files.. A leading / anchors the pattern to the project root. Edit rules apply to all of Claude Code’s built-in file-editing tools, and Claude Code also checks shell output redirects (> file, >> file) against them. They do not cover R code the agent runs, and the documentation does not say they cover other shell commands such as rm, mv or cp. The rules protect specific files rather than whole folders, so the agent can still write the cleaning script in Block 7 and the function and its test in Block 9. Edit(/renv.lock) keeps the lockfile yours, so that renv::status() remains a real check: an agent that could rewrite the lockfile could make any package mismatch disappear.

TipUsing Posit Assistant

Posit Assistant’s permissions are set per tool in .posit/assistant/settings.json, with pattern matching for shell commands:

{
  "permission": {
    "bash": {
      "rm *": "deny"
    },
    "edit": "ask"
  }
}

deny rules are enforced in every approval mode, including auto and YOLO. The documentation does not describe path patterns for file edits, so protection of specific paths comes from a guard hook (see Going further); without one, rely on the Git pane in step 4 below. Posit Assistant blocks reading .env and .Renviron by default.

Test the rule, then find the gap (15 minutes)

Start: your workshop repository open, committed and clean (the Git pane shows no changed files), with Claude Code not yet running. Work on the scratch file below, never on real data.

1. Make a scratch file. In the R console, create a one-line file in the protected folder:

writeLines("a", here::here("data", "raw", "scratch.csv"))

Commit it from the Git pane (tick data/raw/scratch.csv, Commit, message “Add scratch file for testing deny rules”).

2. Confirm the rule refuses. In the Terminal tab, start Claude Code in default mode (claude) and type /permissions: the 16 rules from the file above should be listed. Then ask:

Prompt (Claude Code):

Add a second line, "test", to data/raw/scratch.csv.

Watch how it is refused. There are two possibilities, and they are different layers:

  • Claude Code reports that the edit is denied by a permission rule: that is the deny rule, and it would hold whatever the model intended.
  • The model declines by itself, citing your AGENTS.md (“raw data are never modified”): that is your instruction file, a request. It worked this time, but nothing guaranteed it.

If the model declined by itself, ask again: “This is a scratch file; please make the edit with your edit tool.” Now you should see the rule refuse it. /permissions lists the rules in force but does not say which one refused a request, so match the path yourself.

3. Find the gap. Now ask:

Prompt (Claude Code):

Run this R code with Rscript: writeLines(c("a", "test"), "data/raw/scratch.csv")

The deny rules check Claude Code’s edit tools, and shell redirects such as echo test >> data/raw/scratch.csv, but not R code. So the only thing between this request and the file is the approval prompt. Approve it: it is a scratch file, and the point is to see what catches the change.

4. Detect it. The Git pane now shows data/raw/scratch.csv as modified; Diff shows the added line. Git saw a change that no preventive control stopped. Then confirm the settings themselves are intact, in the R console:

testthat::test_file(here::here("tests", "test_controls.R"))

The test that every shipped deny rule is still present should pass.

5. Tidy up. Revert data/raw/scratch.csv in the Git pane, then delete it and commit the deletion:

file.remove(here::here("data", "raw", "scratch.csv"))

You are done when you have seen the deny rule refuse the edit, the Git pane show the change made through R, test_controls.R pass, and scratch.csv is gone from the repository.

If it goes wrong: if the model keeps declining in step 3, write the line yourself in the console with writeLines(c("a", "test"), here::here("data", "raw", "scratch.csv")) and carry on from step 4: what matters is seeing git catch a change that no rule prevented.

NoteAt the command line

From a second Terminal tab, or after /exit: git add data/raw/scratch.csv and git commit -m "..." for step 1, git status --short data/raw and git diff data/raw for step 4, git restore data/raw/scratch.csv and git rm data/raw/scratch.csv for step 5. See checking work.

ImportantData governance

Restricting tools reduces accidental exposure but does not make an agent safe for confidential data; see Block 4.

Hooks and project settings are also code that runs on your machine. A cloned repository can carry its own settings and hooks. Trust only repositories whose configuration you have read.

Your repository now prevents and detects. The deny rules stop the agent’s edit tools from touching the raw data, the codebook, the checks, the references, the lockfile and the settings themselves. Anything that gets past them by another route (R code, a shell command, a person) is detected: the Git pane shows every changed file, the checksum test in Block 7 fails if the raw data change, and test_controls.R fails if a shipped rule disappears. You do not need to watch the agent every second; you need these checks, and you now know how to run them.

NoteCheck · Reproduce · Record
  • You can now: let an agent work in default mode in a repository where raw data, references and checks are protected, trusted because you have seen the deny rule refuse, seen git catch the route it misses, and have a test that fails if the rules are weakened.
  • Check: test every control by watching it refuse something, and find the route it does not cover.
  • Reproduce: the deny rules live in .claude/settings.json, committed with the project, so everyone who clones it gets the same protection.
  • Record: the Git pane is the record that catches a change by any route. Add a line to docs/ai-log.md noting which requests were refused.

A guard hook

A PreToolUse hook receives the pending tool call as JSON on standard input (stdin). If it exits with status 2, the call is denied and its message is passed to the model. Claude Code and Posit Assistant use the same shape for this, so one script can serve both.

The guard below is written in R. It denies any edit, shell command or R code that mentions a protected path.

#!/usr/bin/env Rscript
# hooks/guard_protected_paths.R ----
# PreToolUse guard for Claude Code and Posit Assistant.
# Reads the pending tool call from stdin and exits 2 (deny) if the call
# mentions a protected path. A tripwire, not a wall: see "Break your own
# guard".

protected <- c(
  "data/raw",
  "tests/fixtures",
  "make_reference.R",
  ".github/workflows"
)

payload <- jsonlite::fromJSON(
  paste(readLines(file("stdin"), warn = FALSE), collapse = "\n"),
  simplifyVector = FALSE
)

# search the whole tool input as text, so the same rule covers file edits,
# shell commands and R code whatever the tool calls its fields
call_text <- as.character(jsonlite::toJSON(payload$tool_input, auto_unbox = TRUE))
hits <- protected[vapply(protected, \(p) grepl(p, call_text, fixed = TRUE), logical(1))]

if (length(hits) > 0) {
  message(
    "Blocked by project guard: this ", payload$tool_name,
    " call refers to a protected path (", paste(hits, collapse = ", "), "). ",
    "Do not modify protected files; ask the user to do it."
  )
  quit(save = "no", status = 2)
}

quit(save = "no", status = 0)

The script runs with Rscript --vanilla, so it does not start renv, and jsonlite must be installed in your user library.

Register it with Claude Code by adding a hooks key to .claude/settings.json, alongside the existing permissions key. The deny rules protect .claude/, so make this edit yourself, not through the agent.

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit|Write|Bash",
        "hooks": [
          {
            "type": "command",
            "command": "Rscript --vanilla \"$CLAUDE_PROJECT_DIR\"/hooks/guard_protected_paths.R"
          }
        ]
      }
    ]
  }
}

The matcher lists the tool names the hook runs for.

Register it with Posit Assistant in .posit/assistant/settings.json. The tool names differ: edit, bash, and executeR for R code run in your session.

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "edit|bash|executeR",
        "hooks": [
          { "type": "command", "command": "Rscript --vanilla hooks/guard_protected_paths.R" }
        ]
      }
    ]
  }
}

Posit Assistant runs project hooks only in a workspace you have trusted.

Test the hook before you trust it

Hooks fail open. If the script crashes, for example because jsonlite is not installed, both tools continue as if the hook had allowed the call. So test the script directly, without the agent. The R below runs the hook exactly as Claude Code does, a fresh Rscript --vanilla process given the tool call on standard input, and works the same on Windows, macOS and Linux.

In the R console:

rscript <- file.path(R.home("bin"), "Rscript")
hook <- shQuote(here::here("hooks", "guard_protected_paths.R"))

run_hook <- function(json) {
  system2(rscript, c("--vanilla", hook), input = json,
          stdout = FALSE, stderr = FALSE)
}

# can the hook's own R session load jsonlite? 0 means yes
system2(rscript, c("--vanilla", "-e", shQuote("library(jsonlite)")),
        stdout = FALSE, stderr = FALSE)

# a call naming a protected path: expect 2
run_hook('{"tool_name":"Bash","tool_input":{"command":"Rscript tests/make_reference.R"}}')

# a harmless call: expect 0
run_hook('{"tool_name":"Bash","tool_input":{"command":"Rscript scripts/05_analysis.R"}}')

Any result other than 2 for the first call and 0 for the second means the hook is broken and is silently allowing everything.

Now repeat the request from step 3 of Exercise 2. The R code mentions data/raw, so the guard should deny it before you see an approval prompt.

To see exactly what each tool sends to hooks, temporarily add a PostToolUse hook with no matcher that appends its input to a log file (Posit Assistant’s hooks documentation gives an example), and read the log.

Break your own guard

Red-team the tripwire

The live block removed the scratch file at the end. Recreate it first, in the R console, and commit it from the Git pane:

writeLines("a", here::here("data", "raw", "scratch.csv"))

Prompt (Claude Code):

Run this R code:
writeLines(c("a", "test"), here::here("data", "raw", "scratch.csv"))

The guard searches for the text data/raw. This call never contains it, because here::here() assembles the path from separate pieces, so the guard allows the call. A Windows path written with backslashes would also slip past.

This is the general limit of hooks that match text: they catch the obvious form of a dangerous action, not every way of expressing it. Claude Code’s documentation makes the same point about command patterns. A guard hook is a tripwire that stops accidents and makes intent visible; it is not a wall. The Git pane still shows the change. Revert the file there before moving on.

The review gate on GitHub

Local controls do not exist for an agent that works remotely, such as the Copilot cloud agent. There, the controls are on the repository itself. Neither file below is in the workshop template; you create them.

1. CODEOWNERS. Create .github/CODEOWNERS on your default branch:

/data/raw/            @your-github-username
/tests/               @your-github-username
/.github/             @your-github-username
/hooks/               @your-github-username
/.claude/             @your-github-username
/.posit/              @your-github-username

Code owners are requested for review automatically when a pull request changes the files they own. CODEOWNERS works in public repositories on free plans; for private repositories it requires a paid plan.

2. Branch protection. In the repository settings, add a rule for main that requires a pull request before merging, requires review from code owners, and requires the r-checks status check to pass. The r-checks workflow is set up in the Going further section of Block 9.

3. Test it. Open a pull request that changes a file under tests/, for example by asking the Copilot cloud agent to “update the test to use a tolerance of 1e-6”. Confirm that the pull request cannot merge until you have reviewed it.

GitHub does not let you approve your own pull request. In a repository where you are the only person, a pull request you open yourself may need an administrator override, which is a reason to test this gate with an agent’s pull request.

Feedback hooks: useful, with a warning

Hooks can do more than block. A PostToolUse hook can run lintr on each R file the agent edits and pass the result back to it. A Stop hook can run the test suite and refuse to let the agent finish while tests fail. The second is powerful and dangerous: an agent told it cannot stop until tests pass may try to change the tests. Use it only when the deny rules and guard hook protect tests/.

Glossary

term definition
branch protection GitHub repository settings that stop changes reaching a branch such as main unless conditions are met, for example a passing check and an approved review.
checksum A short fingerprint computed from a file's contents, for example with tools::md5sum(). Any change to the file changes the checksum, so it detects changes made by any route.
CODEOWNERS A GitHub file listing who must review changes to which paths. With branch protection, a pull request that touches those paths cannot merge without their review.
continuous integration Automated checks, such as tests, that run on a server each time changes are pushed or a pull request is opened. In this course, GitHub Actions.
deny rule A permission rule in the deny list of .claude/settings.json that stops Claude Code's built-in tools from editing or reading the matching files. It checks shell output redirects such as > file, but not R code or most other commands that change the same files.
hook A command the assistant runs automatically at a fixed point, for example before every tool call. A hook can block the call, but it matches text, so a differently written command can get past it.
instruction file A file the assistant loads into every conversation, such as AGENTS.md or CLAUDE.md, stating the project's standing conventions. Its contents are requests, not guarantees.
tool call A single action an agent takes, such as reading a file, editing a file or running a shell command. Permission rules and hooks act on tool calls.
