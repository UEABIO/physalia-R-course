Block 10: Checking the statistics, and reporting the results

The day ends with two checks on the analysis and its report, then a README assembled from everything your repository now holds. Each part splits the work the same way:

You own The AI writes The independent check
The original code and its output A translation Do both versions give the same output?
The numbers in your report Text around inline code Is any number typed rather than computed?
The codebook, scripts, tests, lockfile and AI-use log A README drafted from them Can every statement be traced to one of those files?

You check the agent’s work from the R console and the Git pane, as in checking work. Two more statistical checks (robustness and simulation) are in Going further.

⏱ ~30 minutes

Part A: Translation with an equivalence check

⏱ ~15 minutes

AI translates code quickly: base R to tidyverse, or SPSS, Stata or SAS to R. An equivalence checkA comparison showing that two versions of code, such as an original and an AI translation, give the same output once only presentation (types, row order) is normalised. runs both versions and compares the outputs, as in Block 9. The agent writes the translation; the shipped tests/test_translation.R, which it did not write, decides whether it is equivalent.

Translate and compare (15 minutes)

Start state: your workshop repository, committed and clean, with Claude Code in Manual mode (default) in the Terminal tab, which the repository sets.

1. Run the original. It reads voles_metabolism.csv, the clean trial data that load_voles() also reads, not Block 7’s dirty voles_raw.csv. In the R console:

library(tidyverse)
library(here)

voles <- read.csv(here("data", "raw", "voles_metabolism.csv"),
                  stringsAsFactors = TRUE)
rate_mean <- aggregate(metabolic_rate_post ~ treatment_arm + sex,
                       data = voles, FUN = mean)
rate_n <- aggregate(metabolic_rate_post ~ treatment_arm + sex,
                    data = voles, FUN = length)
names(rate_n)[3] <- "n"
legacy_summary <- merge(rate_mean, rate_n, by = c("treatment_arm", "sex"))
legacy_summary

2. Ask for a translation.

Prompt (Claude Code):

Translate this base R code into a tidyverse function summarise_rate_tidy(data)
in scripts/functions/summaries.R. It takes the tibble returned by load_voles()
and returns one row per treatment_arm and sex, with the columns treatment_arm,
sex, metabolic_rate_post (the mean) and n. Use the native pipe. Do not edit
any other file.

[paste the base R code from step 1]

Approve the edit when asked, after reading it.

3. Compare. Normalise only presentation (type and row order), never values; waldo::compare() shows what still differs. In the R console:

source(here("scripts", "functions", "load_voles.R"))
source(here("scripts", "functions", "summaries.R"))
tidy_summary <- summarise_rate_tidy(load_voles())

normalise <- function(data) {
  data |>
    as_tibble() |>
    mutate(across(where(is.factor), as.character)) |>
    arrange(treatment_arm, sex)
}

waldo::compare(normalise(tidy_summary), normalise(legacy_summary))

4. Find the difference. A different column name is presentation: ask for a rename. A different value is behaviour: find out why before reading on. No difference? Check how the translation handled the missing value anyway.

aggregate() with a formula silently drops rows with a missing value, so the animal with no metabolic_rate_post is left out of both the mean and the count. A direct translation with summarise(mean(metabolic_rate_post), n()) returns NA for that cell and counts the animal in n. Neither is “the translation”: they make different decisions about missing data. Decide which you want, write it explicitly (na.rm = TRUE and a count of non-missing values), and record the decision. It is Block 9’s “unchanged is not correct”, from a different direction.

5. Run the shipped test. Restart R (Session → Restart R), then in the R console:

testthat::test_file(here::here("tests", "test_translation.R"))

The test uses the original code as its reference. If you chose different missing-value handling, it fails, correctly: change the test’s reference and say why in your commit message.

6. Log it and commit. Add a line to docs/ai-log.md, for example:

2026-10-19; Claude Code (model as shown above the Claude Code prompt); translated summary script to tidyverse; kept the translation, matched the original's missing-value handling after the equivalence check

Then commit summaries.R and the log from the Git pane, with a message that records the missing-value decision.

You are done when test_translation.R passes in a fresh R session and your commit message records how missing values are handled.

If it goes wrong: if the agent edited anything other than summaries.R, select the file in the Git pane and choose Revert. If you run short of time, write summarise_rate_tidy() yourself from the hidden explanation above.

TipBackground: translating from SPSS, Stata or SAS

From other software, export the original’s results to a file and compare against those. Expect differences in defaults (missing values, quantiles, rounding); each needs a decision, not a looser tolerance.

Part B: Reporting without typed numbers

⏱ ~7 minutes

A typed number can be mistyped, or go stale when the data change, and an assistant drafting text may restate numbers it saw earlier. So every number in the prose comes from inline code: a code chunk computes the result, and the text calls it with `r round(primary$estimate, 2)`.

TipReference: how inline numbers look

In a code chunk of your report:

# fit the pre-registered primary analysis
library(tidyverse)
library(here)
source(here("scripts", "functions", "load_voles.R"))

voles_df <- load_voles() |>
  mutate(treatment_arm = factor(treatment_arm, levels = c("Control", "Low_dose", "High_dose")))

fit <- lm(mass_post_g ~ mass_pre_g + treatment_arm + sex, data = voles_df)
ci <- confint(fit)["treatment_armHigh_dose", ]
primary <- tibble(
  estimate = unname(coef(fit)["treatment_armHigh_dose"]),
  lower = unname(ci[1]),
  upper = unname(ci[2])
)

and in the text of the report:

High-dose voles were `r round(primary$estimate, 2)` g heavier than controls
after treatment (95% CI `r round(primary$lower, 2)` to
`r round(primary$upper, 2)` g).

Your AGENTS.md asks for this; the shipped find_typed_numbers() checks it, by listing prose lines that still contain numbers outside inline code.

Notescripts/functions/typed_numbers.R 
# scripts/functions/typed_numbers.R ----
# List the prose lines of a .qmd file that still contain numbers outside
# inline code, for you to review by eye. Years, design sizes and YAML values
# are flagged too, so treat each hit as a question, not an error.
find_typed_numbers <- function(path) {
  lines <- readLines(path, warn = FALSE)
  is_fence <- grepl("^```", lines)
  in_chunk <- cumsum(is_fence) %% 2 == 1

  tibble::tibble(line = seq_along(lines), text = lines) |>
    dplyr::filter(!in_chunk, !is_fence) |>
    dplyr::mutate(prose = gsub("`\\{?r\\}? [^`]*`", "", text)) |>
    dplyr::filter(grepl("[0-9]+\\.[0-9]+|\\b[0-9]{2,}\\b", prose, perl = TRUE)) |>
    dplyr::select(line, text)
}

Scan a report (3 minutes)

Start state: the template’s reports/example_report.qmd, an interim summary of the voles trial with some numbers typed in.

1. Scan it. In the R console:

source(here::here("scripts", "functions", "typed_numbers.R"))
find_typed_numbers(here::here("reports", "example_report.qmd")) |>
  print(n = Inf, width = Inf)

2. Sort the hits. The scan flags five lines. Decide for each one whether it is a typed result that should be inline code, or a number that is fine as text.

Lines 37 and 38 are typed results (the 1.53 g difference with its interval, and the mean of 29.4 g): both should be inline code. The other three can stay: the date in the YAML header (line 3), the design size of 12 per arm-by-sex combination (line 28), and “95%” in “95% CI” (line 34).

You are done when you can say which two lines are typed results and why the other three can stay.

If it goes wrong: if find_typed_numbers() is not found, check that the source() line ran without an error.

The same scan works on any .qmd you write, including your Quarto report from Day 3. Every hit is a question, not an error.

NoteCheck · Reproduce · Record
  • You can now: have an agent translate analysis code and draft a README, trusted because shipped tests compare the translation with the original and the README with its sources, and the whole suite passes in a fresh R session.
  • Check: an equivalence test between the original and the translation; a scan for typed numbers; every README statement traced to a file.
  • Reproduce: numbers come from code, so the report updates when the data do; the README’s dependencies come from renv.lock, not from memory.
  • Record: the README and the AI-use log complete the record. Together with the codebook, logs, tests and lockfile, they are what a reviewer, a co-author or you in a year’s time will need.

TipRobustness, not choice

AI should not choose your primary analysis. The BLADE benchmark compared language-model agents with expert analysts on open-ended research questions. It found that the models were often limited to basic analyses, and that agents able to explore the data made more varied but still sub-optimal analytical decisions (Gu et al., 2024). Its useful role is narrower: listing defensible alternatives to an analysis you have already fixed, so you can check whether your conclusion depends on the choice.

Run the steps yourself, and judge each answer before running it.

Enumerate, judge, run

1. Ask for alternatives, not a recommendation:

My pre-registered primary analysis is an ANCOVA:
mass_post_g ~ mass_pre_g + treatment_arm + sex, estimating the High_dose
versus Control difference. List alternative specifications a reasonable
analyst might use for the same question, and for each, say whether it
estimates the same quantity. Do not recommend one.

2. Judge each one yourself. Mark each alternative defensible or not, with a reason. Check especially whether it estimates the same quantity.

3. Run the defensible ones and report them beside the primary analysis.

library(tidyverse)
library(here)
source(here("scripts", "functions", "load_voles.R"))

voles_df <- load_voles() |>
  mutate(treatment_arm = factor(treatment_arm, levels = c("Control", "Low_dose", "High_dose")))

specs_df <- tribble(
  ~spec,                       ~formula,
  "Primary: ANCOVA",           "mass_post_g ~ mass_pre_g + treatment_arm + sex",
  "Change score",              "I(mass_post_g - mass_pre_g) ~ treatment_arm + sex",
  "ANCOVA with arm-by-sex",    "mass_post_g ~ mass_pre_g + treatment_arm * sex"
)

spec_results_df <- specs_df |>
  mutate(result = map(formula, \(f) {
    fit <- lm(as.formula(f), data = voles_df)
    ci <- confint(fit)["treatment_armHigh_dose", ]
    tibble(
      estimate = unname(coef(fit)["treatment_armHigh_dose"]),
      lower = unname(ci[1]),
      upper = unname(ci[2])
    )
  })) |>
  unnest(result)

spec_results_df

In the third specification, the coefficient treatment_armHigh_dose is the High_dose effect in females only (the reference level of sex), because the model includes an interaction. It sits in the same column as the other estimates but answers a different question. It belongs in a separate analysis of whether the effect differs by sex, not in a table of estimates of the same quantity. An AI that lists it as an “alternative” without saying so has made exactly the error step 2 asks you to catch.

Warning

Running many specifications and reporting the one you like best is selective reporting. The primary analysis is fixed in advance; the others are reported as sensitivity analyses whatever they show.

Check your understanding: robustness

Why should the arm-by-sex interaction model not appear in the same robustness table as the primary ANCOVA?

TipSimulation and parameter recovery

If you simulate data from a mechanism whose parameters you chose, a correct analysis should recover those parameters on average, and its 95% confidence intervals should contain the true values about 95% of the time. This tests the analysis code against a known answer, which real data never provide.

Morris, White and Crowther (2019) give a structure for planning simulation studies: the aims, the data-generating mechanism, the estimand, the methods and the performance measures (ADEMP). Here:

  • Aim: check that the analysis code estimates the high-dose effect correctly.
  • Data-generating mechanism: 12 voles per arm-by-sex cell. Pre-treatment mass is normal with mean 28 g and SD 2 g. Post-treatment mass equals 2.8 g plus 0.9 times pre-treatment mass, plus 0.8 g for Low_dose, plus 1.5 g for High_dose, plus 1.0 g for males, plus normal error with SD 0.8 g.
  • Estimand: the difference in post-treatment mass between High_dose and Control, adjusted for pre-treatment mass and sex. True value: 1.5 g.
  • Method: linear model (ANCOVA), mass_post_g ~ mass_pre_g + treatment_arm + sex.
  • Performance measures: bias and confidence-interval coverage, each with its Monte Carlo standard error.

The written mechanism is yours. It is the equivalent of the codebook in Block 7: the AI turns it into code, and you check the code against it.

Write, check, recover

1. Simulation code. Give the AI the data-generating mechanism above, word for word, and ask for a function simulate_voles() returning a tibble with columns treatment_arm, sex, mass_pre_g and mass_post_g.

2. Check the simulated data against the specification. Before using the function, run it once and check that it matches what you wrote:

set.seed(1)
sim_df <- simulate_voles()
sim_df |> count(treatment_arm, sex)            # 12 per cell?
sim_df |> summarise(mean(mass_pre_g), sd(mass_pre_g))
sim_df |>
  summarise(mean_post = mean(mass_post_g), .by = c(treatment_arm, sex))

High_dose should be about 1.5 g above Control within each sex, and males about 1 g above females. If not, the simulation is wrong, and nothing built on it can be trusted.

3. Analysis code, in a separate session. Without showing it the simulation code, ask the AI for a function estimate_high_vs_control(data) that fits the model above and returns the High_dose estimate and its 95% confidence interval.

4. Run the recovery.

simulate_voles <- function(n_per_cell = 12, effect_low = 0.8,
                           effect_high = 1.5, sex_effect = 1.0,
                           slope_pre = 0.9, sd_pre = 2, sd_resid = 0.8) {
  tidyr::expand_grid(
    treatment_arm = c("Control", "Low_dose", "High_dose"),
    sex = c("F", "M"),
    animal = seq_len(n_per_cell)
  ) |>
    dplyr::mutate(
      mass_pre_g = stats::rnorm(dplyr::n(), mean = 28, sd = sd_pre),
      arm_effect = dplyr::case_when(
        treatment_arm == "Low_dose" ~ effect_low,
        treatment_arm == "High_dose" ~ effect_high,
        .default = 0
      ),
      mass_post_g = 28 * (1 - slope_pre) + slope_pre * mass_pre_g +
        arm_effect + sex_effect * (sex == "M") +
        stats::rnorm(dplyr::n(), sd = sd_resid)
    ) |>
    dplyr::select(treatment_arm, sex, mass_pre_g, mass_post_g)
}

estimate_high_vs_control <- function(data) {
  data <- dplyr::mutate(
    data,
    treatment_arm = factor(treatment_arm, levels = c("Control", "Low_dose", "High_dose"))
  )
  fit <- stats::lm(mass_post_g ~ mass_pre_g + treatment_arm + sex, data = data)
  ci <- stats::confint(fit)["treatment_armHigh_dose", ]
  tibble::tibble(
    estimate = unname(stats::coef(fit)["treatment_armHigh_dose"]),
    lower = unname(ci[1]),
    upper = unname(ci[2])
  )
}
set.seed(2026)
n_sim <- 1000
true_effect <- 1.5

results_df <- seq_len(n_sim) |>
  map(\(i) estimate_high_vs_control(simulate_voles(effect_high = true_effect))) |>
  list_rbind()

results_df |>
  summarise(
    bias          = mean(estimate) - true_effect,
    bias_mcse     = sd(estimate) / sqrt(n_sim),
    coverage      = mean(lower <= true_effect & upper >= true_effect),
    coverage_mcse = sqrt(coverage * (1 - coverage) / n_sim),
    empirical_se  = sd(estimate)
  )

Bias should be within about two Monte Carlo standard errors of zero. Coverage should be within about two Monte Carlo standard errors of 0.95, roughly 0.936 to 0.964 with 1,000 runs.

5. Prove the check can fail. Replace the analysis with a version that models the change the wrong way round, as in Block 3:

estimate_buggy <- function(data) {
  data <- dplyr::mutate(
    data,
    treatment_arm = factor(treatment_arm, levels = c("Control", "Low_dose", "High_dose")),
    mass_change_g = mass_pre_g - mass_post_g
  )
  fit <- stats::lm(mass_change_g ~ treatment_arm + sex, data = data)
  ci <- stats::confint(fit)["treatment_armHigh_dose", ]
  tibble::tibble(
    estimate = unname(stats::coef(fit)["treatment_armHigh_dose"]),
    lower = unname(ci[1]),
    upper = unname(ci[2])
  )
}

Rerun the recovery with estimate_buggy(). Bias should be about −3 g and coverage near zero. A check you have never seen fail is a check you are assuming works.

Warning

What recovery does not prove. It shows that the code estimates the right quantity under the mechanism you simulated. It says nothing about whether real voles behave like that. A change-score model fitted to these simulated data would also be nearly unbiased (randomisation makes both estimators valid), but less precise; compare empirical_se to see the cost. Recovery tests code, not scientific assumptions.

Check your understanding: simulation

A simulation recovers the true effect with negligible bias and 95% coverage. What has it shown?
