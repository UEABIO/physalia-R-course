Block 5: Generalising functions with tidy evaluation

Roughly 50 minutes. First why a column name stops working once you pass it into your own function, and the four patterns that fix it; then those patterns applied to the running example, so that make_scatter_plot() and fit_model() work for any pair of columns.

Block 4 left one limitation. One pipeline now fits a model per group, whatever the group is, but fit_model() still fits only body mass on flipper length, and make_scatter_plot() from Block 3 still plots only those two columns. The fix is to make the columns arguments, and that is where dplyr’s convenience bites. It lets you type a column name as if it were an ordinary object, but inside your own function the name arrives inside an argument, one step removed, and you have to tell dplyr to look inside.

The examples use penguins_clean, cleaned in Block 3 from data/raw/penguins_raw.csv. Starting a fresh session? Run Block 3’s loading and cleaning lines first (Which penguins?).

The problem

A first, reasonable attempt that does not work:

summarise_by_species <- function(data, var) {
  data |>
    dplyr::summarise(mean = mean(var, na.rm = TRUE), .by = species)
}

summarise_by_species(penguins_clean, body_mass_g)
# Error in `dplyr::summarise()`:
# ℹ In argument: `mean = mean(var, na.rm = TRUE)`.
# ℹ In group 1: `species = "Adelie"`.
# Caused by error:
# ! object 'body_mass_g' not found

The function received var = body_mass_g, and body_mass_g is plainly a column of penguins_clean. Yet the error says it cannot be found. Why?

Two meanings of “variable”

dplyr’s own guide to programming (vignette("programming", package = "dplyr")) explains this by splitting the word “variable” in two:

  • An env-variable is a programming object that lives in your R session or in a function. You make one with <-, or it arrives as a function argument.
  • A data-variable is a column that lives inside a data frame.
df <- tibble::tibble(x = 1:3)   # df is an env-variable
df$x                            # x is a data-variable inside it

Inside filter(), mutate(), summarise() and friends, dplyr lets you type a data-variable as if it were an env-variable: summarise(mean = mean(body_mass_g)) finds the column. This is data masking: the data frame “masks” your session, so its columns are found first. It is what makes interactive dplyr so pleasant.

The trouble starts with indirection: the column name is no longer typed in the verb, but held in an env-variable, here the argument var. dplyr sees the name var, finds no column called var, and never discovers that var holds the column name you meant.

Think of the argument as an envelope with a column name written inside. dplyr reads the label on the envelope (var), not what is inside it. You need to tell it to open the envelope.

NoteWhy exactly does the error say body_mass_g?

dplyr looks for a column called var, does not find one, and so falls back to the function’s own objects, where it finds the argument var. R evaluates arguments lazily: only now does it work out what var holds, by evaluating the expression the user typed, body_mass_g. It evaluates that in the calling environment, your workspace, not inside the data frame. Your workspace has no object called body_mass_g, hence “object ‘body_mass_g’ not found”. The data mask was applied to the name var, never to the column name the user meant.

Embracing: { }

The embracing operator { } opens the envelope: it tells dplyr “the user handed me a column name; use that, not the word var”.

summarise_by_species <- function(data, var) {
  data |>
    dplyr::summarise(mean = mean({{ var }}, na.rm = TRUE), .by = species)
}

summarise_by_species(penguins_clean, body_mass_g)
# # A tibble: 3 x 2
#   species    mean
#   <chr>     <dbl>
# 1 Adelie    3701.
# 2 Gentoo    5076.
# 3 Chinstrap 3733.

Embrace the column every time it appears, and embrace the grouping column too if it is an argument:

summary_grouped <- function(data, var, group) {
  data |>
    dplyr::summarise(
      mean = mean({{ var }}, na.rm = TRUE),
      sd   = sd({{ var }}, na.rm = TRUE),
      .by  = {{ group }}
    )
}

summary_grouped(penguins_clean, body_mass_g, species)
summary_grouped(penguins_clean, body_mass_g, island)

Only arguments that name columns are embraced. A threshold, a confidence level or a file name is an ordinary value: use it as it is.

NoteUnder the hood (optional)

{ var } is shorthand for !!enquo(var). rlang::enquo() captures the argument as a quosure (the expression plus the environment it came from), and !! injects it back into the verb. You almost never need to write enquo()/!! by hand, but seeing the expansion demystifies the braces: they capture, then inject.

Activity 1: fix the broken function

Activity 1: fix the broken function

Identify the problem and fix it.

my_filter <- function(data, var, threshold) {
  data |> dplyr::filter(var > threshold)
}
my_filter(penguins_clean, body_mass_g, 4000)
# Error in `dplyr::filter()`:
# ℹ In argument: `var > threshold`.
# Caused by error:
# ! object 'body_mass_g' not found

filter() uses data masking, but var is not embraced, so dplyr reads the label on the envelope: it looks for a column called var, fails, and falls back to the argument, which evaluates body_mass_g outside the data. Embrace var:

my_filter <- function(data, var, threshold) {
  data |> dplyr::filter({{ var }} > threshold)
}

threshold does not need embracing: it is an ordinary number, not a column name.

Two kinds of column argument

Column names are used in two different ways in the tidyverse:

Data masking Tidy selection
What the column name does Stands for the column’s values, which you compute with Labels a column you want to pick
Typical code filter(body_mass_g > 4000), mutate(kg = body_mass_g / 1000), summarise(m = mean(body_mass_g)), arrange(desc(body_mass_g)), aes(x = body_mass_g) select(species, body_mass_g), select(starts_with("bill")), pivot_longer(cols = ends_with("_mm")), across(.cols = where(is.numeric)), .by = species
Helpers such as starts_with(), where() No Yes

To filter penguins by mass you compute body_mass_g > 4000 for every row: the values matter, so it is data masking. To select the mass column you compute nothing; only the name matters, so it is tidy selection.

How to tell, without memorising. Two quick tests:

  1. Read the help page. In ?filter or ?select, each argument is labelled <data-masking> or <tidy-select>.
  2. Ask what you could write there. If you could write body_mass_g + 1, it is data masking. If you could write bill_length_mm:body_mass_g or starts_with("bill"), it is tidy selection. (This test comes from R for Data Science, chapter 25.)

Either way, a bare column name passed through your function is embraced with { }. The two kinds differ only when the name arrives as a string, which is the next section.

For each call, choose whether the column reference is data masking, tidy selection, or both (in different arguments).

  1. filter(penguins_clean, body_mass_g > 4000)
  2. select(penguins_clean, species, body_mass_g)
  3. mutate(penguins_clean, mass_kg = body_mass_g / 1000)
  4. pivot_longer(penguins_clean, cols = ends_with("_mm"))
  5. summarise(penguins_clean, mean(body_mass_g), .by = species)
  6. select(penguins_clean, starts_with("bill"))
  7. arrange(penguins_clean, desc(body_mass_g))
  8. filter_out(penguins_clean, body_mass_g > 4000)
  9. summarise(penguins_clean, across(where(is.numeric), mean))
  1. Data masking. A comparison is computed for every row.
  2. Tidy selection. Columns picked by name.
  3. Data masking. A new value computed from existing values.
  4. Tidy selection (the cols argument).
  5. Both. mean(body_mass_g) is data masking; .by is tidy selection (it picks the grouping column by name).
  6. Tidy selection. A helper picks by name pattern.
  7. Data masking. Sorting by computed values.
  8. Data masking. A comparison is computed for every row, as in filter().
  9. Both. summarise() is data masking, and across() is used inside it, but across()’s .cols argument is tidy selection, so where() works there. across() is the bridge between the two kinds; Activity 4 uses it.

When the name arrives as a string

So far the column name arrived bare, as the user typed it. Often it arrives as a string instead: from a vector of names you loop over, a configuration file, or a Shiny input. { } is for bare names only. A string needs a different pattern, and here the two kinds of argument part ways:

  • Data masking: look the string up with the .data pronoun, .data[[var_name]].
  • Tidy selection: wrap the string, or a character vector of strings, in all_of().

The commonest reason for strings is a loop over column names, as in Block 4:

for (var in c("bill_length_mm", "flipper_length_mm")) {
  penguins_clean |>
    dplyr::summarise(mean = mean(.data[[var]], na.rm = TRUE), .by = species) |>
    print()
}
# # A tibble: 3 x 2
#   species    mean
#   <chr>     <dbl>
# 1 Adelie     38.8
# 2 Gentoo     47.5
# 3 Chinstrap  48.8
# # A tibble: 3 x 2
#   species    mean
#   <chr>     <dbl>
# 1 Adelie     190.
# 2 Gentoo     217.
# 3 Chinstrap  196.

In the envelope picture, .data[[var]] says: “this envelope holds a string; find the column with that name”. .data is not a data frame you can use elsewhere: it works only inside data-masking verbs.

The same idea, wrapped in a function:

summarise_by_string <- function(data, var_name) {
  data |>
    dplyr::summarise(mean = mean(.data[[var_name]], na.rm = TRUE), .by = species)
}

summarise_by_string(penguins_clean, "body_mass_g")

Activity 3: fix the warning

Activity 3: fix the warning

This one runs, but not cleanly. Identify and fix the problem.

keep_columns <- function(data, cols) {
  data |> dplyr::select(cols)
}
keep_columns(penguins_clean, c("species", "body_mass_g"))
# Warning message:
# Using an external vector in selections was deprecated in tidyselect 1.1.0.
# ℹ Please use `all_of()` or `any_of()` instead.
#   # Was:
#   data %>% select(cols)
#
#   # Now:
#   data %>% select(all_of(cols))

It returns the right two columns, but only because tidyselect guesses that cols is an external character vector of names rather than a column called cols. That guess is ambiguous (if the data ever gained a column named cols, it would be selected instead) and is deprecated, so it warns today and may error in future. Say what you mean by wrapping the vector in all_of():

keep_columns <- function(data, cols) {
  data |> dplyr::select(dplyr::all_of(cols))
}

If instead the function takes a bare name, embracing works: select({{ cols }}). The right tool depends on how the input arrives: bare ({ }) or as strings (all_of()).

Activity 4: predict the result

Activity 4: predict the result

Before running anything, predict what each call does: does it succeed, return the wrong answer, or error? Then explain why, using the envelope picture.

# (i) embracing a string
summarise_mean <- function(data, var) {
  data |> dplyr::summarise(mean = mean({{ var }}, na.rm = TRUE), .by = species)
}
summarise_mean(penguins_clean, "body_mass_g")

# (ii) a string into a data-masking verb without .data
summarise_mean_str <- function(data, var_name) {
  data |> dplyr::summarise(mean = mean(var_name, na.rm = TRUE), .by = species)
}
summarise_mean_str(penguins_clean, "body_mass_g")

Both return the wrong answer, with only a warning: a column of NA.

  1. { } opens the envelope and finds the string "body_mass_g", not a column name. mean() then receives a single piece of text, and the mean of a piece of text is NA, with the warning “argument is not numeric or logical: returning NA”. Embracing is for bare names; a string needs .data[[ ]].

  2. var_name is not embraced, so dplyr looks for a column called var_name, fails, and finds the argument, which holds the string "body_mass_g". It computes the mean of that string: NA again. Nothing told dplyr to treat the string as a column name; that is the job of .data[[var_name]].

The general lesson: passing the wrong kind of name to a data-masking verb rarely errors loudly. It often produces NA with at most a warning, which is more dangerous than an error. Match the pattern to how the name arrives.

The bridge: across()

Sometimes you need both kinds in one call: pick several columns, then compute with each. across() does exactly that. It is used inside a data-masking verb such as summarise() or mutate(), and its .cols argument is tidy selection, so all_of(), starts_with() and where() all work there.

Activity 5: the bridge

Activity 5: the bridge

Write mean_of_columns(data, cols) that takes a character vector of column names and returns the mean of each, grouped by species.

mean_of_columns <- function(data, cols) {
  data |>
    dplyr::summarise(
      dplyr::across(dplyr::all_of(cols), \(x) mean(x, na.rm = TRUE)),
      .by = species
    )
}

mean_of_columns(penguins_clean, c("body_mass_g", "flipper_length_mm"))
# # A tibble: 3 x 3
#   species   body_mass_g flipper_length_mm
#   <chr>           <dbl>             <dbl>
# 1 Adelie          3701.              190.
# 2 Gentoo          5076.              217.
# 3 Chinstrap       3733.              196.

The strings arrive in .cols, a tidy-selection argument, so they are wrapped in all_of(). The function \(x) mean(x, na.rm = TRUE) is then applied to each selected column. If the user should pass bare names or helpers instead, embrace the argument: across({{ cols }}, ...) accepts c(body_mass_g, bill_length_mm) or ends_with("_mm").

Naming the output columns

For output column names built from an argument, = is not enough: with = the name is used literally, so "{{ var }}_mean" = … makes a column called { var }_mean. The walrus operator := lets rlang fill in { var }, using glue-style name injection:

summarise_dynamic <- function(data, var) {
  data |>
    dplyr::summarise(
      "{{ var }}_mean" := mean({{ var }}, na.rm = TRUE),
      "{{ var }}_sd"   := sd({{ var }}, na.rm = TRUE),
      .by = species
    )
}

summarise_dynamic(penguins_clean, body_mass_g)
# # A tibble: 3 x 3
#   species   body_mass_g_mean body_mass_g_sd
#   <chr>                <dbl>          <dbl>
# 1 Adelie               3701.           459.
# 2 Gentoo               5076.           504.
# 3 Chinstrap            3733.           384.

Two things happen on the left of :=. "{{ var }}_mean" is glue-style injection, replacing { var } with the argument’s name; := is the assignment that lets rlang do that injection (with = the name is used literally). Both are needed. If the name is held in a string instead, use single braces: "{var_name}_mean" :=.

The same trick works for text that is not a column name, such as a plot title or axis label: rlang::englue("Mean of {{ var }}") returns the string "Mean of body_mass_g". The payoff uses it.

Choosing the pattern

The patterns above each answer one combination of two questions:

  1. How does the column name arrive? Bare, as the user typed it; or as a string or character vector?
  2. What kind of argument receives it? Data masking or tidy selection (check the help page)?
The name arrives as… …into data masking …into tidy selection
A bare name { var } { var }
A string .data[[var]] all_of(var)
A character vector across(all_of(vars), f) all_of(vars)

And for new output names: "{{ var }}_mean" := (bare) or "{var_name}_mean" := (string). Memorise the first row; the rest is reference.

For each scenario, name the correct pattern from the table, then write the function. (a), (b) and (d) group by species.

  1. var arrives as a bare name; compute its mean (data masking).

  2. var_name arrives as a string; compute its mean (data masking).

  3. cols arrives as a character vector; select those columns (tidy selection).

# (a) bare name, data masking -> {{ }}
summarise_mean <- function(data, var) {
  data |>
    dplyr::summarise(mean = mean({{ var }}, na.rm = TRUE), .by = species)
}

# (b) string, data masking -> .data[[ ]]
summarise_mean_str <- function(data, var_name) {
  data |>
    dplyr::summarise(mean = mean(.data[[var_name]], na.rm = TRUE), .by = species)
}

# (c) character vector, tidy selection -> all_of()
select_cols <- function(data, cols) {
  data |>
    dplyr::select(species, dplyr::all_of(cols))
}

# (d) bare name, new output name -> {{ }} with :=
summarise_named <- function(data, var) {
  data |>
    dplyr::summarise("{{ var }}_mean" := mean({{ var }}, na.rm = TRUE), .by = species)
}

The decision procedure: first ask whether the name arrives bare or as a string; a bare name is always { }. For a string or vector, ask what kind of argument receives it: data masking (.data[[ ]]) or tidy selection (all_of()).

The payoff: generalising the pipeline

Until now this block has practised on small, stand-alone functions. Now go back to the analysis you have been improving all day. Blocks 3 and 4 left two functions that hardcode the same pair of columns: make_scatter_plot() in R/functions/plotting_functions.R, and fit_model() in R/functions/modelling_functions.R.

make_scatter_plot <- function(data, sp) {
  data |>
    dplyr::filter(species == sp) |>
    ggplot2::ggplot(ggplot2::aes(flipper_length_mm, body_mass_g)) +
    ggplot2::geom_point(alpha = 0.6) +
    ggplot2::geom_smooth(method = "lm") +
    ggplot2::labs(title = sp, x = "Flipper length (mm)", y = "Body mass (g)") +
    ggplot2::theme_minimal()
}

fit_model <- function(data) {
  lm(body_mass_g ~ flipper_length_mm, data = data)
}

You generalise both, so that each works for any pair of columns:

  • Activity 7, the plot. aes() uses data masking, so this is the main pattern of the block, { }, plus englue() from Naming the output columns for the axis labels.
  • Activity 8, the model. lm() is not a tidyverse function, so { } does not work there. This activity shows what to do instead, and when to take column names as strings.

In both, the new arguments default to the columns the functions use now. Existing calls, including the Block 4 pipeline, keep working unchanged, and the characterisation test at the end of this section checks that they do. Edit each function in its file, then source() the file again.

Activity 8: generalise the model

Activity 8: generalise the model

Now let fit_model() fit any response on any predictor, defaulting to body mass on flipper length. First, predict: does this work?

fit_model <- function(data,
                      response  = body_mass_g,
                      predictor = flipper_length_mm) {
  lm({{ response }} ~ {{ predictor }}, data = data)
}

Then find a version that does work. Hint: lm() is base R, not the tidyverse. How does base R already let you pass column names to lm() without evaluating them?

It does not work:

fit_model(penguins_clean)
# Error in eval(mf, parent.frame()) : object 'body_mass_g' not found

{ } is understood only by functions that use tidy evaluation: dplyr, tidyr and ggplot2’s aes(). lm() is not one of them, so to it { response } is just response wrapped in two pairs of braces, and the column name is never found.

Base R already has its own way to pass column names without evaluating them: the formula. So the simplest generalisation takes a formula:

fit_model <- function(data, formula = body_mass_g ~ flipper_length_mm) {
  lm(formula, data = data)
}

fit_model(penguins_clean)                                 # as before
fit_model(penguins_clean, bill_length_mm ~ bill_depth_mm) # new

No tidy evaluation at all. The lesson: before reaching for { }, check whether the function you are calling is a tidyverse function. If it is not, it usually has its own way of taking column names.

When the names come from a vector. To fit the same model to several responses, as you iterated in Block 4, take the names as strings and build the formula with base R’s reformulate():

fit_model <- function(data,
                      response  = "body_mass_g",
                      predictor = "flipper_length_mm") {
  lm(reformulate(predictor, response = response), data = data)
}

c("body_mass_g", "bill_length_mm") |>
  purrr::set_names() |>
  purrr::map(\(r) fit_model(penguins_clean, r)) |>
  purrr::map(broom::tidy) |>
  purrr::list_rbind(names_to = "response")
# # A tibble: 4 x 6
#   response       term               estimate std.error statistic   p.value
#   <chr>          <chr>                 <dbl>     <dbl>     <dbl>     <dbl>
# 1 body_mass_g    (Intercept)       -5781.     306.        -18.9  5.59e- 55
# 2 body_mass_g    flipper_length_mm    49.7      1.52       32.7  4.37e-107
# 3 bill_length_mm (Intercept)          -7.26     3.20       -2.27 2.38e-  2
# 4 bill_length_mm flipper_length_mm     0.255    0.0159     16.0  1.74e- 43

predictor can also be a vector, such as c("flipper_length_mm", "bill_depth_mm"), for a model with two predictors. Strings are the right choice whenever the names come from a vector, a loop or a file: the same reason you met .data[[ ]] and all_of().

TipOptional: bare names for lm()

If you want fit_model(penguins_clean, bill_length_mm, bill_depth_mm) with bare names, you must inject the names into the call yourself, with rlang:

fit_model <- function(data,
                      response  = body_mass_g,
                      predictor = flipper_length_mm) {
  rlang::inject(
    lm(!!rlang::ensym(response) ~ !!rlang::ensym(predictor), data = data)
  )
}

rlang::ensym() captures the bare name the user typed, and !! inside rlang::inject() places it into the formula before lm() sees it. This works, but it is the kind of rlang machinery that most code never needs; the formula and string versions above are simpler to read and to test.

When you change a function’s interface, pin the old behaviour down first with a characterisation test, then confirm the change preserves it. Both versions of fit_model() above pass this test with their defaults:

test_that("fit_model defaults reproduce previous behaviour", {
  m_old <- lm(body_mass_g ~ flipper_length_mm,
              data = test_data |> dplyr::filter(species == "Adelie"))
  m_new <- fit_model(test_data |> dplyr::filter(species == "Adelie"))
  expect_equal(coef(m_old), coef(m_new))
})

  • Not a tidyverse function? { } does nothing there. Look for its own way of taking column names, such as a formula for lm().

rlang has more machinery (enquo(), !!, enquos(), !!!), but most code never needs it.

Note

Where this leaves us. The analysis that began Block 3 as three copy-pasted blocks is now a set of small, tested functions, applied to every group by one pipeline, with no hardcoded columns: make_scatter_plot() and fit_model() take whichever columns you name. Day 2 asks whether someone else could rerun it: reproducibility and code review.
