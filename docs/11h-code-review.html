Block 8: AI-assisted code review

You will hand a script to an AI reviewer and grade what it finds. Because you already know this script’s twelve problems, you can measure the machine rather than trust it.

Note

Before you start. You need the OSF project folder from https://osf.io/jgeq9/ (ANALYSIS.R and its data) and your P1–P12 catalogue from the manual code-review chapter, which is the answer key. No catalogue? Your instructor shares it after Part 3; don’t look before your review has run.

⏱ ~40 minutes

Part 1: What AI is, and is not, good for in code review

⏱ ~5 minutes

An AI reviewer reads every line and never tires, but it sounds equally sure whether it is right or wrong. Here is where to expect help, on the four Rs of code review (Ivimey-Cook et al., 2023):

AI capability mapped onto the four Rs
R AI is likely to be... Why
Reported Useful for drafting It can summarise what the script appears to do and flag missing documentation or undocumented exclusions. It cannot know the intended analysis unless you state it.
Run Strong, if it can execute An agent that runs the script in a fresh R session can show whether it runs. A chat window can only predict, and its prediction can read as though it ran the code.
Reliable Weak Silent semantic errors (P4 precedence, P8 sentinel, P9 incomparable models, P10 wrong family) depend on context. Expect some caught, some missed and some invented, all in the same confident tone.
Reproducible Mixed It can flag a missing lockfile or session record. It can confirm that results reproduce only by running the code and comparing outputs.

The rule: treat every AI finding as a claim to check, and the absence of a finding as no evidence that the problem is absent.

Used that way, AI review is reliably good for:

  • summarising what an unfamiliar script does;
  • flagging missing documentation, unexplained filters and hard-coded paths;
  • finding run errors, when it can actually execute the code;
  • a second pair of eyes that never tires on line 300.

So next week, run your saved review prompt on a script before you share it, and spend your own attention on the Reliable questions. In software engineering, developers acted on about three-quarters of an AI reviewer’s comments but saw only minor gains in quality, and the reviewer did worse when it was not told what the code was meant to do (Cihan et al., 2025; Cihan, 2025). Nobody has measured it on analysis scripts like this one, which is what you will do.

Part 2: Telling the AI how to behave

⏱ ~10 minutes

“Review my code” gets a vague, generous review. A good review prompt has four parts:

Part Why
A role and a standard: “a critical reviewer applying the four Rs” Gives the output a structure you can check
The intended analysis: the model from the OSF page, with TO a count and block B a random effect Without it, the AI cannot see that a Gaussian lmer() is the wrong family (P10)
No flattery: line number, which R, severity, a fix Keeps it to findings you can act on
Honest uncertainty: “NEEDS HUMAN CHECK” instead of guessing Shows you where to look yourself

Write the review prompt (7 minutes)

1. Start from the draft below and check it has all four parts.

2. Split the room. Surnames A–M are Group A and keep the line about the 9999 sentinel valueA number with a special meaning, such as 9999 for “not recorded” or -1 for “run failed”. It must be documented in a codebook and recoded before analysis.; N–Z are Group B and delete it. Everything else stays the same.

3. Keep it. In your workshop project, run usethis::edit_file("docs/review-prompt.md") in the R console, paste your prompt and save. You will reuse it after the course.

You are done when your prompt has all four elements and is saved in docs/review-prompt.md.

Prompt (Claude Code, or a chat window):

You are a critical code reviewer for an evolutionary-biology journal.
Review ANALYSIS.R using the four Rs: Reported, Run, Reliable, Reproducible.

The intended analysis (from the pre-registration) is:
  total offspring (TO, a count: non-negative integer, often overdispersed)
  modelled as TO ~ strain * diet + (1 | B), with block B as a random effect.

Rules:
- Do NOT praise the code. Report only problems.
- For each issue: line number(s), which R it violates, severity
  (critical / high / medium), and a concrete one-line fix.
- The raw data use 9999 as a "not recorded" code. Check whether this is
  handled.                                      <- Group B: delete this line
- Flag anything you CANNOT determine by reading alone as "NEEDS HUMAN
  CHECK" rather than guessing.
- If you are uncertain about a finding, say so explicitly.
Organise your output by the four Rs.

Read the approval prompt, then the output. “The script runs” counts only if you can see the command and its output in the conversation; without them it is a claimed executionA statement that code runs or reproduces, made without the command that was run and the output it produced. Path B: chat window

If you have no agent, paste the whole of ANALYSIS.R into any chat window, followed by your Part 2 prompt. Paste the script only, not the data.

Warning

A chat window cannot run anything, but its answer to “does this run?” can read as though it did. Ask “what would prevent this running?” instead.

Grade the machine (10 minutes)

1. Score the review. Open your P1–P12 catalogue beside the AI’s review:

  • Hits: which of P1–P12 did it identify correctly?
  • Misses: which did it miss? Look especially at P4 (precedence) and P8 (sentinel), the silent, consequential ones.
  • False positives: what did it flag that is not a real problem, or describe wrongly? Each one is a false positiveIn a code review, a problem the AI reports confidently that is not real, or describes wrongly..
  • Execution claims: did it claim the script runs or reproduces? On what evidence?

2. Post your result. In the chat, post your group (A or B), your hit count, your most consequential miss and your most confident false positive, with line numbers.

3. Decide. Which one finding would you act on first, and what would you check before acting on it?

You are done when every P1–P12 problem is marked hit or miss, and you have listed the false positives.

If it goes wrong: if your review never arrived, grade a neighbour’s review posted in the chat; the comparison works the same way.

NoteDebrief (5 minutes)
  1. Compare P8 hit rates between Groups A and B. Only the data and your knowledge reveal that 9999 is a code: what does that say about reviewing code without the data?
  2. Whose AI produced the most confident false positive?
  3. Did any agent claim the script runs without having run it?
  4. Back to the opening poll: would you change your answer?

  • You can now: hand a script to an AI reviewer with a prompt that makes its output checkable, trusted because you grade it against problems you already know, and treat every finding as a claim.
  • Check: grade every AI finding against the P1–P12 answer key; the absence of a finding is no evidence that the problem is absent.
  • Reproduce: a claim that the script runs counts only with the command and the output from a fresh R session; to run one yourself, see checking work.
  • Record: add a line to docs/ai-log.md in your workshop repository: the tool, its hit count and its most confident false positive. An AI-assisted README for the OSF project is in Going further.

Generating the README with AI

⏱ ~20 minutes

The second deliverable is the documentation that makes Reported and Run answerable: a README. You are provided with the research-readme skill: a SKILL.md, two helper scripts and a template.

Install the skill before you start. Download the bundle and unzip it into the OSF project folder at .agents/skills/, so that the folder .agents/skills/research-readme/ contains SKILL.md, scripts/ and references/.

  • Posit Assistant and GitHub Copilot read .agents/skills/ directly.
  • Claude Code reads .claude/skills/. Link or copy the folder there, as described in Block 5.
  • Chat window: you do not need to install anything. You will run the two scripts yourself and paste the template into the chat.

Check that the skill is visible before going on. In Claude Code, type / and look for research-readme. In any tool, the test is behaviour: when you invoke /research-readme in Pass 2, its first reply should be the numbered plan that the skill’s “Before executing” section requires. If it is not, the skill did not load.

Put the folder under version control first. A folder downloaded from OSF is not a git repository, so there would be nothing to compare the README against. With the OSF project open in RStudio or Positron, run usethis::use_git() in the R console and let it make the first commit.

You run this in two passes. The first shows the failure; the second shows the fix.

Pass 1: README from the AI alone (~4 minutes)

Give the AI only ANALYSIS.R and the data, and ask for a README with no constraints. The result reads as complete. It will assign plausible units, describe variables it cannot have verified, and may state package versions it has no way to know. Note what it asserts about the variables and dependencies; Pass 2 replaces each guess with a fact you generate.

Pass 2: README from verifiable inputs

The skill’s rules are that the AI must not fabricate metadata, and that automatic summaries describe; they do not interpret. So you generate the facts mechanically, and the AI only assembles and phrases them.

Step 1: Generate the inputs yourself (R, not AI)

In the R console, with the OSF project open in RStudio or Positron (so that here::here() points at it, not at your workshop repository):

skill_dir <- here::here(".agents", "skills", "research-readme", "scripts")

source(file.path(skill_dir, "describe_csv.R"))
# type, missing count and range per column, printed in full for pasting
describe_project_csvs(here::here()) |> print(n = Inf, width = Inf)

source(file.path(skill_dir, "scan_packages.R"))
print_lockfile(here::here("renv.lock"))  # R and package versions, or a finding

This project has no renv.lock. scan_packages.R reports that as an explicit finding rather than an error, and the README must say so. You cannot pin versions you never recorded.

Look at the offspring column in the summary: its range will read something like 2 to 9999. The 9999 code (P8) is a real number in the file, and the summary reports it without judgement. Judging plausibility is your job. That honest, uninterpreted range is the visible trace of the sentinel.

Step 2: Hand the AI the specification and the inputs

Agent path: invoke /research-readme and let its five stages run. It will ask you for what it cannot find.

Chat path: paste the structure from references/readme_template.md and the output you just generated, with this prompt:

Prompt (chat window):

sections in the template I paste below, in order.

Use ONLY the facts I provide. Do not invent DOIs, ORCIDs, units or package
versions. Where a value is missing, insert a visible placeholder:
  **TODO: supply [field]: not provided**

Add an AI declaration stating that an AI assisted in drafting this README,

Audit the README (10 minutes)

Audit the draft against three of the skill’s rules:

  1. No fabrication. Pick three facts. Can you trace each to an input you gave? If not, it is invented.
  2. Describe, do not interpret. Did the AI assign units or meanings you did not supply? Did the 2 to 9999 range survive, or was it “tidied” into something plausible and wrong?
  3. README only. The Git pane should show that nothing except README.md changed since the commit you made before Pass 1.

Note the worst fabrication or interpretation you caught, and whether the README’s offspring range alone would have led you back to P8. The AI declarationA statement, for example in a README, recording that an AI assisted, naming the tool, model and date, and making no claim about AI use beyond what was recorded. should say no more than you told it.

# describe_csv.R ----
# Purpose: one row per column of a CSV file: name, the type readr assigns,
# missing-value count, and a brief range (numeric) or distinct-value count
# (other). Describes; does not interpret.
# Used by: research-readme skill, Stage 2.

describe_range <- function(x) {
  if (all(is.na(x))) {
    return("all values missing")
  }
  if (is.numeric(x)) {
    return(paste(min(x, na.rm = TRUE), "to", max(x, na.rm = TRUE)))
  }
  paste(dplyr::n_distinct(x, na.rm = TRUE), "distinct values")
}

# one-row-per-column summary of a single CSV ----
describe_csv <- function(path) {
  stopifnot(is.character(path), length(path) == 1L, file.exists(path))
  data_df <- readr::read_csv(path, show_col_types = FALSE)
  tibble::tibble(
    file        = basename(path),
    column      = names(data_df),
    type        = purrr::map_chr(data_df, \(x) class(x)[1]),
    n_missing   = purrr::map_int(data_df, \(x) sum(is.na(x))),
    range       = purrr::map_chr(data_df, describe_range),
    # completed by the user during Stage 2:
    description = NA_character_,
    unit        = NA_character_
  )
}

# describe every CSV in a project, skipping renv and git folders ----
describe_project_csvs <- function(project_dir) {
  stopifnot(dir.exists(project_dir))
  csv_paths <- list.files(
    project_dir,
    pattern = "\\.csv$",
    recursive = TRUE,
    full.names = TRUE,
    ignore.case = TRUE
  )
  csv_paths <- csv_paths[!grepl("(^|/)(renv|\\.git)/", csv_paths)]
  if (length(csv_paths) == 0L) {
    message("No CSV files found under ", project_dir)
    return(tibble::tibble())
  }
  csv_paths |>
    purrr::map(describe_csv) |>
    purrr::list_rbind()
}
Notescripts/scan_packages.R 
# scan_packages.R ----
# Purpose: read renv.lock and report the R version and pinned package
# versions. A missing lockfile is reported as a finding, not an error.
# Used by: research-readme skill, Stage 4.

read_lockfile <- function(lock_path = "renv.lock") {
  if (!file.exists(lock_path)) {
    return(list(found = FALSE, r_version = NA_character_, packages = tibble::tibble()))
  }
  lock <- jsonlite::read_json(lock_path)
  packages <- purrr::pluck(lock, "Packages", .default = list())

  packages_df <- tibble::tibble(
    package = unname(purrr::map_chr(packages, \(p) purrr::pluck(p, "Package", .default = NA_character_))),
    version = unname(purrr::map_chr(packages, \(p) purrr::pluck(p, "Version", .default = NA_character_)))
  ) |>
    dplyr::arrange(package)

  list(
    found = TRUE,
    r_version = purrr::pluck(lock, "R", "Version", .default = NA_character_),
    packages = packages_df
  )
}

print_lockfile <- function(lock_path = "renv.lock") {
  info <- read_lockfile(lock_path)
  if (!info$found) {
    cat(
      "No lockfile found at ", lock_path, ".\n",
      "FINDING: package versions were not recorded.\n",
      "README text: **TODO: supply R version and key package versions: ",
      "not recorded; resolve before submission**\n",
      sep = ""
    )
    return(invisible(info))
  }
  cat("R version: ", info$r_version, "\n\n", sep = "")
  print(info$packages, n = Inf)
  invisible(info)
}

# Research README generator

Produces one README.md for a repository of R code and data that accompanies a
manuscript, including the metadata that journals and archives expect:
persistent identifiers, ORCIDs, funding, per-variable descriptions with units,
an explicit script run order, and a dependency record.

## Operating constraints
These hold for the whole conversation unless the user explicitly withdraws
them.
1. The only file you create or overwrite is README.md. Do not edit, rename or
   delete any other file. If you notice an apparent error in code or data,
   record it under "Open questions" in the README or report it in chat, and
   leave the file untouched.
2. Do not fabricate metadata. DOIs, ORCIDs, grant numbers, collection dates,
   units and affiliations come from the user or from a file the user points to.
   If a value is unknown, insert a placeholder (see Placeholders).
3. Automatic summaries describe; they do not interpret. Report column type,
   missing count and range. Do not state what a variable means, its unit, or
   whether a value is plausible.
4. Work conversationally and write the file directly; do not build an app.

## Before executing
Present a short numbered plan: the folder to be scanned, that only README.md
will be written, and the five stages below. Wait for the user to confirm.

## Stage 1: Project information
Collect title, abstract, DOIs (paper; archived code and data), licences,
authors with ORCIDs and affiliations, and funders with grant numbers. Read
these from CITATION.cff, codemeta.json or DESCRIPTION if present, and ask only
for what is missing. Pair each author with their own ORCID and affiliation. If
no code licence is supplied, flag it prominently and use a placeholder; do not
choose a licence for the user.

## Stage 2: Files and variable summaries
List the data and code files. For CSV files, run
describe_project_csvs() from scripts/describe_csv.R and use its output as a
scaffold. Ask the user for each column's description and unit, and for
collection dates and locations per data file. List other tabular formats
(.xlsx, .tsv) and ask the user to describe their columns by hand. Never infer
units from column names.

## Stage 3: Script order
List executable files (.R, .Rmd, .qmd). Propose a run order using numeric
prefixes (01_, 02_) as the first signal, and ask the user to confirm or
reorder; the user's order is authoritative. Collect a one-line description of
each script. Do not run any script to determine the order.

## Stage 4: R packages and versions
Run print_lockfile() from scripts/scan_packages.R.
- If a lockfile exists, the Dependencies section states the R version, says
  that versions are pinned in renv.lock, gives the restore command
  renv::restore(), and includes the package table.
- If no lockfile exists, the Dependencies section states that package versions
  were not recorded, and contains the placeholder from print_lockfile(). Do not
  guess versions or scan the installed library.

## Stage 5: Assemble, preview and reader-test
Fill references/readme_template.md. Show the rendered Markdown in chat. Then
read it as a newcomer who has only the repository and the paper: could they
find the data, restore the environment, run the scripts in order and
understand every variable? List any section still holding a placeholder. On
confirmation, write README.md to the project root.

## Stage 6: Check the README against its sources
If the project has tests/test_readme.R, run it in a fresh R session
(Rscript -e "testthat::test_file('tests/test_readme.R')") and report the
output verbatim. Otherwise compare the README yourself: the R and package
versions against read_lockfile(), every numbered script against the scripts
folder, and every unit against the user's answers. Report the number of
placeholders left.

## AI declaration
State that an AI assisted in generating this README, naming the model if the
user wishes, with the date. Make no claims about AI use elsewhere in the
project unless the user states them, and then record exactly what they state.

## Placeholders
Write every unknown value as a visible placeholder, in exactly this form:
**TODO: supply [field]: not provided**
Flag a missing code licence and a missing code or data DOI as blocking for
submission, but still write the file so the user has a working draft.

## Scope
This skill does not audit code quality or reproducibility, and does not
produce figures. If asked to do either mid-run, say so and stop that part of
the request.

claimed execution A statement that code runs or reproduces, made without the command that was run and the output it produced. Treat it as a prediction, not evidence.
false positive In a code review, a problem the AI reports confidently that is not real, or describes wrongly.
rung One level of the autonomy ladder in Block 4, from suggesting a line (rung 0) to acting with no prompts (rung 5). Each step up removes a moment when you would have seen an action before it happened.
sentinel value A number with a special meaning, such as 9999 for "not recorded" or -1 for "run failed". It must be documented in a codebook and recoded before analysis.
