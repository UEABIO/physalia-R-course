Self-study: AI-assisted code review

You will hand a script to an AI reviewer and grade what it finds. Because you already know this script’s twelve problems, you can measure the machine rather than trust it. First, note your answer to a question the self-check returns to: if an AI code reviewer told you your analysis was clean, would you trust it enough to submit?

Self-study: about 40 minutes, after the workshop day. Start state: your workshop repository open, Git pane clean. It does not matter which blocks you finished, and there is no checkpoint branch.

NoteThis page’s files, and how it fits

The review runs outside your workshop repository, on purpose. A reviewer started there would read AGENTS.md and the voles data, so its review would not be independent of what your project already tells it. Instead you make a new folder, ~/ai-review, that holds ANALYSIS.R, the script you reviewed by hand on Day 2, and nothing else: no instructions, no settings and no data. Your workshop repository gains only your review prompt and an AI-log line.

Telling the AI how to behave

Write the review prompt (7 minutes)

Goal: a review prompt with all four parts, saved in your workshop repository, so that you can reuse it on your own scripts after the course.

1. Start from the draft below and check it has all four parts. “Review my code” alone gets a vague, generous review; a good review prompt has:

Part Why
A role and a standard: “a critical reviewer applying the four Rs” Gives the output a structure you can check
The intended analysis: the model from the OSF page, with TO a count and block B a random effect Without it, the AI cannot see that a Gaussian lmer() is the wrong family (P10)
No flattery: line number, which R, severity, a fix Keeps it to findings you can act on
Honest uncertainty: “NEEDS HUMAN CHECK” instead of guessing Shows you where to look yourself

2. Choose your version. The line about the 9999 sentinel valueA number with a special meaning, such as 9999 for “not recorded” or -1 for “run failed”. It must be documented in a codebook and recoded before analysis. tells the reviewer something the script alone cannot. Keep it, or delete it to see what the reviewer finds unaided; doing both, as two runs, shows the difference the line makes. Everything else stays the same.

3. Keep it. In your workshop repository, run usethis::edit_file("docs/review-prompt.md") in the R console, paste your prompt, save, and commit it from the Git pane. You will reuse it after the course.

You are done when your prompt has all four elements and is committed as docs/review-prompt.md.

Prompt (Claude Code):

You are a critical code reviewer for an evolutionary-biology journal.
Review ANALYSIS.R using the four Rs: Reported, Run, Reliable, Reproducible.

The intended analysis (from the pre-registration) is:
  total offspring (TO, a count: non-negative integer, often overdispersed)
  modelled as TO ~ strain * diet + (1 | B), with block B as a random effect.

Rules:
- Do NOT praise the code. Report only problems.
- For each issue: line number(s), which R it violates, severity
  (critical / high / medium), and a concrete one-line fix.
- The raw data use 9999 as a "not recorded" code. Check whether this is
  handled.                                <- delete for a run without it
- Flag anything you CANNOT determine by reading alone as "NEEDS HUMAN
  CHECK" rather than guessing.
- If you are uncertain about a finding, say so explicitly.
Organise your output by the four Rs.

Running the review

For a comparison with and without the 9999 line to work, the agentAn assistant that can read across a project’s files and, depending on its permission mode, edit them and run commands, such as Claude Code. An agent acts; a chat window only advises. must see the script and nothing else; with the data it would find the 9999 code by itself. That is why ~/ai-review holds only ANALYSIS.R. Run the review (10 minutes)

Goal: an AI review of ANALYSIS.R, made from the script alone and saved as ~/ai-review/review_claude.md, so that you can grade it against problems you already know.

Start state: your review prompt committed as docs/review-prompt.md in your workshop repository.

1. Get the script into a new folder. In the R console of any project:

review_dir <- usethis::create_project("~/ai-review", open = FALSE)
download.file("https://osf.io/download/3x6hb/",
              file.path(review_dir, "ANALYSIS.R"), mode = "wb")

create_project() prints where it made the folder. Open that folder in a new window: in RStudio, File → Open Project in New Session; in Positron, File → New Window, then open the folder there.

2. Start Claude Code there, in Manual mode. In the new window’s Terminal tab:

claude

This folder has none of your workshop settings, so check that the mode shown is Manual (default); if it is not, press Shift+Tab until it is.

3. Ask for the review. Type /plan, a space, then paste your prompt. Starting with /plan keeps it to reading. Answer each request with plain Yes or No. Never choose an option that says don’t ask again: it saves a rule that skips the question from then on. If it asks whether to proceed, choose No, keep planning.

4. Save the review. plan mode writes no files, so save it yourself: run usethis::edit_file("~/ai-review/review_claude.md") in the R console, paste the whole review and save.

You are done when ~/ai-review/review_claude.md holds the agent’s whole review.

If it goes wrong: if the download fails, download ANALYSIS.R from the OSF project in your browser into the folder create_project() reported. If Claude Code mentions AGENTS.md or the voles data, you started it in your workshop window: /exit, switch windows and start again. If you have no agent, use the chat route in Using another tool.

TipUsing another tool

Doing the Claude Code route and the chat route both shows the difference between a chat window, which can only predict whether the script runs, and an agent, which can run it (see the stretch).

Posit Assistant. Open ~/ai-review in RStudio or Positron and switch Posit Assistant to Ask mode, so it can read but not change anything, then give it your review prompt. For the stretch below, use Normal mode, so it asks before running anything.

Chat window. Paste the whole of ANALYSIS.R into any chat window, followed by your review prompt. Paste the script only, not the data. A chat window cannot run anything, but its answer to “does this run?” can read as though it did: ask “what would prevent this running?” instead.

Either way, save the review as in step 4, naming the file after the tool (for example ~/ai-review/review_chat.md).

TipStretch: let it run the script

An agent that can run R turns the Run question from a prediction into evidence. In the same Claude Code session, after you have saved your review, check that the mode shown is Manual (default): after /plan it may still be in plan, so press Shift+Tab until it shows Manual and it asks before running anything. The folder has no data, and for this it needs none: the run stops before the script reads any. Where it stops, and why, is the finding.

Prompt (Claude Code):

Run ANALYSIS.R from a fresh R session with Rscript and report the exact
output and any errors. Do not install packages; if a package is missing,
report which one. Do not edit any file.

Approve a run only if you can say what it does and why you want it now; refusing is always safe. Then read the output. “The script runs” counts only if you can see the command and its output in the conversation; without them it is a claimed executionA statement that code runs or reproduces, made without the command that was run and the output it produced. Treat it as a prediction, not evidence.. A missing package is a finding about your machine, not about the code.

Grading the review

TipBefore you grade: what AI is, and is not, good for in code review

An AI reviewer reads every line and never tires, but it sounds equally sure whether it is right or wrong. Here is where to expect help, on the four Rs of code review (Ivimey-Cook et al., 2023):

AI capability mapped onto the four Rs
R AI is likely to be... Why
Reported Useful for drafting It can summarise what the script appears to do and flag missing documentation or undocumented exclusions. It cannot know the intended analysis unless you state it.
Run Strong, if it can execute An agent that runs the script in a fresh R session can show whether it runs. A chat window can only predict, and its prediction can read as though it ran the code.
Reliable Weak Silent semantic errors (P4 precedence, P8 sentinel, P9 incomparable models, P10 wrong family) depend on context. Expect some caught, some missed and some invented, all in the same confident tone.
Reproducible Mixed It can flag a missing lockfile or session record. It can confirm that results reproduce only by running the code and comparing outputs.

The rule: treat every AI finding as a claim to check, and the absence of a finding as no evidence that the problem is absent.

Run your saved review prompt on a script before you share it, and spend your own attention on the Reliable questions.

What the evidence says. Used that way, AI review is reliably good for:

  • summarising what an unfamiliar script does;
  • flagging missing documentation, unexplained filters and hard-coded paths;
  • finding run errors, when it can actually execute the code;
  • a second pair of eyes that never tires on line 300.

In software engineering, developers acted on about three-quarters of an AI reviewer’s comments but saw only minor gains in quality, and the reviewer did worse when it was not told what the code was meant to do (Cihan et al., 2025; Cihan, 2025). Nobody has measured it on analysis scripts like this one, which is what you are about to do.

Grade the machine (10 minutes)

Goal: measure the reviewer against the twelve problems you already know, so that you learn which of its findings you can trust before you rely on one.

1. Score the review. Open the answer key, the P1–P12 table under The problems revealed in the manual code-review chapter (click Solution), beside ~/ai-review/review_claude.md:

  • Hits: which of P1–P12 did it identify correctly?
  • Misses: which did it miss? Look especially at P4 (precedence) and P8 (sentinel), the silent, consequential ones.
  • False positives: what did it flag that is not a real problem, or describe wrongly? Each one is a false positiveIn a code review, a problem the AI reports confidently that is not real, or describes wrongly..
  • Execution claims: did it claim the script runs or reproduces? On what evidence?

2. Note your result. Below the review in review_claude.md, write which version of the prompt you used (with or without the 9999 line), your hit count, your most consequential miss and your most confident false positive, with line numbers, so that a second run has something to be compared with.

3. Decide. Which one finding would you act on first, and what would you check before acting on it?

4. Record it. In your workshop repository, add a line to docs/ai-log.md (date; tool and model; task; what you kept or changed), with the reviewer’s hit count and its most confident false positive in the last part. Commit it from the Git pane.

You are done when every P1–P12 problem is marked hit or miss, you have listed the false positives, and your AI-log line is committed.

If it goes wrong: if your review never arrived, run it through the chat route in Using another tool; the grading works the same way.

NoteSelf-check (5 minutes)
  1. If you ran the review both with and without the 9999 line, compare P8. Only the data and your knowledge reveal that 9999 is a code: what does that say about reviewing code without the data?
  2. What was the reviewer’s most confident false positive, and what would acting on it have cost you?
  3. Did the agent claim the script runs without having run it?
  4. Back to the question at the start. Was your answer yes, because it read every line; only if you had also read it yourself; no, because you would trust your own review over the AI’s; or for Run, not for Reliable? Would you change it now?
NoteCheck · Reproduce · Record
  • You can now: hand a script to an AI reviewer with a prompt that makes its output checkable, trusted because you grade it against problems you already know, and treat every finding as a claim.
  • Check: grade every AI finding against the P1–P12 answer key; the absence of a finding is no evidence that the problem is absent.
  • Reproduce: a claim that the script runs counts only with the command and the output from a fresh R session; to run one yourself, see checking work.
  • Record: your review prompt and a line in docs/ai-log.md, both committed in your workshop repository: the tool, its hit count and its most confident false positive. An AI-assisted README for ~/ai-review is in Going further.

Notescripts/describe_csv.R 
# describe_csv.R ----
# Purpose: one row per column of a CSV file: name, the type readr assigns,
# missing-value count, and a brief range (numeric) or distinct-value count
# (other). Describes; does not interpret.
# Used by: research-readme skill, Stage 2.

describe_range <- function(x) {
  if (all(is.na(x))) {
    return("all values missing")
  }
  if (is.numeric(x)) {
    return(paste(min(x, na.rm = TRUE), "to", max(x, na.rm = TRUE)))
  }
  paste(dplyr::n_distinct(x, na.rm = TRUE), "distinct values")
}

# one-row-per-column summary of a single CSV ----
describe_csv <- function(path) {
  stopifnot(is.character(path), length(path) == 1L, file.exists(path))
  data_df <- readr::read_csv(path, show_col_types = FALSE)
  tibble::tibble(
    file        = basename(path),
    column      = names(data_df),
    type        = purrr::map_chr(data_df, \(x) class(x)[1]),
    n_missing   = purrr::map_int(data_df, \(x) sum(is.na(x))),
    range       = purrr::map_chr(data_df, describe_range),
    # completed by the user during Stage 2:
    description = NA_character_,
    unit        = NA_character_
  )
}

# describe every CSV in a project, skipping renv and git folders ----
describe_project_csvs <- function(project_dir) {
  stopifnot(dir.exists(project_dir))
  csv_paths <- list.files(
    project_dir,
    pattern = "\\.csv$",
    recursive = TRUE,
    full.names = TRUE,
    ignore.case = TRUE
  )
  csv_paths <- csv_paths[!grepl("(^|/)(renv|\\.git)/", csv_paths)]
  if (length(csv_paths) == 0L) {
    message("No CSV files found under ", project_dir)
    return(tibble::tibble())
  }
  csv_paths |>
    purrr::map(describe_csv) |>
    purrr::list_rbind()
}
Notescripts/scan_packages.R 
# scan_packages.R ----
# Purpose: read renv.lock and report the R version and pinned package
# versions. A missing lockfile is reported as a finding, not an error.
# Used by: research-readme skill, Stage 4.

read_lockfile <- function(lock_path = "renv.lock") {
  if (!file.exists(lock_path)) {
    return(list(found = FALSE, r_version = NA_character_, packages = tibble::tibble()))
  }
  lock <- jsonlite::read_json(lock_path)
  packages <- purrr::pluck(lock, "Packages", .default = list())

  packages_df <- tibble::tibble(
    package = unname(purrr::map_chr(packages, \(p) purrr::pluck(p, "Package", .default = NA_character_))),
    version = unname(purrr::map_chr(packages, \(p) purrr::pluck(p, "Version", .default = NA_character_)))
  ) |>
    dplyr::arrange(package)

  list(
    found = TRUE,
    r_version = purrr::pluck(lock, "R", "Version", .default = NA_character_),
    packages = packages_df
  )
}

print_lockfile <- function(lock_path = "renv.lock") {
  info <- read_lockfile(lock_path)
  if (!info$found) {
    cat(
      "No lockfile found at ", lock_path, ".\n",
      "FINDING: package versions were not recorded.\n",
      "README text: **TODO: supply R version and key package versions: ",
      "not recorded; resolve before submission**\n",
      sep = ""
    )
    return(invisible(info))
  }
  cat("R version: ", info$r_version, "\n\n", sep = "")
  print(info$packages, n = Inf)
  invisible(info)
}

# Research README generator

Produces one README.md for a repository of R code and data that accompanies a
manuscript, including the metadata that journals and archives expect:
persistent identifiers, ORCIDs, funding, per-variable descriptions with units,
an explicit script run order, and a dependency record.

## Operating constraints
These hold for the whole conversation unless the user explicitly withdraws
them.
1. The only file you create or overwrite is README.md. Do not edit, rename or
   delete any other file. If you notice an apparent error in code or data,
   record it under "Open questions" in the README or report it in chat, and
   leave the file untouched.
2. Do not fabricate metadata. DOIs, ORCIDs, grant numbers, collection dates,
   units and affiliations come from the user or from a file the user points to.
   If a value is unknown, insert a placeholder (see Placeholders).
3. Automatic summaries describe; they do not interpret. Report column type,
   missing count and range. Do not state what a variable means, its unit, or
   whether a value is plausible.
4. Work conversationally and write the file directly; do not build an app.

## Before executing
Present a short numbered plan: the folder to be scanned, that only README.md
will be written, and the five stages below. Wait for the user to confirm.

## Stage 1: Project information
Collect title, abstract, DOIs (paper; archived code and data), licences,
authors with ORCIDs and affiliations, and funders with grant numbers. Read
these from CITATION.cff, codemeta.json or DESCRIPTION if present, and ask only
for what is missing. Pair each author with their own ORCID and affiliation. If
no code licence is supplied, flag it prominently and use a placeholder; do not
choose a licence for the user.

## Stage 2: Files and variable summaries
List the data and code files. For CSV files, run
describe_project_csvs() from scripts/describe_csv.R and use its output as a
scaffold. Ask the user for each column's description and unit, and for
collection dates and locations per data file. List other tabular formats
(.xlsx, .tsv) and ask the user to describe their columns by hand. Never infer
units from column names.

## Stage 3: Script order
List executable files (.R, .Rmd, .qmd). Propose a run order using numeric
prefixes (01_, 02_) as the first signal, and ask the user to confirm or
reorder; the user's order is authoritative. Collect a one-line description of
each script. Do not run any script to determine the order.

## Stage 4: R packages and versions
Run print_lockfile() from scripts/scan_packages.R.
- If a lockfile exists, the Dependencies section states the R version, says

Glossary

term definition
agent An assistant that can read across a project's files and, depending on its permission mode, edit them and run commands, such as Claude Code. An agent acts; a chat window only advises.
AI declaration A statement, for example in a README, recording that an AI assisted, naming the tool, model and date, and making no claim about AI use beyond what was recorded.
claimed execution A statement that code runs or reproduces, made without the command that was run and the output it produced. Treat it as a prediction, not evidence.
false positive In a code review, a problem the AI reports confidently that is not real, or describes wrongly.
rung One level of the autonomy ladder in Block 4, from suggesting a line (rung 0) to acting with no prompts (rung 5). Each step up removes a moment when you would have seen an action before it happened.
sentinel value A number with a special meaning, such as 9999 for "not recorded" or -1 for "run failed". It must be documented in a codebook and recoded before analysis.
