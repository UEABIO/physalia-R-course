Block 5: From Chat to Agent

In Block 4 you used Chat in Ask mode: you asked a question, it answered, and nothing on your machine or in your repository changed unless you copied the answer out yourself. This block introduces the shift that the rest of the workshop depends on, from an assistant that advises to an agent that acts. The configuration files you write in Block 6 exist because of this shift, so it is worth being precise about what changes, where it changes, and why it matters.

⏱ ~30 minutes

Three surfaces, before we start

This workshop puts the same ideas in front of you through three different tools, and they do not all offer the same modes or honour the same files. You met this distinction in Block 4 for context; it returns here for actions, and it is the single thing most likely to make an exercise behave differently for other participants. Hold the three apart from the outset.

  • Web-based GitHub Chat on github.com. It works in the context of the repository you open it from and can read its committed files, but it has no connection to your machine and runs no local code. Its agent is the Copilot cloud agent, which acts on the remote, on its own branch. This is the surface that behaves the same for everyone, which is why several exercises specify it.

  • GitHub Copilot Chat in VS Code. The in-editor Copilot. It reads Copilot’s instruction files (.github/copilot-instructions.md, and also an AGENTS.md in the repository), runs in your local session and, in Agent mode, acts on your files.

  • Posit Assistant. Posit’s assistant for Positron and RStudio. At the time of writing (October 2026) it ships as Positron’s default AI experience, replacing the now-deprecated Positron Assistant and Databot, and is also available in recent RStudio releases. You can use it through Posit’s managed Posit AI Pass subscription or with your own provider (Anthropic, OpenAI, and others; in Positron, GitHub Copilot is available as a provider in preview). It acts locally, like the VS Code agent, but it looks for configuration in its own places: it reads an AGENTS.md file in the project root, not Copilot’s .github/copilot-instructions.md, and it loads skills from .agents/skills/ (or its own .posit/assistant/skills/). That difference is the subject of Block 6 rather than this one.

The blunt version: the cloud agent lives on github.com and is the same for everyone; Copilot in VS Code is the Copilot-aligned local agent; Posit Assistant is a separate local agent with its own configuration discovery. The one file both local agents read is AGENTS.md, which Block 6 returns to. Where a step depends on which tool you are using, it says so.

Ask, Plan, Agent

Beneath the surface differences, chat assistants offer more than one mode, and they differ in what the assistant is permitted to do, not in how clever it is. At the time of writing, Copilot Chat in VS Code offers Ask, Plan and Agent; Posit Assistant offers the same three ideas (an Ask mode, a /plan command, and its default agent behaviour). VS Code also used to offer an Edit mode that changed only the files you named; it was deprecated in VS Code 1.110 (March 2026) and removed in 1.126 (June 2026), and that kind of change is now made in Agent mode. If you see Edit mode in an older tutorial, read it as “Agent mode restricted to named files”.

  • Ask mode answers in prose. It can read context and write code into the reply, but it changes nothing for you. Everything it suggests, you apply by hand. This is the mode you used throughout Block 4, and it is available on every surface, including web-based GitHub Chat.

  • Plan mode researches the task and returns a step-by-step plan: which files it would touch, in what order, and how it would check the result. It does not change your code while it plans; you review and amend the plan, and only when you approve it does the work begin. (In Posit Assistant, the plan is written to a Markdown plan file, which is the one file it writes while planning.)

  • Agent mode is given a goal rather than a file list. It decides which files to read, which to change, and what commands to run to reach the goal, then carries those steps out, often in a loop: make a change, run something, read the result, change again.

Agent mode runs in two distinct places, and the difference is where the changes land:

  • The in-IDE agent (Copilot in VS Code, or Posit Assistant in Positron or RStudio) works on the files on your own machine and runs commands in your local session, so its actions appear in your working directory in real time.

  • The cloud agent on github.com works on your repository on the remote, in an environment you do not see, and delivers its work on a branch, usually as a pull request you review and merge.

The progression is one of widening autonomy: Ask tells you, Plan tells you exactly what it intends to do and waits, Agent decides what to change and does it. A short way to hold the distinction is that in Ask mode you are the hands and the agent is the advisor; in Agent mode the agent is both.

Mode Reads context Writes code Edits your files Runs commands Decides scope Where it runs
Ask Yes Into the reply only No No No Any surface, incl. web
Plan Yes Into the plan only No, until you approve No, until you approve Proposes it for your approval In-IDE
Agent Yes Yes Any it judges relevant Yes Yes In-IDE or cloud agent
ImportantWhich modes you can actually run

These modes are not equally available on every plan, and the cloud agent in particular is gated. Plan names, allowances and billing change often; what follows is the position at the time of writing (October 2026), so check GitHub’s Copilot plans page for your own access before the course.

  • In-IDE Chat (Ask, Plan and Agent) is usable on Copilot Free, subject to a monthly allowance and to automatic model selection only (you cannot pick the model). Copilot Student, free to verified students, has the same Auto-only model choice. Paid plans draw on a monthly allowance of AI Credits and let you choose models. For this workshop the free allowance is enough to follow the exercises, though a heavy session can reach it; if your requests stop being answered, a limit rather than a bug is the likely cause. Posit Assistant’s limits depend on how you connect it: your Posit AI Pass, or the provider whose key you give it.

  • The Copilot cloud agent on github.com is not part of Copilot Free. It is included in Copilot Student, Pro, Pro+ and Max; on Copilot Business or Enterprise it depends on your organisation’s policy. Note that this is a Copilot plan, not a GitHub Pro account, which is a different product. If you are on Copilot Free, you can run agent mode inside your IDE but not the cloud agent on the website.

The practical consequence for the exercise below: everyone can run the in-IDE route, and the cloud-agent route on github.com is only open to those with a Copilot plan that includes it. The exercise is written so the in-IDE route is the default and the cloud agent is the variant, not the reverse.

Why this is the moment configuration starts to matter

In Ask mode, a vague or unconventional answer costs you a re-read and a re-prompt. You are the filter: nothing reaches your files except what you choose to paste. An agent removes that filter. When the assistant edits files and runs commands on a goal you stated once, every convention it does not know, it will guess, and every guess lands in your project rather than in a reply you can ignore.

This is the practical reason the persistent-context mechanisms in Block 6 exist. A copilot-instructions.md (or AGENTS.md) that says you use the native pipe and write outputs only to a dedicated directory is mildly useful to an advisor and essential for an agent, because the agent acts on those conventions unsupervised. The looser the leash, the more the standing instructions matter. Put plainly: in Ask mode you can afford to correct the assistant after the fact; in Agent mode you want the conventions in place before it starts, because “after the fact” now means after your files have changed.

This is also where the three surfaces stop being interchangeable. A .github/copilot-instructions.md is honoured by web-based GitHub and by Copilot in VS Code, but Posit Assistant will not read it; Posit Assistant reads AGENTS.md instead, which Copilot also reads. An agent that cannot see your conventions does not become cautious; it proceeds anyway, on assumptions. So the surface you run the agent on decides whether the standing instructions you wrote are even in force, which is a reason to know which tool you are in before you hand it a goal.

Warning

Autonomy and trust are not the same thing. An agent that can run commands can run a wrong command. In the in-IDE agent that command executes in your local session as it works; on the cloud agent it executes in the remote environment before its work reaches you. Either way it acts before you have read it. Two habits limit the damage, and both are reasons the Block 6 instructions file matters: forbid destructive operations in standing instructions (no rm(list = ls()), no overwriting raw data, outputs only to dedicated directories), and keep the agent working against version control so any change it makes is a diff you can inspect and revert. Never run an agent with uncommitted work you are not prepared to lose.

Exercise: the same task, three modes

The same task, three modes

This exercise makes the difference concrete by giving the same kind of task to each mode in turn, growing the scope as the autonomy grows. Steps 1 and 2 use a deliberately small change so the mode, not the task, is what you are watching; step 3 hands the agent a larger, end-to-end job that a single edit could not cover, because that is the kind of job an agent is for. Have your forked workshop repository to hand, committed and clean, so that anything the agent changes is a diff you can inspect.

1. Ask mode. This works on any surface. In Ask mode, prompt:

In scripts/01_load_data.R, I want to add a column mass_change that is
mass_post_g minus mass_pre_g. How do I do that?

Read the answer. It will tell you the line to add and roughly where, and possibly explain the mutate() call. Notice what has not happened: the file is unchanged. To apply this you would copy the line into the script yourself.

2. Plan mode. This is a local-IDE step; if you are on web-based GitHub, read it and move on. In Copilot Chat in VS Code, switch to Plan mode (in Posit Assistant, type /plan), and give the same instruction as an instruction rather than a question:

Add a column mass_change that is mass_post_g minus mass_pre_g to
scripts/01_load_data.R. Change no other file.

Now you are offered a plan, not a change: which file it will edit, where, and how it will check the result. Read it before approving. Nothing has changed yet; the decision to go ahead is still yours, and you can narrow or correct the plan first. When you approve, it carries the plan out and you see the diff against that one file.

Discard the change. Read the diff, then throw it away so that step 3 starts from a clean repository. In a terminal at the project root, run git restore . to undo changes to tracked files and git clean -fd to remove any new files and folders (this deletes untracked files, which is why you committed first). Or use the Git pane: Discard All Changes in the Source Control view in VS Code or Positron, or select the changed files and click Revert in RStudio’s Git pane. git status should then report a clean working tree.

3. Agent mode. Now the task grows beyond a single edit. Rather than name a change, you state an outcome that spans the pipeline: a new derived variable, a plot that uses it, and the surrounding work needed to keep everything running. This is the kind of job that distinguishes an agent from an editor, because no one file is named and the agent must read the project, decide what to touch, and verify its own work.

This step has two routes. Use the in-IDE route if you are in Copilot in VS Code or Posit Assistant; use the cloud-agent route only if your Copilot plan includes the cloud agent (see the availability note above). The goal is the same for both; what differs is where the work happens and how it comes back to you.

In-IDE agent (default route). Switch the Chat panel to Agent mode and give it the goal:

In the voles pipeline, read data/voles_metabolism.csv through the existing
loading step, add a derived mass_change column (mass_post_g minus
mass_pre_g), and create a new script that produces an exploratory plot of
mass_change by treatment_arm. Make sure the loading step and the rest of
the pipeline still run end to end.

Watch what it does in your working directory. It cannot satisfy this from one edit: it must locate the loading step, decide whether the derived column belongs there or in a new script, write the plotting code in a new file, and run the pipeline to confirm nothing downstream broke. It works in a loop, editing then running then reading the result, and you see each change land in your working tree as it goes. This is why you committed first: every file the agent writes or alters is a diff you can inspect, accept, or revert. Read the diff before you keep it; the agent’s confidence that the pipeline “still runs” is its claim, and a claim is not a check until you have seen the output yourself.

Discard the change. Once you have read the diff, discard it as you did after step 2 (git restore . and git clean -fd, or the Git pane equivalent), so your repository is clean again for Block 6.

Cloud agent route. On github.com, hand the same goal to the Copilot cloud agent. The mechanics are worth seeing once, because a pull request is how an agent’s work reaches a real project.

  1. Open the Agents panel on github.com (or start from Copilot Chat on your repository), choose your fork, and give it the same goal as above. There is no separate “agent mode” switch on github.com: starting a task from the Agents panel is handing it to the cloud agent. You can also assign a GitHub Issue to Copilot, but for this exercise prompting it directly is enough.

  2. The agent starts a session on the remote, in an environment you do not see. It works on a new branch rather than your default branch, so nothing it does affects your main line of work until you decide it should.

  3. It then works through the goal on that branch, committing as it goes: reading the data, editing the loading step, adding the plotting script, and running the pipeline to check it. You can follow its progress in the session log while it runs, and steer or stop it from the Agents page if it heads the wrong way.

  4. When it finishes, you can review its changes and ask for refinements before anything is proposed for merging; ask it for a pull request (or include “open a pull request” in your first prompt). A pull request is a proposed merge: a named, reviewable bundle of commits asking to be brought into your main branch. This is the unit you review, not the individual edits.

  5. Open the pull request and read the Files changed tab. This is the diff: every line the agent added or removed, across every file it touched. Read it as you would a colleague’s contribution, because that is what it is. Check that the derived column is computed correctly, that the plot uses the right variables, and that nothing unrelated was changed.

  6. In a real project, if you are satisfied, you would merge the pull request, which brings the changes into your main branch on the remote; then git pull locally to bring them to your machine. If you are not satisfied, you can comment on the pull request to ask the agent to revise it, or simply close it and discard the branch. Nothing reaches your main branch, or your local working tree, until you choose to merge. For this exercise, close the pull request without merging once you have read it, so your repository is clean again for Block 6. If you did merge it, ask the instructor how to revert the merge before you start Block 6.

The review step is built into the cloud agent’s flow: it never edits your working files directly, and its work arrives on a branch as a proposal you approve rather than a change you discover. The in-IDE agent gives you speed and immediacy; the cloud agent gives you a review gate by default.

Whichever route you took, notice the autonomy you handed over: you specified an outcome and the agent chose the steps, the files, and the order. The agent decides just as much on both routes. What differs is where its decisions take effect: live in your working tree, or on a branch behind a pull request you approve first.

4. The point of the comparison. Re-read the results together. What differed across the modes was how much you decided versus how much the assistant decided. In Ask mode you placed every character. In Plan mode you approved a stated intention, for one file you named, before anything changed. In Agent mode you approved an outcome and trusted the agent to choose the files, the steps, and the order, whether that ran live in your working tree or on a branch behind a pull request. The step-3 task was large enough that you could not have specified it edit by edit in advance, which is the point: an agent is for the jobs where stating the goal is tractable but stating every step is not. Ask yourself whether the agent structured the pipeline the way you would have, whether the plot answers the question you meant, and whether you would have caught it had it not. That question, scaled up to a task you cannot read line by line, is why the standing instructions in Block 6 are written before the agent runs, not after, and why it matters that the surface you run on is one that reads them.
